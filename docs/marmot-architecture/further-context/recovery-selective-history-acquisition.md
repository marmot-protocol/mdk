# Selective history acquisition budget qualification

This note covers one adapter slice of [#1947](https://github.com/marmot-protocol/mdk/issues/1947). Production bounded recovery remains disabled. The account recovery owner still chooses the route/window, retains the durable obligation, and admits returned ciphertext through the worker. This change does not make NIP-77 exhaustive, establish older history beyond the retained inventory floor, or remove the ordinary broad replay that a separate activation may run alongside comparison.

## Replaced execution path

`NostrSdkRelayClient::reconcile_subscription` still dry-runs NIP-77 against the caller's retained IDs and selects at most 128 remote-only IDs in cursor order. The previous missing-ID branch sent those IDs in one SDK `fetch_events` filter to every endpoint. That call had a timeout but no received-item or serialized-event byte budget. It could transfer the whole selected payload set, including duplicate copies from two relays, before the app learned whether it could retain any of it.

The replacement uses the same account client and the request-local SDK `acquire_history(KnownEventIds)` path. It asks for one selected ID at a time, at most 16 exact-ID requests in one comparison. The whole comparison retains its two-second deadline; the acquisition receives only the time left after negotiation and local cache reads. Full-event SDK cache hits spend the same combined 16-item / 128-KiB-serialized-event returned-result allowance as fetched events. For network requests, the adapter charges the largest per-endpoint reported cost of each request; charging the maximum is conservative when endpoints use different amounts. SDK accounting includes duplicates and the item that crosses a budget boundary. The adapter can therefore observe one rejected over-budget event beyond its retained-result allowance; the allowance is not a WebSocket-byte or memory ceiling.

Before each potentially cancellable exact-ID request, the account-owned route cursor records that ID. A cached event that fits the remaining allowance also records its ID before joining the result; a fitting cache entry deferred by earlier results leaves the cursor in place for the next pass. A cached object larger than the entire allowance remains incomplete but rotates past the cursor so later smaller IDs are reachable and the large ID recurs on wrap. A cancelled or refused ID is still remote-only until durable account admission removes it. One-ID requests avoid a relay's fixed response order repeatedly sending the same affordable prefix ahead of a missing later ID. This costs up to 16 REQs per endpoint instead of the previous single batch REQ; the fixed request count and original deadline cap one pass. Compatible live subscriptions remain owned by the SDK and are not closed by request cleanup.

The adapter sorts returned events by authored time and ID and deduplicates cross-relay copies before returning an owned batch. Fetched events retain their observed endpoint label; cached bytes retain the existing first-route label because cache provenance is unavailable. A byte, item, deadline, or unattempted-suffix exit keeps eligible partial events but marks affected endpoints incomplete in `NostrReconciliationSummary`. An endpoint that reported an ID in NIP-77 but then reaches EOSE without its bytes is also incomplete. If a suffix was not attempted, every endpoint is incomplete for this pass. The app maps any failed endpoint to a transient comparison outcome. Even a successful NIP-77 exchange and every exact-ID EOSE remain operational observations, not complete-history or durable-admission proof. Empty endpoint sets retain their existing no-op result; endpoint setup/rejection remains retryable and does not become backend-wide `Unsupported`.

## Controlled protocol-byte evidence

`selective_history_acquisition_tests.rs` places a counted WebSocket proxy in front of each of two local relays. It counts complete text messages before SDK duplicate filtering, separating EVENT JSON bytes from control text. Both relays hold the same 1,108 kind-445 events, including 1,100 locally retained IDs and eight missing events with 40 KiB content each.

- With all 1,108 IDs in the caller inventory, the comparison returned no events and issued zero REQs. One measured run used 1,724 total WebSocket text bytes; the deterministic fixture ceiling is 160 KiB, including both relays and all control traffic.
- With eight missing IDs, the old fetch sent 331,112 EVENT JSON bytes from the first relay in one pass and failed the fixture's 180 KiB per-relay bound. The bounded path keeps each pass below that bound, including duplicate copies and the rejected boundary event, then admits returned IDs into the test inventory and reaches all eight within four passes. One measured run used ten exact-ID REQs per relay over the whole sequence, 25,492 control-text bytes, and 827,780 prefilter EVENT JSON bytes across both relays and retries. The extra requests and boundary redelivery are a real tradeoff; the fixture asserts an absolute control-byte ceiling of 160 KiB for the complete sequence.
- A relay that repeats one EVENT beyond the item allowance yields one deduplicated owned event and a mixed one-success/one-failure summary. A relay that never answers the exact REQ yields the healthy relay's event and a mixed summary after the finite deadline. A relay that claims the ID in NIP-77 but omits the exact EVENT likewise stays incomplete. None of these partial results certifies coverage.
- A warm full-event SDK cache returns eight 40-KiB objects over finite passes with each returned batch within 128 KiB and no network REQs. A cache object larger than the whole allowance is omitted and incomplete while a smaller cached ID remains reachable. A mixed cache/network fixture shares one returned-result allowance and resumes the deferred fourth ID after admitting the first three.

These are synthetic local WebSocket text measurements. The 180 KiB assertion applies to this event-size fixture, not arbitrary event sizes, carrier-billed bytes, process RSS, or concurrent ordinary replay. The tests do not prove app SQLCipher retention, process-crash recovery, complete P6, or the cold-reopen 36-group workload. The compatible ordinary replay and automatic account-wide overflow acquisition still need their own bandwidth and admission qualification before activation.
