# Upgrading MDK 0.10.2 → 0.10.3

## Scope and provenance

This guide compares `v0.10.2` / `marmotkit-v0.10.2` at
`7dba6fc83eb054c6d703da182300a8e0f140eefc` with the source shipped as
`v0.10.3`. All four 0.10.3 cohort tags must peel to the release PR's merged
commit; packaged manifests record that exact SHA. The behavior comparison was
prepared against master `11632573ecb492772449fc3576c34fabf830b65b` (use the full release SHA from the tags for
artifact verification). This guide ships in the release commit, not a later
supplement. See the [release notes](../release/0.10.3.md),
[previous upgrade guide](0.10.2.md), and
[current binding reference](../../crates/marmot-uniffi/README.md).

## Upgrade decisions

| Category | Required action or effect |
| --- | --- |
| Required | Replace generated Swift/Kotlin, native libraries and C headers together; rebuild all consumers and manually constructed prepared-row records. |
| Existing requirement | Keep Apple privacy resource wiring and Android initialization before constructing Marmot. |
| Optional UI adoption | Render the selected `preview` and use `actions` for chat-row menus. |
| Automatic behavior | Both live list APIs refresh after draft mutations; ordering and unread state stay unchanged. |
| Automatic fixes | Profile lookup tolerates optional AUTH; Android salt creation avoids sandbox-denied hard links while retaining API 26. |
| Operator tooling | Use the Hermes installation doctor for bounded, read-only observations. |
| Unchanged defaults | No new migration, download policy, storage quota, deployment target or exporter feature default. |

## Required upgrade steps

1. Pin all inputs to 0.10.3 and verify the release manifest source SHA and hashes.
   Never combine the new generated records with 0.10.2 native libraries.
   `PresentedChatRowFfi` / `MarmotPresentedChatRow` add `preview` and `actions`;
   update test fixtures, record constructors and any raw layouts.
2. Preserve the Swift wrapper's `PrivacyInfo.xcprivacy` resource and dependency
   from every app/extension. Update the binary ZIP, shared Swift file and platform
   privacy file together. See the [distribution contract](../../crates/marmot-uniffi/DISTRIBUTION.md).
3. Android retains API 26. Call `MarmotAndroid.initialize(context)` before creating
   `Marmot`; stage the matching Kotlin helpers and all required JNI ABIs together.
4. No migration follows 86 in this release. Existing 0.10.2 databases reopen on
   the same schema; upgrading from older cohorts still has their migration and
   downgrade restrictions. Back up before such upgrades; restore a pre-upgrade
   export or re-upgrade instead of removing migration rows. See the
   [storage-format definition](../marmot-architecture/storage-format-v2.md).

## Selected chat previews and row actions

Use the existing bounded `openChatListWindow` handle, presented-list subscription,
list snapshot or keyed presented-row read. No new query or network request is
needed to obtain the added fields. Take the initial snapshot, consume live
updates, page using the returned sequence and retain the visible anchor. Replace
rows from each authoritative snapshot; draft changes are visible through the
live sequence, not `presentation_version`, which versions selected identity.
See [the complete row contract](../../crates/marmot-uniffi/CHAT-LIST-ROWS.md).

The preview enum selects Draft, Message, Invitation or Empty. Draft wins only
for non-whitespace text or attachments. Render Message from the same row's
`row.last_message`. A reply-only draft does not hide that message. A pending
invitation can select Message while still requiring an invitation indicator:
`row.pending_confirmation` remains independent. Clients localize draft labels,
attachment kinds/counts and invitation/empty placeholders.

Draft text is trimmed to at most 1,024 Unicode scalar values, with
`text_truncated` marking shortening. Attachment summaries contain kind/count,
never filenames, URLs or bytes. These are private plain-text previews: do not
log them or rebuild the composer from them. Continue using revisioned draft
APIs for the exact composer content and durable send acceptance. A newer draft
edit survives an older send. Failed sends do not grant permission to clear it.

Illustrative rendering fragments (application render helpers are placeholders;
the DTO names/cases follow the generated binding smoke tests):

```swift
switch prepared.preview {
case .draft(let draft):
    renderDraft(text: draft.text, count: draft.attachmentCount,
                kind: draft.attachmentKind, shortened: draft.textTruncated)
case .message: renderMessage(prepared.row.lastMessage)
case .invitation: renderInvitationPlaceholder()
case .empty: renderEmptyPlaceholder()
}
```

```kotlin
when (val preview = prepared.preview) {
    is SelectedChatPreviewFfi.Draft -> renderDraft(preview.draft)
    SelectedChatPreviewFfi.Message -> renderMessage(prepared.row.lastMessage)
    SelectedChatPreviewFfi.Invitation -> renderInvitationPlaceholder()
    SelectedChatPreviewFfi.Empty -> renderEmptyPlaceholder()
}
```

Reads use one local database snapshot for row and draft metadata and inspect
only returned groups' drafts, with no engine hydration. They do not load
attachment plaintext. Paging remains bounded by the existing window contract;
SQLite still inspects the selected drafts' text/metadata to trim/count it. Draft
changes do not move chats, alter filters/pins or create unread activity. A draft
outside the retained window appears when its row is paged in.

Treat `actions` as advisory menu availability. Read/unread, pin/unpin, mute/unmute
and archive/restore use the existing commands and their current-state checks.
`canStartLeave` requires the existing authoritative leave preflight, including
admin-demotion/disband decisions; `canDeleteLocal` is for eligible terminal
history and still needs host confirmation. Restoring archived departed history
does not rejoin it. Pending or queued departures must not be treated as ordinary
active membership. Preserve state/error handling if a command rejects stale UI.
Do not blindly retry mutations after arbitrary errors: durable intent or external
effects may already exist. Read authoritative state first.

Swift owns generated values/handles through its binding lifetime. Keep live
handles screen-scoped and end their existing subscription/task lifetime when the
screen or account goes away. Kotlin must close generated handles (for example
with `use`/`finally`) and cancel collecting coroutines. Apply snapshots on the UI
executor and keep blocking work off it. Existing APIs remain supported; no new
formal deprecation is introduced.

### C and Rust hosts

C's `MarmotSelectedChatPreview` is a tagged union; inspect its tag before its
`DRAFT` payload. The draft's text is owned by its parent row. Do not free embedded
fields separately: use `marmot_presented_chat_row_free`,
`marmot_presented_chat_list_snapshot_free`,
`marmot_presented_chat_list_update_free`, or
`marmot_chat_list_window_snapshot_free` for the returned root. Use the matching
subscription free function for handles. Do not retain pointers after root free.
As of 0.10.3, ordinary host-thread `marmot_client_free` also waits for runtime
worker cleanup, preventing database destruction from racing SQLCipher process
exit. Release subscriptions, shut down, and perform final free off the UI thread.
Free from inside a Tokio runtime context remains nonblocking to avoid deadlock;
it is not a process-teardown barrier. No C signature changes for this fix.

C calls/next operations block; run them off the UI thread, handle timeout/closed
statuses, and serialize callbacks into the host's UI lifetime. See the
[C reference](../../crates/marmot-c/README.md).

Rust hosts receive the same prepared preview/actions and draft invalidations.
Account identity salt publication on Android now uses a private stable
`.publish.lock` sibling and ordinary rename, with the canonical destination
preserved under competing creators. Never unlink that lock while publishers can
run. The helper blocks on its filesystem lock; use a thread that permits blocking
I/O. This changes publication mechanics, not key derivation or the stored salt
format. Other platforms retain their existing publication path.

## Changes requiring no new calls

Public profile fetches set the Nostr client's optional-authentication policy so
an AUTH challenge does not interrupt public lookups. This does not guarantee
access to relays that actually require authentication or network availability.

Hermes operators can run `install-hermes-marmot.sh --doctor --json` for installation,
service, connector and plugin observations. It does not install, repair or prove
message delivery. Unknown/ambiguous configuration stays unknown; diagnostic
status and ACK lifecycle observations do not establish recipient delivery.
The original adapter welcomer resolution is preserved. Review
[Hermes operations](../../integrations/hermes/marmot/README.md) for configuration.

Attachment acquisition, retention, deletion provenance and local-first KeyPackage
inventory were already in 0.10.2; follow its guide when skipping that release.
`Delivered` remains local source-backed publication, not a recipient read receipt.

## Acceptance and remaining work

Compile matched release inputs, then exercise these consuming-app checks:

- Text, attachment-only, mixed, whitespace and reply-only drafts; incoming messages
  while Draft is selected; clear/send-failure/newer-edit races on both list APIs.
- Invitation indicators, mute expiry, archived/Left actions, leave preflight,
  deletion confirmation and stale-action rejection.
- Offline reopen, cold start, paging/anchor retention, account switches and screen
  cancellation; foreground/background restoration without leaked collectors.
- Android API 26 and current devices: first identity creation, concurrent creation,
  restart with the existing salt, and initialization before JNI calls.
- Optional-AUTH public lookup, offline failures and authenticated relay behavior.
- Representative large draft/history workloads without loading attachment bytes;
  C deep-free and callback shutdown paths, plus Apple privacy archive delivery.

Source signatures and host DTO round trips are separate evidence from packaged
artifacts, consuming-app archives and real-device acceptance. This guide does not
claim client adoption or device performance results. Existing Apple required-reason
and SDK-signing questions remain in [#1874](https://github.com/marmot-protocol/mdk/issues/1874).
No new App Store acceptance claim is made by this SDK release.
