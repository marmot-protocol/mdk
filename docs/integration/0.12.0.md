# Upgrading MDK 0.11.0 → 0.12.0

## Scope and provenance

This guide compares `v0.11.0` / `marmotkit-v0.11.0` / `marmotc-v0.11.0` /
`wn-agent-v0.11.0`, which all peel to
`946e0547485c9a2c393c2048ec3a968fd50fb441`, with the source to be shipped as
`v0.12.0`. All four 0.12.0 cohort tags must peel to the release PR's merged
commit, and packaged manifests must record that exact SHA. The behavior comparison
was prepared against `origin/master` at
`6275d69aba4b360604e6e3b61ddd3b8c5b218e1a`; use the full release SHA from the
tags for artifact verification. This guide ships in the release commit, not a
later supplement. See the [release notes](../release/0.12.0.md),
[previous upgrade guide](0.11.0.md), and
[current binding reference](../../crates/marmot-uniffi/README.md).

Readers: native app hosts (Swift/Kotlin through MarmotKit), C hosts, Rust hosts
that embed `marmot-app`, and WN Agent operators.

## Upgrade decisions

| Category | Required action or effect |
| --- | --- |
| Required | Replace generated Swift/Kotlin, native libraries and C headers together. Update exhaustive `MarmotKitError` handling for `InvalidAppComponent`. Pass `reactionMessageIdHex` when constructing `ConversationReactionFfi` by hand; it has no binding default. |
| Required for C hosts | Recompile. Six account entry points gain trailing `inbox_relays` / `inbox_relays_len`, and `MarmotMediaUploadRequest` and `MarmotConversationReaction` gain trailing fields. |
| Required storage | Back up, then allow migrations 99–101 to complete on first open. Downgrade across them is unsupported. |
| Required for Rust hosts | Set the new fields in full struct literals (see [Rust host changes](#rust-host-changes)) and handle `AppError::InvalidAppComponent`. |
| Strongly recommended host UI | Render NIP-30 custom emoji in chats and reactions. Peers on 0.12.0 can send them; without rendering, users see `:shortcode:` text. |
| Strongly recommended | Route ordinary attachment taps through `requestExplicitAttachment` instead of `controlAttachment(Retry)`. |
| New defaults | A durable chat mute lets direct mentions of the account through to notification subscriptions. Sent attachments are retained locally for the sender. Recovery parks behind a required relay that never answers. |
| Optional adoption | Per-voter poll results (`pollVotes`), application-owned group components, a separate kind-10050 inbox relay list, sending custom emoji. |
| Automatic fixes | Agent-sent attachments download, missing-key deferrals terminate, route changes keep recovery progress, catch-up and group creation are faster on large accounts, publishing reuses connections, audit v5 keeps engine disposition reasons. |

## Required upgrade steps

1. Pin all MDK, MarmotKit, Marmot C and WN Agent inputs to 0.12.0. Verify the
   source SHA in each manifest and every sibling checksum. Do not combine new
   generated records or headers with 0.11.0 native libraries.
2. Rebuild Swift/Kotlin clients after updating exhaustive handling:
   - `MarmotKitError` gains `InvalidAppComponent { details }`, returned only by the
     new app-component methods.
   - `ConversationReactionFfi` gains `reactionMessageIdHex: String?`. It has no
     binding default, so records the host constructs (previews, fixtures) must
     pass it, normally as `nil` / `null`.
   - `MediaUploadRequestFfi.messageTags` and `OnboardingOptionsFfi.inboxRelays`
     are new fields with empty binding defaults.
   - New types: `GroupAppComponentFfi`, `PollVoteFfi` and `PollVotePageFfi`.

   Six existing methods gain a trailing `inboxRelays` parameter with an empty
   binding default: `createIdentity`, `createIdentityWithProfile`, `login`,
   `loginRecoveringIncompleteSetup`, `loginExternalSigner` and
   `publishRelayLists`. Existing Swift/Kotlin call sites compile unchanged and
   keep the 0.11.0 behavior. No other existing exported method changed its
   signature (compared against the `v0.11.0`
   [method reference](https://github.com/marmot-protocol/mdk/blob/v0.11.0/crates/marmot-uniffi/API-REFERENCE.md)).
3. Recompile C consumers. `marmot_create_identity`,
   `marmot_create_identity_with_profile`, `marmot_login`,
   `marmot_login_recovering_incomplete_setup`, `marmot_publish_relay_lists` and
   `marmot_begin_onboarding` take trailing `inbox_relays` / `inbox_relays_len`;
   pass `NULL, 0` for the previous behavior. `MarmotMediaUploadRequest` appends
   `message_tags` / `message_tags_len` (`NULL, 0` for none), and
   `MarmotConversationReaction` appends the nullable `reaction_message_id_hex`,
   which the existing deep-free releases. `MARMOT_STATUS_INVALID_APP_COMPONENT`
   is 95; existing status and event values are unchanged. Use only the header
   shipped with the exact library.
4. Preserve the Swift wrapper's `PrivacyInfo.xcprivacy` resource and dependency in
   every app and extension. Update the binary ZIP, shared Swift file and privacy
   resource together. Android still requires `MarmotAndroid.initialize(context)`
   before creating `Marmot`, and all JNI ABIs must come from one cohort.
5. Back up each account database before first open. See
   [Storage upgrade](#storage-upgrade).
6. Add custom emoji rendering. See [NIP-30 custom emoji](#nip-30-custom-emoji-strongly-recommended).
7. Rust hosts: see [Rust host changes](#rust-host-changes).

## Storage upgrade

Account databases advance from schema 98 to 101 on first open:

- 0099 adds a `preparation_deferrals` counter so missing-key attachment
  deferrals back off and fail on the sixth consecutive miss.
- 0100 replaces an attachment-priority trigger so a tapped attachment keeps its
  explicit priority when its history row is reprojected.
- 0101 adds bounded outgoing-upload retention records (at most 256 outstanding)
  for genuinely sent files.

These migrations add a column, a trigger and small tables; they do not rebuild message
history. Downgrade across them is unsupported: the 0.11.0 binary
refuses the upgraded database before reading application tables. Re-upgrade or
restore a pre-upgrade backup/export instead of removing migration rows. See the
[storage-format contract](../marmot-architecture/storage-format-v2.md).

## Feature adoption

### NIP-30 custom emoji (strongly recommended)

Clients on 0.12.0 can send custom emoji in chats and reactions. The image is an
ordinary encrypted Marmot attachment; the `["emoji", shortcode, url]` tag names it
by its first locator.

- **Render chats.** Conversation-window kind-9 rows now keep NIP-30 `emoji` tags in
  `timeline.tags` (other reserved-kind tags are still dropped). For each
  `:shortcode:` in the text, find the `emoji` tag with that shortcode and render
  the row's attachment whose `imeta` locator matches the tag URL inline. Fall back
  to the literal `:shortcode:` text when no tag or attachment matches. An `emoji`
  URL that matches no attachment is not a decryptable Marmot reference; never
  fetch it.
- **Render reactions.** `ConversationReactionFfi.reactionMessageIdHex` names the
  earliest active kind-7 that carries the reaction's emoji. For a `:shortcode:`
  reaction, `listMedia` returns its image under that message id; resolve and
  cache it as you would a chat attachment.
- **Send.** Upload the image with `uploadMedia` and `send = false`, then send the
  returned `attachments[].reference` through `sendTaggedMedia` (a chat containing the image) or
  `reactWithMedia` (a reaction), naming it with
  `["emoji", shortcode, reference.locators[0].value]`. `sendTaggedText` sends text
  with tags but no attachments. `MediaUploadRequestFfi.messageTags` tags an upload
  that sends immediately.
- **Limits.** At most 64 tags and 16 KiB of tag values per event. `imeta` rows are
  rejected (attachments carry their own), and `e` / `q` rows need a non-empty
  target. Reaction images keep their media epoch secret like chat attachments, so
  they stay decryptable after the group advances.

Illustrative Swift (check names against your generated `MarmotKit.swift`):

```swift
// `upload` is a MediaUploadRequestFfi with `send: false`.
let result = try await marmot.uploadMedia(accountRef: account, groupIdHex: group,
                                          request: upload)
let ref = result.attachments[0].reference
let url = ref.locators[0].value
_ = try await marmot.reactWithMedia(accountRef: account, groupIdHex: group,
                                    targetMessageId: messageId, emoji: ":party:",
                                    tags: [["emoji", "party", url]],
                                    attachments: [ref])
```

C uses `marmot_send_tagged_text`, `marmot_send_tagged_media`,
`marmot_react_with_media` and `MarmotMediaUploadRequest.message_tags`.

### Per-voter poll results (optional)

`pollVotes(accountRef, groupIdHex, pollEventId, afterVotedAt, afterVoterAccountIdHex, limit)`
returns a `PollVotePageFfi` of each voter's effective selection for a "View votes"
sheet. It uses the same rules as `TimelineMessageRecordFfi.poll`, so all pages sum
to each option's `votes` and to `participants`.

- Omit both cursor fields for the first page; then pass the last vote's `votedAt`
  and `voterAccountIdHex` while `hasMoreAfter` is true. `limit` is 1–100.
- It is a synchronous local query: run it off the UI thread. Re-read from the start
  when the poll row is reprojected.
- Blocked voters stay listed because the tally counts them; mark them using the
  account's block list. A missing, deleted, hidden or non-poll row returns an
  empty page.
- Polls are not anonymous: every member can already read each response and its
  sender. Say so wherever votes are shown.

C uses `marmot_poll_votes` and frees the page with `marmot_poll_vote_page_free`.
See [Polls](../../crates/marmot-uniffi/POLLS.md).

### Application-owned group components (optional)

`groupAppComponent(accountRef, groupIdHex, componentId)` reads and
`updateAppComponent(accountRef, groupIdHex, componentId, data)` replaces one
optional application-owned component in the group's MLS state. Use it for shared
group settings that must survive message expiry and reach new members in their
Welcome without sharing message history.

- Ids must be `0xf000` or above. The protocol registry allocates upward from
  `0x8001`, so pick ids inside the application range and version your payloads.
  Use the typed profile, image, retention and policy APIs for protocol settings.
- `data` is at most 4096 bytes. The application-owned state as a whole is capped at
  32 entries and 8192 encoded bytes. It is re-encoded into every later commit and
  Welcome, so treat it as a settings channel, not a blob store.
- `nil` / `null` means absent; a record with empty `data` is present empty state.
  Writing empty `data` does not remove the component.
- Updates are admin-only MLS commits with the usual publication and convergence
  semantics: handle publication uncertainty and `GroupChangeSuperseded`. The
  runtime does not retry an application's desired value. Refresh reads after group
  events (including `EpochChanged` and convergence) and after local updates; reads
  queue behind in-flight account-worker mutations.
- Invalid ids, components the group requires, and oversized data fail with
  `MarmotKitError.InvalidAppComponent` (C: `MARMOT_STATUS_INVALID_APP_COMPONENT`).

C uses `marmot_group_app_component` (free with `marmot_group_app_component_free`)
and `marmot_update_app_component`.

### Separate kind-10050 inbox relays (optional)

Hosts can declare the kind-10050 inbox relay list separately from the NIP-65 list.
Pass `inboxRelays` to `createIdentity`, `createIdentityWithProfile`, `login`,
`loginRecoveringIncompleteSetup`, `loginExternalSigner` or `publishRelayLists`,
or set `OnboardingOptionsFfi.inboxRelays` for onboarding's recommended inbox list.
Empty keeps declaring `defaultRelays` in both lists, as in 0.11.0. Persisted setup
contexts and onboarding checkpoints written by 0.11.0 resume unchanged.

### Explicit attachment requests (strongly recommended)

`requestExplicitAttachment(accountRef, groupIdHex, target)` joins a current
source or promotes automatic demand to explicit priority without resetting retry
budgets, scheduled backoff or active deadlines. Use it when a user taps an
attachment. Reserve `controlAttachment(Retry)` and `downloadAttachmentAgain` for
deliberate recovery after a failure. A returned reference does not promise
readiness: inspect transfer state and prefer local assets first. Cancelled,
removed, exhausted and failed sources are not rearmed. C uses
`marmot_request_explicit_attachment`. See
[Attachment access](../../crates/marmot-uniffi/ATTACHMENT-ACCESS.md).

## Changed defaults

- **Muted chats and mentions.** A durable chat mute still suppresses ordinary
  notification traffic, but a direct mention of the receiving account now reaches
  notification subscriptions with `NotificationUpdateFfi.isMention = true`.
  Blocked senders stay suppressed. Hosts apply their own permission, channel and
  foreground policy; a host that wants mutes to silence mentions too must filter
  them itself.
- **Sent attachment retention.** After a successful upload, the runtime stages a
  private local copy bound to the confirmed source, so the sender reopens the file
  without downloading it again. Staging is best-effort and bounded; a staging,
  quota or disk failure never blocks the send.
- **Recovery parking behind dead relays.** When one required relay never answers
  while another does, history recovery stops after six such comparisons for the
  unchanged goal and raises the existing "history may be incomplete" notice
  instead of retrying forever. Offline passes and deadline-cut routes spend no
  budget.
- **Onboarding indexer search.** Import and external-signer onboarding also
  search the built-in public indexers for an identity's profile, follows and
  relay lists, so an existing list is not mistaken for missing. A missing list is
  concluded only when every searched relay answers. Repairs still publish only to
  the host's discovery relays and the account's declared relays. A set chosen with
  `setOnboardingDiscoveryRelays` is used as given, without indexers.

## Rust host changes

- `AccountSetupRequest::inbox_relays`, `AccountRelayListBootstrap::inbox_relays`
  (`with_inbox_relays`), `OnboardingOptions::inbox_relays` and
  `MediaUploadRequest::message_tags` are new fields; set them in full struct
  literals or use `..Default::default()`.
- `ConversationReaction::reaction_message_id_hex` is a new field.
- `AppError::InvalidAppComponent(String)` is new (error code
  `invalid_app_component`); update exhaustive matches.
- New runtime methods: `group_app_component`, `update_app_component`,
  `request_explicit_attachment`, `poll_votes`, `send_tagged_text`,
  `send_tagged_media` and `react_with_media`.
- The engine's `GroupEvent::MessageReceived` gains an optional
  `encrypted_media_secret` (`EncryptedMediaSecret`, `Debug` redacted). Patterns
  that destructure the variant without `..` must add it. It is serde-defaulted,
  so pending events stored by 0.11.0 still decode.
- Account-worker startup records six in-flight runtime operations
  (`account_startup_spawned`, `_open_queued`, `_account_state`, `_session_open`,
  `_client_restore`, `_ready_handoff`). An expired ready-wait now fails with
  `account worker startup timed out at <stage>`; match on the prefix if you
  matched the old message exactly.
- `transport-nostr-adapter` adds the non-breaking
  `NostrSdkRelayClient::from_builder` constructor; `new(Client)` is unchanged.

## WN Agent and integrations

- **Group profile updates.** The control protocol adds `group_profile_update`. An
  agent whose account is a current group admin can change the group name,
  description or both. Omitted fields are kept, an empty string clears, success
  returns the published commit message ids, and a lost admin role returns
  `not_group_admin`. Hermes registers the `marmot_group_profile` tool, which
  reports an unknown outcome on a control timeout so the caller checks current
  group details before retrying.
- **Profile publishing.** `account_publish_profile` merges the request into the
  currently published kind:0 profile instead of replacing it, and accepts optional
  `about`, `picture`, `nip05` and `lud16`. Fields the request omits survive. A
  relay read error fails the publish rather than writing a partial profile. Older
  clients that send only `name` and `display_name` still decode.
- **Attachments.** `wn-agent` flushes downloaded files before returning their
  path, so inbound files no longer fail harness validation on the first try.
  `wn-opencode` passes attachments with `--file`; `wn-pi` passes images and UTF-8
  text with `@<path>` and needs Pi 0.79.6 or later for attachments. Both reject a
  turn whose attachment cannot be read before spawning the harness.
  `send_artifacts` waits for the `send_media` reply for the worst-case upload
  time.
- **Installers.** Install only from the immutable `wn-agent-v0.12.0` release with
  sibling `.sha256` verification. See the
  [integrations quickstart](../../integrations/README.md).
- The control socket still grants its whole API to an authenticated client;
  capability-scoped grants remain tracked in
  [#1445](https://github.com/marmot-protocol/mdk/issues/1445).

## Changes requiring no new calls

- **Agent-sent attachments.** A media message surfaced after the group advanced
  past its epoch no longer stays in `RetryScheduled` forever. The engine captures
  the media key for the message's source epoch while authenticating it, and falls
  back to retained epoch state (newest five epochs). Retry and download-again
  derive a missing key the same way, so attachments projected before this release
  can recover while their epoch is retained.
- **Terminal attachment failures.** Missing-key deferrals back off from 15 to
  240 seconds and fail after about eight minutes. A blob that every Blossom server
  reports as 404/410 fails without retrying.
- **Recovery progress.** A route change, such as creating a DM, no longer restarts
  recovery for every route; unchanged routes keep their certificates.
- **Large accounts.** Host catch-up and post-group-change catch-up drain live input
  and return without running recovery on the account worker, so sends,
  conversation opens and new DMs no longer wait behind it. Group creation installs
  only the invitees' inbox routes, and the post-join sweep is no longer quadratic in
  the number of chats.
- **Recovery comparisons** no longer fail when a route changes after the
  comparison was requested.
- **Convergence.** A convergence pass that selected no branch no longer withdraws
  messages as undecryptable.
- **Publishing.** Each account keeps a retained, signerless publisher for group and
  push traffic (at most 16 idle connections for 60 seconds). Push notification
  chunks publish four at a time per server with at most 19 tokens per envelope.
- **Audit v5** rows keep the engine's `pre_membership_event`,
  `app_payload_retention_expired`, `peel_failed_no_snapshot` and
  `quarantined_group_input_deferred` reasons instead of `unclassified`. Older v5
  rows stay ambiguous.

## Acceptance and remaining work

Compile matched artifacts, then exercise these consuming-app checks:

- Upgrade and reopen databases from 0.11.0, including one with pending and failed
  attachments. Verify the 0.11.0 binary refuses the upgraded database.
- Custom emoji: a peer's tagged chat renders the inline image, a `:shortcode:`
  reaction resolves its image through `reactionMessageIdHex` and `listMedia`, an
  unmatched shortcode renders as text, and sending through `uploadMedia(send = false)`
  then `sendTaggedMedia` / `reactWithMedia` round-trips to a second device after the
  group advances an epoch.
- Attachments: an agent-sent file downloads on the recipient, a tap through
  `requestExplicitAttachment` during backoff does not reset the retry counter, a
  sent file reopens offline on the sender after restart, and a missing blob fails
  rather than spinning.
- Notifications: a muted chat stays silent for ordinary messages, delivers a
  direct mention with `isMention`, and suppresses a blocked sender's mention.
- Poll votes: paging across more than one page sums to the tally; a blocked voter
  is listed and marked.
- App components: absent versus empty state, a non-admin update failure, an id
  below `0xf000` failing with `InvalidAppComponent`, and a newly invited member
  reading the current value.
- Inbox relays: a generated identity with a distinct inbox list publishes kind
  10050 with that list and kind 10002 with `defaultRelays`.
- WN Agent: `group_profile_update` as admin and after admin removal, a partial
  `account_publish_profile` that preserves avatar and about text, and inbound and
  outbound files through Codex, OpenCode and Pi.
- Android 16 KB page-size validation in the consuming app bundle; Apple
  privacy-resource delivery; C deep-free paths for the changed records.

Source tests, generated binding checks and packaged artifact validation are
separate from consuming-app archives, real-device measurements, live connector
deployment and store acceptance. This guide claims none of those later stages.
The publishing latency figure in the release notes comes from a matched
release-build comparison against the operated relays, not from device
measurements.

Known limitations:

- [#2086](https://github.com/marmot-protocol/mdk/issues/2086): during a large
  catch-up, a member can advance more than five epochs past application messages
  it has not downloaded yet. Those messages cannot be decrypted and raise no
  notice. This release fixes the attachment-key variant only.
- `HistoryNoticeCauseFfi::KnownEvent` still has no production producer
  ([#2082](https://github.com/marmot-protocol/mdk/issues/2082)), and the drain-era
  `FullHistoryRepairIncompleteReason` variants remain
  ([#2083](https://github.com/marmot-protocol/mdk/issues/2083)).
- Apple required-reason and SDK-signing work remains tracked in
  [#1874](https://github.com/marmot-protocol/mdk/issues/1874).
