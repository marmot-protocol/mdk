# Upgrading MDK 0.10.3 → 0.10.4

## Scope and provenance

This guide compares `v0.10.3` / `marmotkit-v0.10.3` at
`7d8bba365def75a66774f2b2036f839411010001` with the source to be shipped as
`v0.10.4`. All four 0.10.4 cohort tags must peel to the release PR's merged
commit, and packaged manifests must record that exact SHA. The behavior comparison
was prepared against `origin/master` at
`8702f634ddd2d748e46cb6370c06d1834317a34b`; use the full release SHA from the
tags for artifact verification. This guide ships in the release commit, not a
later supplement. See the [release notes](../release/0.10.4.md),
[previous upgrade guide](0.10.3.md), and
[current binding reference](../../crates/marmot-uniffi/README.md).

## Upgrade decisions

| Category | Required action or effect |
| --- | --- |
| Required | Replace generated Swift/Kotlin, native libraries and C headers together; rebuild consumers and update changed record/enum/error handling. |
| Required storage | Back up, then allow migrations 87–89 to complete. Downgrade across them is unsupported. |
| Optional host policy | Select `HostManaged` attachment acquisition before startup only when the host will own network/type permission and automatic demand. The default remains `NativeAutomatic`. |
| Optional composer adoption | Use token-aware send APIs for immediate durable acceptance and exact optimistic-row correlation. Existing send APIs remain supported. |
| Required preview behavior | If displaying disappearing-message chat previews, hide content at `retention_expires_at`; time alone emits no list update. |
| Optional agent behavior | Adopt `group_create` in control-protocol v2 and opt into Hermes approval reactions if desired. Both require explicit host integration. |
| Automatic fixes | Deferred pre-peel wrappers stay redeliverable; overflow retry pacing, pending-row visibility and draft-save cost improve without new calls. |
| Packaging only | MarmotKit build parallelism and provenance agreement checks preserve artifact names, layouts, deployment targets and privacy-resource requirements. |

## Required upgrade steps

1. Pin all MDK, MarmotKit, Marmot C and WN Agent inputs to 0.10.4. Verify
   the source SHA in each manifest and every sibling checksum. Do not combine new
   generated records or headers with 0.10.3 native libraries.
2. Rebuild Swift/Kotlin clients after updating exhaustive handling for the three
   new terminal attachment states: `PreviouslyAcquiredUnavailable`,
   `CompletedUnretained` and `RetryExhausted`. Handle the new
   `AttachmentModeRequired` and `AttachmentAccountSignedOut` errors. Full Rust
   `MarmotAppConfig` literals must set `attachment_acquisition_mode` or use
   `Default`; native `MarmotOptions` adds an optional mode.
3. Recompile C consumers. `MarmotClientOptions`, `MarmotTimelineMessageRecord` and
   `MarmotChatListMessagePreview` changed layout; `MarmotStatus` appends values 93
   and 94. Use only the header shipped with the exact library.
4. Preserve the Swift wrapper's `PrivacyInfo.xcprivacy` resource and dependency
   from every app/extension. Update the binary ZIP, shared Swift file and privacy
   resource together. Android still requires `MarmotAndroid.initialize(context)`
   before creating `Marmot` and all required JNI ABIs must come from one cohort.
5. Back up each account database before first open. Migration 87 preserves existing
   acquisition jobs while adding history and zero-initialized opt-in budgets;
   migration 88 adds a blob-free draft attachment descriptor index; migration 89
   adds durable local submissions. Do not remove migration rows to roll back.
   Restore a pre-upgrade backup/export or re-upgrade. See the
   [storage-format contract](../marmot-architecture/storage-format-v2.md).

## Durable local sends and caller correlation

The new token-aware methods are `sendTextWithClientToken`,
`replyToMessageWithClientToken`, `sendMessageDraftWithClientToken`,
`uploadMediaWithClientToken` and `localSendStatus` in generated native bindings.
They are optional replacements for optimistic composer flows, not formal
deprecations of existing send methods.

Allocate one opaque 1–128 byte UTF-8 token for each logical submission and insert
the optimistic bubble before calling MDK. Acceptance means a SQLCipher transaction
recorded MDK ownership and the pending timeline row; it does not mean relay
publication, recipient delivery or successful remote MLS processing. Replace the
optimistic bubble only when the authoritative timeline row carries the exact same
`client_token`. Remote and older messages have no token.

Illustrative host flow (generated naming can vary by language toolchain):

```swift
let token = UUID().uuidString
insertOptimisticBubble(token: token, text: text)
let accepted = try await marmot.sendTextWithClientToken(
    accountRef: account, groupIdHex: group, text: text, clientToken: token)
// Reconcile when a timeline row echoes accepted.clientToken.
```

```kotlin
val token = UUID.randomUUID().toString()
insertOptimisticBubble(token, text)
val accepted = marmot.sendTextWithClientToken(account, group, text, token)
// Reconcile from the timeline row whose clientToken equals accepted.clientToken.
```

Repeating the same accepted token and request returns the original identity while
queued, engine-owned or completed. A rejected attempt, different request with the
same token, or local message-identity collision requires a new token. Do not retry
by content or timestamp. `localSendStatus` recovers queued, engine-owned, completed
or rejected state after an interrupted wait or restart. A completed send summary
can still report pending or completion-unknown transport disposition.

Admission is bounded to 256 queued submissions and 16 MiB retained request/payload
data per account. Once admission begins, cancelling the caller does not cancel the
owned task. Shutdown leaves undrained work for the next account worker. The media
variant uploads before admission; an interrupted upload is not restart-resumable or
an idempotent blob operation, so query the original token before uploading again.

C uses `marmot_send_text_with_client_token`,
`marmot_reply_to_message_with_client_token`,
`marmot_send_message_draft_with_client_token`,
`marmot_upload_media_with_client_token` and `marmot_local_send_status`.
Calls block until local acceptance (or upload then acceptance), so keep them off the
UI thread. Free roots with `marmot_local_send_acceptance_free`,
`marmot_media_upload_submission_free` and `marmot_local_send_status_free`.
The timeline-owned token is deep-freed with its row; never free it separately.
See the [complete local-send contract](../../crates/marmot-uniffi/LOCAL-SENDS.md).

## Host-managed automatic attachment acquisition

Existing clients require no change to preserve native automatic discovery. Select
`HostManaged` before runtime startup only when one host coordinator will translate
network and media preferences into MDK permission and demand. Host-managed mode
starts denied for every account on each runtime construction and after sign-out;
permissions and generations are runtime/account/store-scoped and must not persist.

For each ordered network or preference event:

1. Call `beginAttachmentPermissionUpdate(account)` to revoke the old permission
   and obtain a single-use generation.
2. Evaluate current host policy asynchronously, then call
   `setAttachmentAutomaticPermission(account, generation, permission)`. A false
   result means stale/consumed/wrong-runtime state; do not obtain a new generation
   inside the old callback to bypass it.
3. Call `requestAutomaticAttachment(account, group, target)` for eligible demand.
   Foreground views and restored workers can repeat this idempotently.

```swift
let generation = try await marmot.beginAttachmentPermissionUpdate(accountRef: account)
let permission = AttachmentAutomaticPermissionFfi(
    images: allowImages, videos: allowVideos, audio: allowAudio, files: allowFiles)
guard try await marmot.setAttachmentAutomaticPermission(
    accountRef: account, generation: generation, permission: permission) else { return }
_ = try await marmot.requestAutomaticAttachment(
    accountRef: account, groupIdHex: group, target: target)
```

```kotlin
val generation = marmot.beginAttachmentPermissionUpdate(account)
val applied = marmot.setAttachmentAutomaticPermission(
    account, generation, AttachmentAutomaticPermissionFfi(images, videos, audio, files))
if (applied) marmot.requestAutomaticAttachment(account, group, target)
```

The C equivalents are `marmot_begin_attachment_permission_update`,
`marmot_set_attachment_automatic_permission` and
`marmot_request_automatic_attachment`; borrowed inputs remain caller-owned and
returned roots use their documented free functions. These calls return the new
mode/signed-out status codes when the runtime configuration or account lifecycle is
wrong.

Opted-in automatic work is bounded to four acquisition attempts and 64 network
attempts per source/request cycle. Permission interruptions refund the interrupted
acquisition claim, not completed network attempts. A verified-body receipt can
finish local publication after network revocation; explicit cancel/remove, expiry
and source replacement still fence it. `PreviouslyAcquiredUnavailable`,
`CompletedUnretained` and `RetryExhausted` prevent silent automatic redownload
loops. Deliberate explicit Retry/download-again begins a new bounded cycle when
eligible. Historical acquisitions without durable records cannot be reconstructed.
See [attachment access and policy](../../crates/marmot-uniffi/ATTACHMENT-ACCESS.md).

## Disappearing-message chat previews

`ChatListMessagePreviewFfi` / `MarmotChatListMessagePreview` now include optional
`retention_seconds` and `retention_expires_at`. These are the pinned decision from
the selected source message, not a recalculation from current group policy. Unknown,
disabled, finite and overflow/unbounded decisions remain distinct.

When current Unix time reaches a finite expiry, hide the preview content even if
periodic pruning has not run. Re-evaluate on resume and schedule a visible-row timer;
time passing by itself does not emit a chat-list update. This release does not fall
back automatically to an older surviving message. Localize placeholders in the host
and do not log preview plaintext. See the
[chat-list row contract](../../crates/marmot-uniffi/CHAT-LIST-ROWS.md).

## WN Agent and Hermes integration

Control protocol v2 adds `group_create` with `account_id_hex`, `name`, `members`
and optional `description` / `relays`. Omitted relays preserve connector defaults;
explicit routes pass the normal public-host safety policy before group mutation.
The `group_created` response returns `group_id_hex`, `agent_created` and an optional
`pending_welcome_count`. Creation is non-idempotent: failure to read the best-effort
pending-Welcome count must not trigger another create, and zero does not mean invitees
accepted. Group info now reports creator provenance for activation only; it grants no
sender or approval authorization.

Hermes can set `platforms.marmot.extra.approval_reactions: true`. Authorized
`MARMOT_ALLOWED_USERS` senders may use 👍 once, 👎 deny or ❤️ permanent approval
when the request permits it. `MARMOT_ALLOW_ALL_USERS` does not grant approval
authority, self-reactions are ignored and the default remains off. This integration
is tested against the Hermes 0.19.0 revision pinned by `hermes-agent.lock`; changing
the host pin requires compatibility validation.

## Changes requiring no new calls

- A wrapper parked by the ingest halt gate before MLS peel is no longer marked
  processed merely because ingest returned `Buffered`; redelivery remains possible.
- Repeated epoch-backfill overflow uses execution-ordinal exponential backoff rather
  than repeatedly using the 15-second base delay. Queue capacity, durable markers
  and cursor completion rules are unchanged. Recovery remains non-resumable and is
  not claimed end-to-end lossless.
- Conversation windows can present a coherent locally accepted pending row before
  relay publication finishes. Revisioned draft saves no longer hydrate an unused
  copy of attachment plaintext and use migration 88's descriptor index.
- MarmotKit workflow parallelism changes build scheduling and provenance transfer,
  not SDK APIs, artifact layouts, deployment targets or privacy packaging.

## Acceptance and remaining work

Compile matched artifacts, then exercise these consuming-app checks:

- Upgrade/reopen databases with acquisition work, large attachment drafts and
  pending local submissions; verify restart recovery and prior-binary downgrade
  refusal before application-table access.
- Token send/reply/draft/media acceptance, same-token interruption/retry, rejected
  token replacement, process restart, group/source deletion and optimistic-row
  reconciliation without content/timestamp matching.
- Host-managed cold start and sign-out/sign-in, ordered network changes, stale
  generations, category denial, permission flaps during transfer, budget exhaustion,
  explicit retry/remove/download-again and verified receipt during revocation.
- Native-automatic regression with no host-managed calls, including existing queued
  work and explicit downloads.
- Finite, disabled, unknown and overflow/unbounded preview retention; background/
  resume and visible-row expiry without a list update.
- WN Agent group creation with omitted/explicit safe relays, invalid members, pending
  Welcomes and unknown response outcome without blind retry. Test Hermes reactions
  disabled, unauthorized, expired/parallel and permanent-restriction cases.
- Swift/Kotlin cancellation and screen lifetime, C deep-free/blocking-call paths,
  Apple privacy-resource delivery, representative device storage and memory loads.

Source tests, generated binding checks and packaged artifact validation are separate
from consuming-app archives, real-device measurements, live connector deployment and
store acceptance. This guide claims none of those later stages. Existing Apple
required-reason and SDK-signing work remains tracked in
[#1874](https://github.com/marmot-protocol/mdk/issues/1874); broader resumable overflow
recovery remains outside this release.
