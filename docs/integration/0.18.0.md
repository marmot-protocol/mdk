# Upgrading MDK 0.17.0 → 0.18.0

## Scope and provenance

This guide compares `v0.17.0` / `marmotkit-v0.17.0` / `marmotc-v0.17.0` /
`wn-agent-v0.17.0`, which all peel to
`4df811aea99269b437a6023be9446a5141e93cbe`, with the source to be shipped as
`v0.18.0`. All four 0.18.0 cohort tags must peel to the release PR's merged
commit, and packaged manifests must record that exact SHA. The comparison was
prepared against `origin/master` at
`470d4b4d53e5b29b59b7df75595fbcacc52a9725` (76 commits after `v0.17.0`, the
last being [#3568](https://github.com/marmot-protocol/mdk/pull/3568)); the
release commit is this documentation update's merge on top of it. Use the full release SHA from the tags for artifact
verification. This guide ships in the release commit, not a later supplement.
See the [release notes](../release/0.18.0.md), [previous upgrade guide](0.17.0.md),
and [current binding reference](../../crates/marmot-uniffi/README.md).

Readers: native app hosts (Swift/Kotlin through MarmotKit), C hosts, Rust hosts
that embed `marmot-app` or lower crates, and WN Agent operators.

The largest client change is that multi-device is built into every artifact
and on in every constructor. Until 0.17.0 it existed only in
`dev-device-groups` test builds. `MarmotKitError` gains three cases
(`GroupCommitPending`, `NoUsableRelay`, `ReactionNotFound`), C gains three
statuses (`131`–`133`), `GroupEventKindFfi` gains `GroupChangeNotDelivered`,
and no `MarmotEventFfi` case is added. Account databases migrate from schema
207 to 216, the shared database from 4 to 5, and each account's directory
cache from 2 to 3. Conformance vectors are
unchanged apart from their version stamp; the sibling Welcome gains a
version 3 (see [Device groups on by default](#device-groups-on-by-default)).

| Category | Required action or effect |
| --- | --- |

Pass the new fields where you construct changed records. |

## Required upgrade steps

1. Pin all MDK, MarmotKit, Marmot C and WN Agent inputs to 0.18.0. Verify the
   source SHA in each manifest and every sibling checksum. Do not combine new
   generated records or headers with 0.17.0 native libraries. See the
   [distribution guide](../../crates/marmot-uniffi/DISTRIBUTION.md).
2. Ship the 0.18.0 library in **every** process that opens the root, including
   a notification service extension or background worker. Once 0.18.0 has
   opened an account, a 0.17.0 process cannot open its database at all: it
   refuses the newer schema (`UnsupportedSchemaVersion`), even for an account
   with a single device. Separately, a runtime with device groups off fails a
   compatible account that holds or is joining a device group with
   `MarmotKitError.Runtime` `experimental_device_groups_required`. See
   [Storage upgrade](#storage-upgrade) and
   [Device groups on by default](#device-groups-on-by-default).
3. Add the new error cases to exhaustive error handling:

   | Case | Meaning | Host action |
   | --- | --- | --- |
   | `GroupCommitPending(groupIdHex:)` | The group's own last commit has not confirmed. Group changes, a member's leave and an invite decline fail with it; disbanding and an admin's leave are accepted. Messages are accepted but wait in the queue until the commit resolves, and a send of media encrypted before the commit can fail with `MediaReferenceEpochUnsettled` or, once the epoch moves, `MediaReferenceStaleEpoch`. | Say the previous change is still being sent; retry once it confirms. Show queued messages as pending, not sent, and upload media again after `MediaReferenceStaleEpoch`. Read `groupPendingCommit` to show it. |
   | `NoUsableRelay` | MDK may send to none of the group's relays (for example, all at private-network addresses). Nothing was sent and a commit rolled back. It was `Publish` before. | Do not offer a retry: it fails the same way while the group's relays stay the same. |
   | `ReactionNotFound` | A reaction removal found no matching active reaction locally; nothing was published. | Refresh state; do not treat it as proof other devices converged. |

   `GroupCommitPending` is checked before `GroupCatchingUp` and
   `GroupCommitUndelivered`, and no acknowledgement releases it, so those
   acknowledgements stay unspent.
4. Handle `GroupEventKindFfi.GroupChangeNotDelivered { commitIdHex, intentKind,
   reason }` and `OnboardingActionFfi.RemoveUnusableRelays` in exhaustive
   `switch`/`when`. See [Group changes that confirm, stick or are given
   up](#group-changes-that-confirm-stick-or-are-given-up) and
   [Onboarding](#onboarding).
5. Pass the new fields where you construct these records yourself (tests and
   previews, typically). Fields with a default compile without change in
   Swift and Kotlin; the others must be passed:

   | Record | New field |
   | --- | --- |
   | `AppMessageRecordFfi` | `invalidated: Bool` (no default; true for a raw row kept only as an invalidated tombstone) |
   | `DeviceLinkSnapshotFfi` | `chatProgress: [LinkChatProgressFfi]` (default empty) |
   | `OnboardingDevicePackageFfi` | `client: String?` (no default) |
   | `OnboardingRelayTagChangeFfi` | `removalReason: OnboardingRelayRemovalReasonFfi` (no default; `.none` for an entry not removed) |
   | `OnboardingRepairProposalFfi` | `inconclusive: Bool` (default `false`) |
   | `SelectedMessageDraftAttachmentFfi` | `fileBacked: Bool` (default `false`) |
   | `AttachmentStorageUsageFfi` | `draftBytes: UInt64` (default `0`) |

6. Remove any `--dev-device-groups` flag from local build scripts and any
   reference to `output-dev-device-groups/`. `xcframework.sh`,
   `xcframework-macos.sh`, `kotlin-bindings.sh`, `options-smoke.sh` and
   `c-bindings.sh` build the one library every constructor uses.
7. Expect usage-diagnostics consent to need acceptance again. The registry
   adds the `mdk_onboarding_summary` aggregate, so its revision changes and a
   granted receipt from 0.17.0 no longer covers it. Hosts need no new calls.
   See [Usage diagnostics: onboarding pauses](#usage-diagnostics-onboarding-pauses).
8. If you export v5 audit records, repin and deploy the White Noise audit
   receiver before shipping, so it accepts the new kinds
   (`welcome_event_size`, `welcome_withdrawn`, `pending_commit_changed`). An
   older receiver rejects a whole batch that contains an unknown kind; MDK
   then splits and retries the batch and skips the rejected rows, so other
   rows can arrive late. See the
   [receiver contract](../marmot-architecture/audit-logging.md#downstream-whitenoise-data).

## Storage upgrade

Account databases run nine migrations on first open, moving from schema 207
to 216:

| Migration | Change |
| --- | --- |
| 0208 | Repairs retained NIP-22 comment parents, media and accepted author edits, and backfills attachment slots, encrypted-media source-epoch references and cached-secret retention for them. Raw events, deleted tombstones and unrelated custom rows are kept. |
| 0209 | Lets a draft attachment own a staged media file instead of holding bytes. |
| 0210 | Adds `cgka_changes_not_delivered`, the group changes given up after their call returned, kept until acknowledged. |
| 0211 | Adds `account_sign_in_removals`, the slots the trusted device roster recorded as removed. |
| 0212 | Adds the bounded attachment body-removal journal. |
| 0213 | Persists the end of each epoch-gap visit. |
| 0214 | Persists link chat progress across restarts. |
| 0215 | Adds `stall_evidence` to released transport receipts. |
| 0216 | Changes no table; gates the new stored Welcome payload tags 14 and 15 so an older binary refuses the database. |

The shared database (`shared.sqlite3`) runs migration 0005, moving from schema
4 to 5: per-slot publication journals and barrier state for direct-follow
availability, bounded to 500 slots per account and 1,000 rows in all, holding
event ids and timestamps, never KeyPackage bytes.

Each account's directory cache runs its migration 0003, moving from 2 to 3: a
table for the direct-follow availability projection. A new account database
also records, in an unnumbered `cgka_database_origin` row, that it was created
empty, so an early read no longer makes a fresh account look upgraded.

None of these rewrites message history; 0208 repairs only NIP-22 comment
projections. A 0.17.0 binary refuses either upgraded database before reading
or writing its tables.

Downgrade to 0.17.0 is unsupported. If you may need to roll back, keep a
device-local copy of the MDK data directory taken before upgrading while the
app and every extension (such as a notification extension) are stopped, so no
database or its WAL file is open while it is copied. Leave out
`accounts/*/handoff/`: it holds plaintext attachment copies lent to the OS,
which the backup would keep after their leases end, and a rollback does not
need them. Never remove migration rows by hand. See the
[storage-format contract](../marmot-architecture/storage-format-v2.md).

## Device groups on by default

Every MarmotKit, Marmot C, `wn` and WN Agent build now includes multi-device,
and every constructor opens with device groups on:

- `newWithConfiguration` (C `marmot_client_new_with_configuration`) links
  devices, lists linked devices, reviews sign-ins, transfers history, runs
  backups, and steps a nonlast admin down on Leave.
  `requiresSelfDemoteBeforeLeave` is false for a nonlast admin, and
  `canLeave` includes that Leave. The last active admin is still refused.
- `newWithExperimentalDeviceGroups` (C
  `marmot_client_new_with_experimental_device_groups`) is now the same open,
  kept so existing hosts compile, and no longer fails with
  `experimental_device_groups_unavailable`. New code can use
  `newWithConfiguration`.
- There is no binding switch to turn device groups off. Rust hosts can set
  `MarmotAppConfig::with_device_groups(false)` in every opener of a root; the
  CLI honors `WN_DEVICE_GROUPS=0` for both `wn` and `wnd`.

What a host should do:

- Offer device linking and the linked-device screens described in
  [Linking a new device](../../crates/marmot-uniffi/README.md#linking-a-new-device),
  [Linked devices](../../crates/marmot-uniffi/README.md#linked-devices) and
  [Unrecognized sign-ins](../../crates/marmot-uniffi/README.md#unrecognized-sign-ins),
  or at least handle their events (`DeviceLinkChanged` and the sign-in
  notices) without crashing.
- Re-read `groupManagement` for Leave instead of assuming an admin must
  demote first.
- During linking, read `DeviceLinkSnapshotFfi.chatProgress`. Each
  `LinkChatProgressFfi { slotIdHex, onNewDevice, total, remaining }` names the
  new device by slot. On the approver `remaining` counts chats still owed an
  Add; on the new device it counts expected chats not yet joined. Show a
  joining banner while it is positive. An absent entry means progress is
  unavailable (before a complete report, with older peers, after opt-out, or
  once the direct-add window expires).

Mixed versions: a sibling Welcome that forwards how the adding device holds a
chat (its inviter, and whether a copy with no invitation generation is
confirmed) is encoded as version 3, which devices older than 0.18.0 refuse.
0.17.0 production artifacts had no device groups, so this matters only for
devices that ran `dev-device-groups` builds: update every device of an
account together before linking. Every build supports the device-roster
component (`marmot.account.device-roster.v1`), and a runtime with device
groups on, the default, advertises it in its capabilities.

How linked devices now behave:

- A newly linked device gets each chat as the device that adds it holds it. A
  chat confirmed there from before invitation generations arrives confirmed
  instead of as an invitation from the account itself. One with an
  invitation generation settles through its shared decision and can show as
  pending until that decision arrives, and a chat whose inviter this device
  blocks stays pending
  ([#3556](https://github.com/marmot-protocol/mdk/issues/3556)). An
  unanswered invitation arrives pending with the original inviter as
  `welcomerAccountIdHex`.
- When a device is linked to an account that already has two or more devices,
  the approver adds it to the chats the approver is in while the approver is
  active (heard from within two hours) and the link is under a week old. The
  other devices gap-fill only once the approver goes quiet, so they no longer
  both add it and fork chats. A sibling running an older version still
  gap-fills at once.
- An invitation answered on one linked device shows as answered on the other
  within seconds. The answer is sent on the worker's next turn, a sibling's
  winning answer is applied when it arrives, and the chat then reports
  `GroupStateUpdated`, as a host accept does.
- A device the user linked and then removed no longer comes back as a new
  sign-in once its `removed` roster record expires. A later publication in
  that slot is still a new sign-in.
- History recovery no longer stalls a newly linked device on traffic that may
  predate its Welcome.

## Group changes that confirm, stick or are given up

0.17.0 retried a group change whose relay answer was unclear until it either
confirmed or exhausted its retries, and a change could stay pending
indefinitely. 0.18.0 resolves it
([#2332](https://github.com/marmot-protocol/mdk/issues/2332)):

- **Confirmed by echo.** When the account's own group subscription receives
  that exact change from one of the group's relays, it confirms. A copy under
  another event id, or from a relay outside the group's list, confirms
  nothing.
- **Confirmed by read-back.** Ten minutes after the first send, each retry of
  a relay that may hold the change first reads that exact change back. The
  read never signs in as the account, sends one request per relay, at most
  eight per account per relay an hour, and feeds nothing into message handling.
- **Given up.** A change no relay accepted and none may hold, with relays still
  unreached, rolls back ten minutes after its first send once the device shows
  it is online. A change any relay may hold never rolls back, and an offline
  device keeps the change pending.
- **Prepared once.** A queued message or change names its stored send, so a
  retry or restart no longer prepares it a second time as a new message with
  a new identity. The same event can still be republished to relays while its
  send resolves; that is one logical delivery. A send stored by 0.17.0 can
  still be prepared once more after a restart.

While the group's own commit is pending, group changes fail with
`GroupCommitPending`. To show the user what is happening:

- `groupPendingCommit(accountRef, groupIdHex)` returns `GroupPendingCommitFfi?`
  with `state` `Sending` (its first ten minutes, and while no relay may hold
  it) or `Stuck` (ten minutes on, some relay may hold it, none acknowledged).
  It names the change by `intentKind`, plus `queuedIntentIdHex` for a queued
  one, gives `firstAttemptAt`, and lists `unconfirmedRelayUrls`,
  `owedRelayUrls` and `refusedRelays`. MDK never gives up a stuck commit. No
  event announces a confirmation, so poll while showing it. It is a local
  read with no network I/O.
- `groupChangesNotDelivered(accountRef, groupIdHex)` returns
  `GroupChangeNotDeliveredFfi` records, oldest first, for changes given up
  after their call returned: a direct change that answered
  `CompletionUnknown`, or a queued one that answered `AcceptedPending`.
  `reason` is `not_delivered`, `event_too_large` or `refused`. A direct change
  is also announced by `GroupEventKindFfi.GroupChangeNotDelivered`; a queued
  one by `QueuedIntentRefused`, as before. Read the records on start: the
  events only notify. Clear one with
  `acknowledgeChangeNotDelivered(accountRef, groupIdHex, commitIdHex)`. A
  change staged by 0.17.0 and given up after the upgrade is not recorded.

```swift
// Illustrative.
if let pending = try await kit.groupPendingCommit(accountRef: account, groupIdHex: group),
   pending.state == .stuck {
    showStuckChange(kind: pending.intentKind, relays: pending.unconfirmedRelayUrls)
}
for record in try await kit.groupChangesNotDelivered(accountRef: account, groupIdHex: group) {
    showChangeNotApplied(kind: record.intentKind, reason: record.reason, at: record.at)
}
```

```kotlin
// Illustrative.
marmot.groupPendingCommit(account, group)?.takeIf { it.state == GroupPendingCommitStateFfi.STUCK }
    ?.let { showStuckChange(it.intentKind, it.unconfirmedRelayUrls) }
marmot.groupChangesNotDelivered(account, group).forEach {
    showChangeNotApplied(it.intentKind, it.reason, it.at)
}
```

See [A group change still being sent](../../crates/marmot-uniffi/README.md#a-group-change-still-being-sent)
and [Group changes that were not applied](../../crates/marmot-uniffi/README.md#group-changes-that-were-not-applied).

## Changed defaults

### Maintenance timing

The 15-second maintenance tick no longer drives an idle account. Session
maintenance runs at the earliest time its data gives (rotation, leaf refresh,
self-update phase, KeyPackage refresh, expiry or relay backoff, a fanout's
backoff, a private KeyPackage expiry, a reinvite retry, or the 10-minute
component recheck). Device-group passes run at their own times: the sign-in
check, and once linked the hourly heartbeat, the small-state broadcast,
private KeyPackage request pacing, a leaving sibling's decision, gap filling
and inventory pages. Device pairing runs only while linking is under way.
Recovery, post-join work, attachments, avatars, presentation, local-submission
retries, push windows, history dispatch and the compaction batch each run when
an event wakes them and at their own deadlines. Work with no stored time
retries 15 s after the last run while it lasts.

Effects a host can see: an idle device uses less CPU and no longer writes the
database on each tick; a push token change goes out at once as a plain
`PushTokenUpdate`, followed by the announce it owes once the push fetch clock
settles (two group messages per group instead of one); KeyPackage publication
retries follow their stored backoff (30 s doubling to 1 h). Times a week or
more out (history expiry, inactivity, takeover) ride the run the hourly
heartbeat brings, so they can be up to an hour late. Nothing changes in the
API.

### Relays MDK may not send to

A group send none of whose relays MDK may send to fails as `NoUsableRelay`
instead of `Publish`. A relay the host-safety rule refuses no longer counts as
one a send may have reached: a Welcome whose inbox relays it refuses no longer
counts toward maintenance's ambiguous-exposure total, and a commit or message
every other group relay refused for size fails as `EventTooLarge`.

### Sticker and emoji relays

Sticker pack reads (`syncStickerPacks`, `fetchStickerPack`,
`installStickerPack`, resolving a received sticker) and emoji set reads
(`syncEmojiSets`, `fetchEmojiSet`, the sets `userEmojiList` points to) query
the runtime's configured relays as well as the account's NIP-65 relays. The
newest version among the relays that answered wins. The installed lists
(kinds 10031 and 10030) are still read from and published to the account's
relays only. A pack's share link names only relays that served the version MDK
kept.

### Onboarding

- A relay that closes a query with `ERROR: auth-required: ...` is reported as
  needing authentication, and an account that can sign authenticates and asks
  again. After connecting (up to 5 s), a check waits up to 8 s for a relay to
  finish answering, not 3 s, so one relay's inspection can take 13 s; the
  step cancels a relay's check at 15 s. Relays are checked concurrently. Do
  not put a shorter watchdog or "timed out" copy in front of that window.
- A `RetryableFailure` relay or inbox step whose check was inconclusive also
  offers `EditRelays` and, where defaults can change the list,
  `UseRecommendedRelays`. `OnboardingRepairProposalFfi.inconclusive` marks a
  proposal built on such a check; show an explicit at-your-own-risk
  confirmation before approving it.
- A step offers `RemoveUnusableRelays` when
  `proposeOnboardingRelayRepair` would return an approvable preview that
  removes a declared relay: a retired relay, or one that refused the
  declared-route check with `auth-required` or `payment-required` while the
  client held the account's local key. Each `Removed`
  `OnboardingRelayTagChangeFfi` carries `removalReason` (`Retired`,
  `AuthenticationRequired`, `PaymentRequired`) for a localized explanation;
  every other entry carries `None`, which exhaustive switches must handle. C
  uses the non-pointer enum `MarmotOnboardingRelayRemovalReason`.
  It is advice: readiness never depends on it.
- `OnboardingDevicePackageFfi.client` names the app another installation's
  package reports. See
  [Onboarding: other-installation client labels](#onboarding-other-installation-client-labels).
- A single-device acknowledgment survives a pause of more than five minutes
  before Continue; the notice returns only when discovery finds something new.

See [Interactive account onboarding](../../crates/marmot-uniffi/README.md#interactive-account-onboarding).

### Usage diagnostics: onboarding pauses

Hosts make no new calls. MDK now records the `mdk_onboarding_summary` usage
diagnostics aggregate itself (#3440). It shows which interactive onboarding
step (profile, follows, relays, inbox relays, single device, KeyPackage) an
attempt stopped at and why. Each row has the blocking status, the primary and
per-source issue classes, the finding context and a bucketed count of failing
sources. It has no relay URL, account, event id or free text. Each attempt
counts a distinct step, status and issue once, across retries and restarts,
and only while usage-and-diagnostics consent is granted.

The product catalogue gains this family, so the registry revision changes.
After the upgrade, a user who had granted usage and diagnostics reads as
`AcceptanceRequired` until they accept again. Show the scope-change explanation
you already use when registered schemas change (see
[Usage and diagnostics](../marmot-architecture/usage-diagnostics.md#consent-and-host-integration)),
not the one-time legacy explanation. Keep recording `mdk_onboarding_step` as
before: the new rows explain a pause, and the host's step events still mark
start and completion.

### Onboarding: other-installation client labels

Someone importing an existing key almost always has KeyPackages that their previous
app published, so the `SingleDevice` notice reports `OtherInstallationPossible` for
nearly everyone moving between apps. The generic "Other sign-in records were found"
copy can read as a reason to stop. Each `single_device_notice.other_packages` entry
now carries an optional `client` string (#3438): `OnboardingDevicePackage::client` in
Rust, `OnboardingDevicePackageFfi.client` in Swift/Kotlin and
`MarmotOnboardingDevicePackage.client` in C. It comes from the record's NIP-89
`client` tag. Hosts can use it to name the likely source, for example "We found
messaging keys from Example Chat".

- **Required.** Replace generated Swift/Kotlin, native libraries and C headers
  together. Code that constructs `OnboardingDevicePackageFfi` directly (previews,
  fakes) must pass `client`. C hosts must recompile: `MarmotOnboardingDevicePackage`
  gains a trailing `client` pointer, which `marmot_onboarding_snapshot_free` releases
  with the rest of the snapshot.
- **Untrusted.** The label is whatever the record's signer wrote. Present it as what
  the records report, render it as plain text (never markup or a link), and never base
  trust, identity, deduplication or security decisions on it. Keep it out of logs,
  telemetry and analytics.
- **Sanitized by MDK.** Only the first value of the first `client` tag is read, never
  the handler address or relay hint after it. Control, bidirectional and invisible
  formatting characters are removed, whitespace runs collapse to one space, and the
  label keeps at most 64 whole grapheme clusters and 1024 bytes. A missing tag or a
  label with nothing visible left is `None` (C: `NULL`). C strings never contain an
  embedded NUL.
- **Optional and backward compatible.** Several entries can share a label, and entries
  without one still need the existing generic wording. Checkpoints saved by 0.17.0
  load unchanged and report `None` until `SingleDevice` is checked again. Discovery,
  consent and the step's actions are unchanged; no network work is added.

```swift
// Illustrative.
let names = Set(notice.otherPackages.compactMap(\.client)).sorted()
let source = names.isEmpty
    ? "another app"
    : ListFormatter.localizedString(byJoining: names)
```

The [binding reference](../../crates/marmot-uniffi/README.md#single-device-notice) has the
notice copy and discovery limits.

## Feature adoption

### Direct-follow availability (optional)

`followAvailabilityPage(accountRef, after, limit)` reads the selected
account's direct follows from its encrypted cache without networking; pass
`nextCursor` as `after`, and `limit` clamps to 1–100. Each row is `ready` (MDK
selected a current compatible KeyPackage), `unknown`, or `notFound` (for 15
minutes after a completed miss), with check time, expiry and provenance. It
never says which client an account installed. `refreshFollowAvailability`
checks at most 100 follows (four at a time, 10 s per target, five minutes in
all), committing per target so pages show partial progress; concurrent calls
share one refresh, and completed refreshes have a 60-second cadence. Poll
`followAvailabilityStatus` and cancel with
`cancelFollowAvailability(accountRef, operationId)`, using the same account;
a stale id returns false. Keep the synchronous page read off the UI thread.
See [Direct-follow availability](../../crates/marmot-uniffi/README.md#direct-follow-availability).

### File-backed draft attachments (optional)

`stageMessageDraftAttachmentFile(accountRef, revision, request, control)`
copies a host file, up to the encrypted-media blob limit, into the account's
encrypted media store and adds it to the draft, so no full-size buffer crosses
the binding. The draft owns the copy across text-only saves and restarts;
clearing or sending the draft releases it. Staging returns the selected
draft: use its revision from then on, because the revision you staged with
is stale once the copy lands. Then:

- Keep such attachments through edits with
  `saveMessageDraftInputsIfRevision`, passing
  `MessageDraftAttachmentInputFfi.retained(id:)` for each one to keep and
  `.inline(attachment:)` for in-memory ones. A save deletes every attachment
  its inputs omit, including its staged file.
- Read previews with `readMessageDraftAttachment` (1 MiB chunks; `nil` means
  no such attachment, an empty chunk the end) or hand a file to the OS with
  `openMessageDraftAttachmentHandoff`. The handoff is a plaintext copy under a
  lease that outlives draft edits, clears and sends: call
  `releaseAttachmentHandoff` once the OS consumer has finished with it.
- Upload with `uploadMessageDraftAttachments`, then pass its references, in
  the draft's attachment order and with that same revision, to
  `sendMessageDraft`.
- `SelectedMessageDraftAttachmentFfi.fileBacked` marks them, and storage usage
  reports staged bytes as `draftBytes`. `messageDraftAttachmentIfRevision`
  refuses a file-backed attachment (it still reads inline ones), and the
  legacy whole-draft read refuses a draft that holds one.

`sendMessageDraft` and captured-media admission now match prepared media to
the draft after an upload's normalization (a V1 upload trims the file name;
both versions canonicalize the media type), so `" clip.mp4 "` or `Video/MP4`
no longer fail to match. See
[Conversation windows](../../crates/marmot-uniffi/CONVERSATION-WINDOW.md#file-backed-attachments).

### Emoji-scoped reaction removal (optional)

`unreactFromMessageMatching(accountRef, groupIdHex, targetMessageId, emoji)`
removes the account's active reactions with that exact emoji and keeps its
others. Both removal calls return `ReactionNotFound` for a local no-match.
Target-wide `unreactFromMessage` is unchanged.

### Direct chats with a disappearing-message duration (optional)

`startDirectConversationWithOptions(accountRef, peerAccountId,
DirectConversationOptionsFfi(disappearingMessageSecs:))` founds a new direct
chat with that duration in its founding MLS state and Welcome; zero disables
it. A nonzero duration requires the peer to support message retention, as
`createGroupWithOptions` does; otherwise the call fails and creates no chat,
so explain that the peer cannot keep disappearing messages and create the
chat with `startDirectConversation` only after the user agrees to go without
them. Reuse and retry
keep the existing chat's duration and roles.
`startDirectConversation` is unchanged.

### Attachment removal cursors (optional)

`attachmentRemovals(accountRef, cursor, limit)` returns
`AttachmentBodyRemovalPageFfi`: ordered, durable removal identities for host
derivative caches (thumbnails, decoded copies). Persist the returned cursor
after evicting. A first-use, reset or trimmed cursor asks for a full cache
reconciliation against the captured high-water mark. Pages hold up to 256
records and the journal 4,096. A removal never authorizes a byte read.

### Raw messages: invalidated tombstones

`messages` returns raw rows retained after invalidation, including kind-7
reactions and kind-1111 comments. Those rows now carry `invalidated` in
`AppMessageRecordFfi` and `MarmotAppMessageRecord` (#3411). The flag is true
for a row kept only as a tombstone and false for a live row.

- **Required.** Replace generated Swift/Kotlin bindings, native libraries and
  `marmot.h` together. Code that constructs `AppMessageRecordFfi` directly must
  pass `invalidated`.
- **Required for C.** Recompile against the matching header and library.
  `MarmotAppMessageRecord` gains a trailing `bool`, which changes the record
  size and the item stride in `MarmotAppMessageRecordList`.
- **Required for raw reactions and comments.** Check `invalidated` before
  treating a row as live. Hide the tombstone or render its invalidated state;
  do not render its reaction emoji or comment as live content.

Validate the binding with one live row and one invalidated row in the same
`messages` result. Their flags must be false and true respectively.

## WN Agent and integrations

the runtime's default configuration, so they now run with device groups on:

## Changes requiring no new calls

- History recovery continues across partial MLS epoch advances: retained
  unreadable messages can arm the next recovery request after local replay
  settles, without reopening the account or waiting for fresh traffic.
- Queued detached Welcomes no longer start relay publication after their
  native origin loses.
- Retrying an emoji-set install no longer deletes emoji the user already has;
  `skipped` names only entries left without an image. Emoji discovery applies
  its 60-set limit after deduplicating.
- NIP-22 comments (kind 1111 with a numeric lowercase `k` tag) project their
  parent, media and author-only edits, and their media keys are cached and
  carried in history bundles, so comment media stays decryptable after the
  epoch advances and on devices that import history
  ([#3410](https://github.com/marmot-protocol/mdk/issues/3410)).
- The compaction batch retries 15 s after the account's storage fails to open.
- Runtime shutdown gives Welcome waves still publishing up to 2 s before it
  cancels them, so a Welcome a create or invite just started usually goes out
  before exit. A relay can outlast that bound, and `shutdownAndClose` closes
  storage first, so a send can finish without being recorded; a Welcome still
  owed is sent on the next start, possibly again.
- Destructive sign-out reports a member Leave it could only queue in its leave
  failures instead of counting the group as left.
- A fresh account no longer fails KeyPackage rotation ("legacy key package
  replacement is pending") or reports `RecoveryRequired` because an early read
  created its database.
- A newly linked device no longer reads pre-join history as an epoch gap,
  which offered a needless Reset Device List and held its chats back.
- A refused Welcome delivery no longer drops a later delivery of the same
  Welcome as a duplicate.
- Background history drains without a live tail end instead of polling slow
  relays continuously, and `RecoveryStatusChanged` fires per route, not per
  relay.
- History notices, recovery status and the prepared-image, fresh-start and
  history-import reads answer from the published read state, and no read
  answers earlier than the worker would.
- With device groups on, an idle maintenance tick takes no writer
  transaction.

## Acceptance and remaining work

Before shipping an app on 0.18.0:

- Compile against the matched artifacts with every exhaustive `switch`/`when`
  updated; for C, rebuild every consumer and check the new free paths.
- Ship the same library in the app and every extension; confirm an extension
  delivers notifications for an account that has linked a device.
- Upgrade a 0.17.0 install in place and confirm both databases migrate once
  and the second open changes nothing. Confirm 0.17.0 refuses to reopen them,
  and that restoring the pre-upgrade copy works.
- Link a second and a third device: confirm emoji comparison, chat progress,
  with an inviter neither device blocks, that a confirmed chat without an
  invitation generation arrives confirmed at
  once and one with a generation turns confirmed when its shared decision
  arrives, that an invitation answered on one
  device shows on the other within seconds, and that removing a device keeps
  it out of sign-ins.
- As a nonlast admin, leave a group and confirm the step-down happens without
  a separate demote.
- Give up: make a group change with one group relay unreachable throughout
  and another refusing it. After ten minutes, once the reachable relay has
  refused a later send or answered the read-back without the event, confirm
  a `groupChangesNotDelivered` record and `GroupCommitPending` until then. A
  device whose relays are all unreachable keeps the change pending.
- Stuck: make a group change that a relay accepts without answering `OK`,
  with the account's subscription echo of it suppressed and the relay's
  read-back answering without it. Confirm `groupPendingCommit` reaches
  `Stuck` after ten minutes and the change is never given up.
- Leave an account idle and confirm it no longer wakes every 15 s (CPU and
  database writes).
- If adopted: page and refresh follow availability and cancel a refresh;
  stage a large video in a draft, restart, and send it; remove one emoji
  reaction of several; start a direct chat with a disappearing-message
  duration, and confirm a peer without message-retention support makes the
  call fail with no chat created.
- Report evidence by stage: source, host smoke, packaged artifact, consuming
  app, real device.

What was validated: every change in this comparison landed through the merge
queue's CI matrix, and the binding-docs gate passes for the MarmotKit method and
C symbol inventories at this source. Not validated here: upgrade of a real
0.17.0 installation, device linking between production iOS and Android
builds, and app-level adoption on iOS or Android.

Known limitations:

- A linked device can show an accepted chat as an invitation until its
  decision arrives ([#3556](https://github.com/marmot-protocol/mdk/issues/3556)),
  and a sibling Add whose Welcome goes out late can still forward "pending"
  for an invitation the user accepted on this device in between
  ([#3559](https://github.com/marmot-protocol/mdk/issues/3559)). An Add that
  would forward invitation facts is no longer queued.
- A message sent while a new device is joining a chat can be lost on that
  device ([#3537](https://github.com/marmot-protocol/mdk/issues/3537)), and
  the approver hold's hand-off edges remain
  ([#3561](https://github.com/marmot-protocol/mdk/issues/3561)).
- A sibling decline this device cannot apply as the chat's last admin waits
  for the next maintenance run, up to an hour.
- Startup hydration re-drives every outstanding fanout after each batch of
  four groups, delaying live transport on accounts with many groups
  ([#3367](https://github.com/marmot-protocol/mdk/issues/3367)).
- Pending Welcomes and some other reads still go through the worker queue
  ([#3273](https://github.com/marmot-protocol/mdk/issues/3273)).
- Still open from earlier releases: right after a reconnect a new send can
  still go out ahead of older unsent ones; the automatic-rejoin handshake's
  inner event kind is under discussion
  ([marmot#451](https://github.com/marmot-protocol/marmot/issues/451));
  [#2237](https://github.com/marmot-protocol/mdk/issues/2237),
