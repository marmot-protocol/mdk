# Upgrading MDK 0.13.0 → 0.14.0

## Scope and provenance

This guide compares `v0.13.0` / `marmotkit-v0.13.0` / `marmotc-v0.13.0` /
`wn-agent-v0.13.0`, which all peel to
`891ab34980ee9dc2ef45bf690733a6e31d3e6778`, with the source to be shipped as
`v0.14.0`. All four 0.14.0 cohort tags must peel to the release PR's merged
commit, and packaged manifests must record that exact SHA. The behavior
comparison was prepared against `origin/master` at
`d274dd228a3ac8d624073d8f5835e06c7cd7b30d`; use the full release SHA from the
tags for artifact verification. This guide ships in the
release commit, not a later supplement. See the
[release notes](../release/0.14.0.md), [previous upgrade guide](0.13.0.md), and
[current binding reference](../../crates/marmot-uniffi/README.md).

Readers: native app hosts (Swift/Kotlin through MarmotKit), C hosts, Rust hosts
that embed `marmot-app` or lower crates, and WN Agent operators.

There is no wire-format or MLS change in this release. The conformance vectors
changed only their `conformance_version`, and the formal model is unchanged.

## Upgrade decisions

| Category | Required action or effect |
| --- | --- |
| Required | Replace generated Swift/Kotlin, native libraries and C headers together. Pass a deployment to every constructor in every process (app, background, notification extension). Update exhaustive handling of `MarmotKitError` (seven new variants, `MissingKeyPackage.reason`), `AttachmentTransferStateFfi` (two new states) and `RetentionSweepStatusFfi` (one removed). |
| Required, non-White-Noise hosts | If 0.13.0 kept account secrets in the platform keychain (no `SecretStore`), set `keychainService` to `com.marmot.whitenoise`, the 0.13.0 default. Supply your own services: the neutral deployment has none. |
| Required for C hosts | Recompile. Every `marmot_client_new*` takes a required `deployment`. `MarmotRetentionSweepStatus` renumbers (`FAILED` 5 → 4). Statuses 101–107 and transfer states 17–18 are new. No existing struct layout changed. |
| Required storage | Keep a device-local copy, then allow migrations 0108–0116, directory-cache migration 2 and a one-time raw-key rekey to complete on first open. Downgrade is unsupported. Exclude the account directory, including `media/` and `handoff/`, from cloud and device backups. |
| Required for Rust hosts | Pick a deployment (`MarmotAppConfig::default()` is now neutral), call directory methods through `app.directory()`, and handle the API changes in [Rust host changes](#rust-host-changes). |
| New defaults | MarmotKit's own runtime threads. Encrypted media files with no retained-byte quota and a 2× disk rule. Group changes can refuse with `GroupCatchingUp` or `GroupCommitUndelivered`. New error mappings for invitations and full disks. Follow lists edited in place. Bundled-root QUIC trust. Onboarding repair waits for every source. Background body move, compaction and own-leaf refresh. |
| Optional adoption | Manage storage, Keep media, attachment handoff leases, account attachment history, public event previews, captured media send, commit delivery status, WN Agent `edit_message`. |
| Automatic fixes | Ordered offline catch-up, batched group subscriptions, epoch-gap paging, no retries of terminal relay rejections, retention sweep no longer deletes unread messages, quarantined groups no longer stall receives, iOS `0xdead10cc` fix, consumed KeyPackage keys kept 24 hours, faster database opens, security dependency updates. |

## Required upgrade steps

1. Pin all MDK, MarmotKit, Marmot C and WN Agent inputs to 0.14.0. Verify the
   source SHA in each manifest and every sibling checksum. Do not combine new
   generated records or headers with 0.13.0 native libraries.
2. Choose a deployment and pass it everywhere. See
   [Deployment](#deployment).
3. Rebuild Swift/Kotlin clients after updating exhaustive handling:
   - `MarmotKitError` gains `InvalidEditTarget`,
     `InvalidPublicEventReferences { maxReferences }` (16),
     `DirectoryLookupIncomplete { account }`, `FollowListTooLarge`,
     `GroupCatchingUp { groupIdHex }`, `GroupCommitUndelivered { groupIdHex }`
     and `StorageFull { details }`.
   - `MissingKeyPackage` becomes `MissingKeyPackage { account, reason }` with
     `MissingKeyPackageReasonFfi.NotFound` / `ObsoleteOnly`. Its display text
     now ends in `[not_found]` or `[obsolete_only]`.
   - The same inputs can now arrive as different variants: an incomplete member
     lookup was `Runtime` and is now `DirectoryLookupIncomplete`; a recipient
     with only obsolete KeyPackages was `InvalidKeyPackageEvent` and is now
     `MissingKeyPackage { reason: ObsoleteOnly }`; a full disk or database was
     `Runtime` and is now `StorageFull`.
   - `AttachmentTransferStateFfi` gains `StorageBlocked` and
     `CleanedBySetting`. `RetentionSweepStatusFfi.DeferredScanExhausted` is
     gone; delete that match arm.
   - New records have no binding defaults. `MarmotOptions` has no Rust
     `Default` any more, so `MarmotOptions()` without a deployment no longer
     compiles. Construct `AccountAttachmentQueryFfi` with explicit `[]` / `nil`.

   No existing exported method was removed, renamed or changed between sync and
   async. Five constructors gained a trailing `deployment` argument; compare
   with the `v0.13.0`
   [method reference](https://github.com/marmot-protocol/mdk/blob/v0.13.0/crates/marmot-uniffi/API-REFERENCE.md).
4. Recompile C consumers against the regenerated `marmot.h`. See
   [C host changes](#c-host-changes).
5. Keep the Swift wrapper's `PrivacyInfo.xcprivacy` resource, update the binary
   ZIP, shared Swift file and privacy resource together, keep
   `MarmotAndroid.initialize(context)` before creating `Marmot`, and take all
   JNI ABIs from one cohort.
6. Exclude the account directory from backups and keep a device-local copy
   before first open. See [Storage upgrade](#storage-upgrade).
7. Rust hosts: see [Rust host changes](#rust-host-changes). WN Agent operators:
   see [WN Agent and integrations](#wn-agent-and-integrations).

## Deployment

Services that 0.13.0 compiled in for White Noise now come from one
host-supplied record: recovery-operated relays, discovery indexer relays,
new-group media servers, the group- and profile-image servers, Open Ranking,
the KeyPackage client preference, the moderation label namespace, and the
keychain service used when no `SecretStore` is given. The full contract is in
the binding README's [Deployment](../../crates/marmot-uniffi/README.md#deployment)
section.

- Every constructor takes `deployment: MarmotDeploymentFfi`: `Marmot(rootPath,
  relayUrls, deployment)`, `newWithOptions`, `newWithSecretStore`,
  `newWithCursorPersistence` and `newWithClientName` as their last argument,
  and `newWithConfiguration` through the now-required
  `MarmotOptions.deployment`.
- Start from `marmotDeploymentWhiteNoise()` or `marmotDeploymentNeutral()`
  and change what differs. Blank values count as unset.
- Pass the same deployment to the app, background and notification-extension
  runtimes. Changing `recoveryOperatedRelays` rebuilds pending recovery scopes.
- The lookup is local; no deployment value starts network work by itself.

White Noise apps pass the White Noise preset (illustrative):

```swift
let options = MarmotOptions(clientName: "whitenoise", deployment: marmotDeploymentWhiteNoise())
let marmot = try Marmot.newWithConfiguration(rootPath: rootPath, relayUrls: relayUrls, options: options)
```

```kotlin
val marmot = Marmot(rootPath, relayUrls, marmotDeploymentWhiteNoise())
```

Other hosts start from the neutral preset. If 0.13.0 stored account secrets in
the platform keychain, keep the 0.13.0 service name, or existing accounts can
no longer be unlocked:

```swift
var deployment = marmotDeploymentNeutral()
deployment.keychainService = "com.marmot.whitenoise" // the 0.13.0 default
deployment.newGroupMediaEndpoints = ["https://media.example"]
deployment.groupImageEndpoint = "https://media.example"
```

```kotlin
val deployment = marmotDeploymentNeutral().copy(
    keychainService = "com.marmot.whitenoise", // the 0.13.0 default
    newGroupMediaEndpoints = listOf("https://media.example"),
    groupImageEndpoint = "https://media.example",
)
```

Nothing left unset falls back to White Noise's services:

- With no `newGroupMediaEndpoints`, new groups carry no encrypted-media
  component and stay text-only.
- With no `groupImageEndpoint`, setting or fetching a group image fails:
  MarmotKit reports `Runtime`, C reports status 31, and Rust hosts get
  `AppError::BlobStore`. Group state records no server, so every client sharing a group
  must use the same group-image server; White Noise uses
  `https://blossom.divine.video`.
- With no `profileImageEndpoint`, `uploadProfileImage` needs an explicit server;
  0.13.0 defaulted to `blossom.primal.net`.
- With no `moderationLabelNamespace`, `configureModerationReporting` returns
  `InvalidModerationReportConfig`, a `MarmotOptions.moderationReportConfig` is
  ignored, and reporting reads as unavailable.
- With no `discoveryIndexerRelays`, onboarding, login and relay-list publishing
  search only bootstrap, default and host-passed relays. A neutral host whose
  users' relay lists live only on public indexers should list those indexers;
  confirm `login` against such an account before shipping.
- No recovery relays means every route's history needs all its relays to
  certify; no Open Ranking turns that search tier off; no KeyPackage client
  preference leaves candidates unranked by client tag.

The build-time `MARMOT_ENCRYPTED_MEDIA_BLOB_ENDPOINTS` override is gone. Builds
that set it must set `newGroupMediaEndpoints` instead.

## Storage upgrade

### Schema migrations

Account databases advance from schema 107 to 116 on first open. Each migration
runs in its own transaction, and none rewrites or copies message history.

- 0108 adds account-wide attachment-history expiry and change counters. It
  updates every attachment-history metadata row once, without bodies.
- 0109 lets downloads park on a full disk while keeping their checkpoint.
- 0110 adds the encrypted media-file catalog.
- 0111 adds convergence witness columns to message rows and builds two indexes
  over them. Existing rows are back-filled in the background, 32 rows per 15 s
  maintenance tick (about 7,700 rows an hour); correctness does not depend on it.
- 0112 discards download checkpoints saved by 0.13.0. Interrupted downloads
  restart from the beginning.
- 0113 adds staged outgoing media files.
- 0114 moves avatars and group images to media cache files. At open it copies at
  most 32 MiB of avatars, smallest first; the rest are dropped as if evicted and
  fetched again when shown. A full 128 MiB avatar cache took about 1.1 s and
  166 MiB of extra disk in a desktop debug build.
- 0115 adds subscription-replay recovery obligations for ordered catch-up.
- 0116 adds the Keep media setting.

The per-account directory cache (`app-cache.sqlite3`) advances from schema 1 to
2, adding the public event preview table. The shared `shared.sqlite3` schema is
unchanged.

### Raw SQLCipher keys

App databases now present the same HKDF-derived 32 bytes to SQLCipher as a raw
key instead of a hex passphrase, skipping a 256,000-iteration PBKDF2 on every
open. On a Pixel 8 Pro fixture a keyed schema probe went from 75.9 ms to
0.35 ms; on desktop a full storage open went from 81.9 ms to 21.1 ms. These are
standalone measurements, not app-startup acceptance.

On the first open after upgrade, each `session.sqlite`, `app-cache.sqlite3` and
legacy `app.sqlite3`, for local and external-signer accounts, is rekeyed once:

- MDK tries the raw key, falls back to the passphrase, writes a
  `<database>.raw-key-migrating` marker, runs `PRAGMA rekey`, verifies a fresh
  raw-key connection, and removes the marker. An interrupted rekey resumes on
  the next open.
- `PRAGMA rekey` rewrites every database page. For `session.sqlite` this runs
  before the schema migrations and includes any attachment bodies still stored
  in the database. The directory cache rekeys on first directory use.
- The rekey has been timed only on a tiny fixture. Its cost on a large account
  database, and its temporary disk use (expected to be about one database size
  of WAL), have not been measured. Native startup diagnostics report it under
  the `RecoveryProbe` stage.
- If a notification extension can be the first process to open an account after
  upgrade, it performs the rekey and migrations inside its time and memory
  budget. Test that path; prefer letting the main app open first.

### Encrypted media files

Attachment bodies, download checkpoints, avatars and group images are now
encrypted files under the account directory:

- `<account>/media/<xx>/<id>`: encrypted bodies (an `mdkmedia` header, then an
  age v1 payload in 64 KiB segments) and `<id>.wire` download checkpoints.
- `<account>/handoff/<lease>/<name>`: plaintext copies for OS surfaces, removed
  when released, when the account is removed, or when the worker next starts in
  a new process.

Exclude the whole account directory, including `media/` and `handoff/`, from
iCloud and Android backups. Restoring a database without its media files, or
media files without their database, is not supported; the media sweep removes
files that have no row.

Bodies 0.13.0 kept in the database move to files in the background, smallest
first. The worker starts at most one batch per 15 s maintenance tick; it skips
a tick while the previous batch is still running or the runtime is frozen
(notification extensions), and defers it when the account's storage cannot be
opened, so a backlog can take longer than the batch limits alone suggest. A
batch stops after 64 bodies, or before
starting another body once 64 MiB have moved, so one large body can take a
batch past 64 MiB. Each file is verified before its rows are deleted. On a
tight disk the move pauses, reports `AttachmentMigrationStateFfi.Paused` with
the bytes it needs, and deletes nothing to make room. Avatars and group images
move the same way, in batches of up to 64 images that stop starting new ones
after 16 MiB.

The database file does not shrink when bodies leave it. New databases use
incremental vacuum. An existing database gets one automatic compaction from the
maintenance tick, never at open, when at least a quarter of it is free, its live
data is at most 64 MiB, and the disk has room for the reserve plus twice the
live data. Account reads and writes wait during it, about a second on a recent
iPhone, and a close for suspension may wait for its last part.
`AttachmentMigrationStateFfi.Compacting` reports it. Accounts with more live
data than 64 MiB are not compacted automatically in this release.

### Downgrade and backups

Downgrade is unsupported. 0.13.0 cannot open a rekeyed database and returns a
key error without reading any table. After the documented
[offline rekey](../marmot-architecture/storage-format-v2.md#offline-downgrade)
back to a passphrase, 0.13.0 refuses schema 116 with `UnsupportedSchemaVersion`.
The remedies are to re-upgrade or to restore a device-local copy of the account
directory taken before upgrading: the databases with their WAL, the `.salt`
sidecars, and the secret-store credentials. Restoring an older database also
rewinds MLS state, so prefer re-upgrading.

See the [storage-format contract](../marmot-architecture/storage-format-v2.md)
and [local artifact safety](../marmot-architecture/overview/local-artifact-safety.md).

## Changed defaults

### MarmotKit threading

MarmotKit now runs MDK on its own process-wide Tokio runtime, with half the
CPUs as workers, clamped to 2–4, named `marmotkit-rt`. In 0.13.0 async calls
ran on UniFFI's single compatibility thread plus whichever host thread polled
them.

- Awaiting a MarmotKit call from the main actor or `Dispatchers.Main` no longer
  runs MDK work on the UI thread.
- Cancelling a Kotlin coroutine aborts its task. Swift still waits for the call
  to finish.
- Subscription receives (`next()`, `nextUpdate()`) and `openAttachmentHandoff`
  are polled on the caller's thread, so a cancelled wait loses no update.
  `shutdownAndClose` and `releaseAttachmentHandoff` run to completion even if
  the caller cancels.
- Host callbacks (`SecretStore`, external signers) can run on runtime threads
  concurrently and must not wait for the main thread.
- There is one runtime per process; its idle threads remain after
  `shutdownAndClose`. Constructors return `Runtime` if it cannot start.

See the binding README's [Threading model](../../crates/marmot-uniffi/README.md#threading-model).

### Attachment storage rules

- `AttachmentDownloadPolicyFfi.retainedBytes` no longer limits downloads. Free
  disk above the policy's reserve is the only gate, and nothing is evicted
  automatically. Use [Manage storage](#manage-storage-optional) and
  [Keep media](#keep-media-optional) to give users control.
- A download needs the reserve plus twice its body, down from four times.
- On a full disk a download parks as `StorageBlocked` instead of retrying on a
  timer. It is readmitted once the needed space plus 4 MiB is free; a parked
  prefix is kept for up to seven days.
- `uploadMedia*` copies each source into the media store before uploading and
  fails with `StorageFull` before uploading anything if it does not fit. With
  256 uploads already awaiting publication, a send fails with
  `InvalidMediaReference` and publishes nothing.
- `controlAttachment` Remove deletes the released file before it returns, and
  fails before removing anything if the media store cannot open.

### Group-change gates

Group changes can now be refused while the device may be acting on stale or
undelivered state:

- `GroupCatchingUp { groupIdHex }`: the device is still catching up on the
  group's history.
- `GroupCommitUndelivered { groupIdHex }`: the account's previous commit has
  been owed to at least one relay for two minutes.

Gated calls are invites, removals, admin promotion and demotion, enabling
disbanding and disbanding, retention, app components, media endpoints, the
group avatar URL, the group image and the group profile. Messages and leaving
are never gated.

Show the user what is happening, then call `acknowledgeGroupCatchingUp` or
`acknowledgeGroupCommitUndelivered(accountRef, groupIdHex)` and retry. An
acknowledgement is held in memory only, admits exactly one attempt, and is spent
even if that attempt fails. It returns `false` when nothing applies. The device's
own due self-updates wait up to 24 hours while catching up and up to an hour for
delivery.

Illustrative Swift:

```swift
do {
    try await marmot.inviteMembers(accountRef: account, groupIdHex: group, memberRefs: members)
} catch MarmotKitError.GroupCommitUndelivered(let groupIdHex) {
    if await userConfirmsSendingAnyway(groupIdHex) {
        _ = try await marmot.acknowledgeGroupCommitUndelivered(accountRef: account, groupIdHex: groupIdHex)
        try await marmot.inviteMembers(accountRef: account, groupIdHex: group, memberRefs: members)
    }
}
```

`groupCommitDelivery(accountRef, groupIdHex)` returns the owed relays for a
group, or `nil` when nothing is owed. It is local and works before the group is
hydrated. A result does not mean the next change will be refused, and no event
fires when delivery completes, so poll while you show it. Relay URLs in it must
stay out of logs.

### Invitation lookup outcomes

Invitations and member resolution stop at the first unusable recipient, in
request order:

- `MissingKeyPackage { account, reason: ObsoleteOnly }`: the recipient only has
  KeyPackages from an outdated client and must update their app.
- `MissingKeyPackage { account, reason: NotFound }`: no KeyPackage was found.
- `DirectoryLookupIncomplete { account }`: the lookup ran out of time or relay
  coverage. Offer a retry. Its display text leaves the account out.
- `MissingMemberInboxRoute`: unchanged.

The whole resolution shares one 50-second deadline, so no call takes longer
than before.

### Follow lists and edits

- `followUser` and `unfollowUser` edit the current kind-3 list in place, keeping
  petnames, relay hints, other tags and content. With 2,048 or more follows they
  refuse with `FollowListTooLarge` and publish nothing; 0.13.0 truncated the list.
- `editMessage` refuses with `InvalidEditTarget`, publishing nothing, when the
  original is not an available chat message the account sent. A message whose
  own publish failed and is awaiting retry stays editable.

### QUIC broker trust

`startAgentTextStream`, `openAgentPublisher` and `watchAgentTextStream` (and the
C equivalents with a NULL certificate) verify brokers against the bundled
Mozilla roots (`webpki-roots`) instead of the OS trust store. This fixes an
Android abort on the first handshake. A broker behind a private or enterprise
CA must be pinned with `serverCertDer`.

### Onboarding repair freshness

`approveOnboardingRepair` and `approveOnboardingRepairInEpoch` now require a
completed freshness query from every source, including relays the account
itself declared. Otherwise the step becomes `RetryableFailure` and the proposal
is cleared; show the retry rather than an error.

### Background maintenance

`start` now schedules, besides the body move and compaction above, a
self-update commit for any group where the account's own leaf is stale, at a
random persisted time within five days. It re-advertises every supported app
component and is ordinary commit traffic other members see. Frozen
(notification-extension) runtimes run none of this.

## Feature adoption

### Manage storage (optional)

Show users where attachment storage goes and let them free it. See
[Manage storage](../../crates/marmot-uniffi/ATTACHMENT-ACCESS.md#manage-storage).

- `attachmentStorageUsage(accountRef)` returns `AttachmentStorageUsageFfi`:
  `mediaBytes`, `legacyBytes` (still in the database), `attachmentCount`,
  `databaseBytes`, `databaseFreeBytes`, `cacheBytes`, and the body move's
  `migration` state with `migrationBytes` (bytes remaining while `Running`,
  bytes needed while `Paused`, otherwise 0).
- `attachmentStorageByChat(accountRef, limit, cursor)` and
  `largestRetainedAttachments(accountRef, groupIdHex, limit, cursor)` page
  through chats and attachments. Limits are 1–256; an invalid limit surfaces as
  an untyped `Runtime`, so validate it in the host. Cursors are opaque, never
  persisted, and invalid after any removal: start over.
- `removeChatAttachments(accountRef, groupIdHex)` and
  `removeAttachmentsOlderThan(accountRef, receivedBefore, groupIdHex)` return
  the number removed. `receivedBefore` is Unix seconds; `UInt64.max` removes
  everything.

All of these are local. Run them off the UI thread; removals unlink files before
returning.

### Keep media (optional)

`setAttachmentKeepMedia(accountRef, keep)` sets how long this device keeps
attachments: `Forever` (the default), `OneYear` (365 days), `SixMonths`
(183 days) or `ThirtyDays`. Setting a window removes everything past it before
returning and returns the count; afterwards the worker sweeps hourly, at most
250 ms per tick. Age is the later of the received time and the last explicit
download. Removed attachments show `CleanedBySetting`. The setting is per device
and is read back with `attachmentKeepMedia(accountRef)`.

### Attachment handoff leases (optional)

`openAttachmentHandoff(accountRef, groupIdHex, target, control)` copies one
locally held attachment to a plaintext file for the share sheet, a document
viewer or another app, and returns `AttachmentHandoffFfi` (`lease`, `path`,
`byteCount`, `mediaType`, `fileName`), or `nil` when the attachment is not held
locally (no download starts). Pass a fresh `MediaFileTransferControlFfi` and
cancel only through it. Call `releaseAttachmentHandoff(lease)` when the OS is
done; it is idempotent. A malformed lease returns `InvalidMediaReference`, a
failed delete returns `Io` and should be retried. Removing the attachment does
not revoke a lease. Android needs a `FileProvider` path for
`accounts/*/handoff/`. See
[Handoff leases](../../crates/marmot-uniffi/ATTACHMENT-ACCESS.md#handoff-leases).

### Account attachment history (optional)

`accountAttachmentHistoryPage(accountRef, query, limit, cursor)` lists
attachments across every chat. `AccountAttachmentQueryFfi` filters by groups,
senders and a timeline window; pass `[]` and `nil` for no filter. The result is
`AccountAttachmentPageReadFfi`: `Page { page }`, `RestartRequired`,
`CursorMismatch`, `InvalidQuery` or `InvalidLimit`.

- Limits are 1–100. A read visits at most 101 slots; metadata is capped at
  32 KiB per entry and 512 KiB per page, and `metadataLimited` marks an entry
  over the cap. An empty page that still has `nextCursor` is not the end.
- `accountAttachmentHistoryVersion(accountRef)` and
  `version.changeSince(previous)` return `Unchanged`, `Additions` or
  `RestartRequired`. Schedule a re-read at the page's `nextExpiry`.
- Reads are local and decrypt nothing. Keep handles in memory only.

See [account attachment history](../../crates/marmot-uniffi/ACCOUNT-ATTACHMENT-HISTORY.md).

### Public event previews (optional)

Render `nostr:` references in messages:

1. `cachedPublicEventPreviews(accountRef, references)` is synchronous and local,
   takes at most 16 references (`InvalidPublicEventReferences` above that), and
   returns results in input order, duplicates included. A cold call opens the
   encrypted directory cache, so call it off the UI thread.
2. For each reference shown, `resolvePublicEventPreview(accountRef, reference)`
   fetches only when the entry is missing or stale. An event id that every relay
   answered is never fetched again; partial fetches and `naddr` references are
   refetched after 30 minutes, and calls within 30 seconds of a finished fetch
   return local state. A failed fetch keeps prior content.

`PublicEventPreviewFfi` carries `state` (`Present`, `Deleted`, `Missing`,
`Unsupported`), `eventJson` (NIP-01 JSON, only when present) and `fetchedAt`.
`Deleted` means the author published a NIP-09 deletion. See
[Public event previews](../../crates/marmot-uniffi/README.md#public-event-previews).

### Captured media send (optional)

`sendPreparedMediaWithClientToken(accountRef, groupIdHex, attachments, caption,
clientToken, consumingDraft)` sends media that was uploaded earlier with
`send = false`. The draft is consumed only if its revision is still current, so
a newer draft is kept. Replaying a token returns its original identity; after a
restart, call `localSendStatus` first. There is no reply target. See
[local sends](../../crates/marmot-uniffi/LOCAL-SENDS.md).

## C host changes

Recompile against the `marmot.h` shipped with the exact library. Hand-written
FFI declarations (ctypes, cgo, Dart) are not compiler-checked; update them by
hand.

- `marmot_client_new`, `_with_options`, `_with_cursor_persistence`,
  `_with_secret_store`, `_with_client_name` and `_with_configuration` take
  `const struct MarmotDeployment *deployment` immediately before `out_client`.
  NULL returns `MARMOT_STATUS_NULL_POINTER` (1) before anything opens, and a
  host secret store passed with a NULL deployment is not taken. The deployment
  is cloned, so free it right after the call:

  ```c
  struct MarmotDeployment *deployment = NULL;
  marmot_deployment_white_noise(&deployment);
  struct MarmotClient *client = NULL;
  enum MarmotStatus status =
      marmot_client_new(root_path, relays, relay_count, deployment, &client);
  marmot_deployment_free(deployment);
  ```

  `marmot_deployment_neutral` and the setters
  `marmot_deployment_set_{recovery_operated_relays,discovery_indexer_relays,new_group_media_endpoints,group_image_endpoint,profile_image_endpoint,open_ranking,key_package_client_preference,moderation_label_namespace,keychain_service}`
  build other deployments. Strings are borrowed; a failed setter leaves the
  handle unchanged. Non-White-Noise hosts that used the keychain must call
  `marmot_deployment_set_keychain_service(deployment, "com.marmot.whitenoise")`.
- `MarmotRetentionSweepStatus` drops `DEFERRED_SCAN_EXHAUSTED`, so `FAILED`
  moves from 5 to 4. A host built against the old header reads a failed sweep
  as scan exhaustion.
- `MarmotAttachmentTransferState` appends `STORAGE_BLOCKED` (17) and
  `CLEANED_BY_SETTING` (18).
- New statuses: `GROUP_CATCHING_UP` (101), `GROUP_COMMIT_UNDELIVERED` (102),
  `INVALID_PUBLIC_EVENT_REFERENCES` (103), `DIRECTORY_LOOKUP_INCOMPLETE` (104),
  `INVALID_EDIT_TARGET` (105), `STORAGE_FULL` (106), `FOLLOW_LIST_TOO_LARGE`
  (107). Lookups that ran out of time return 104 instead of `RUNTIME` (31);
  capacity errors return 106 instead of 31; obsolete-only recipients return 15
  instead of `INVALID_KEY_PACKAGE_EVENT`, with the last-error text ending in
  `[obsolete_only]`.
- No existing struct layout changed; callback typedefs and the
  `MarmotSecretStore` vtable are byte-identical.

New functions mirror the features above:
`marmot_acknowledge_group_catching_up`, `marmot_acknowledge_group_commit_undelivered`,
`marmot_group_commit_delivery`, `marmot_cached_public_event_previews`,
`marmot_resolve_public_event_preview`, `marmot_open_attachment_handoff`,
`marmot_release_attachment_handoff`, `marmot_attachment_storage_usage`,
`marmot_attachment_storage_by_chat`, `marmot_largest_retained_attachments`,
`marmot_remove_chat_attachments`, `marmot_remove_attachments_older_than`,
`marmot_attachment_keep_media`, `marmot_set_attachment_keep_media`, the
`marmot_account_attachment_history_*` family and
`marmot_send_prepared_media_with_client_token`, each with its free function.
Ownership notes that differ from the Swift/Kotlin contract:

- One deep-free releases a page result of any tag; its `version` and
  `next_cursor` are borrowed fields. Keep page N alive while passing its cursor.
  Never pass a page's own `version` to `marmot_account_attachment_version_free`;
  clone it first.
- A storage page's cursor is borrowed from the page. A limit outside 1–256
  returns 31, not 6.
- Copy `lease` before `marmot_attachment_handoff_free`, which does not release
  the lease. A cancelled copy returns 39; on Windows handoff always returns 39.
- `marmot_group_commit_delivery` writes NULL when nothing is owed.
- Every new call blocks. Only `marmot_resolve_public_event_preview` does network
  work.

`MarmotAttachmentDownloadPolicy.retained_bytes` no longer gates downloads, as
described under [Attachment storage rules](#attachment-storage-rules). See the
[C README](../../crates/marmot-c/README.md) and
[symbol inventory](../../crates/marmot-c/API-REFERENCE.md).

## Rust host changes

- **Deployment.** `MarmotAppConfig::default()` and `MarmotDeployment::default()`
  are neutral. Use `MarmotAppConfig::white_noise()` or
  `with_deployment(MarmotDeployment::white_noise())` to keep White Noise's
  services and keychain service. Removed: `recovery_operated_relays`, four
  `MarmotServiceEndpoints` fields, `default_directory_discovery_relays`,
  `DEFAULT_BLOSSOM_SERVER_URL(S)`, `MODERATION_REPORT_LABEL_NAMESPACE`,
  `DEFAULT_KEYCHAIN_SERVICE_NAME`, `AccountHome::open_with_default_keychain`
  and the `MARMOT_ENCRYPTED_MEDIA_BLOB_ENDPOINTS` build override.
- **Directory.** The user directory is the `nostr-directory` crate. `MarmotApp`'s
  16 directory methods (`search_users`, `resolve_member_key_packages`,
  `directory_entry_for_account_id`, `refresh_profile_for_account_id` and the
  rest) are called as `app.directory().<same name>(…)` and return
  `DirectoryError`; `?` or `AppError::from` converts it with the same variant,
  message and `privacy_safe_kind`. Directory types keep their `marmot_app::`
  paths. `MarmotAppRuntime` and the bindings are unchanged.
- **Errors.** `AppError` gains `DirectoryLookupIncomplete`,
  `InvalidPublicEventReferences`, `GroupCatchingUp`, `GroupCommitUndelivered`,
  `FollowListTooLarge` and `InvalidEditTarget`; `MissingKeyPackage(String)`
  becomes `MissingKeyPackage { account, reason }`.
- **Enums and records.** `RetentionSweepStatus::DeferredScanExhausted` is
  removed; `AttachmentTransferState` gains `StorageBlocked` and
  `CleanedBySetting`; recovery enums gain subscription-replay variants;
  `GroupMaintenanceState.leaf_refresh_due_at`,
  `RetainedKeyPackagePrivateMaterial.consumed` and
  `PendingKeyPackageReplacement.consumed_at` are new (serde defaults keep old
  records readable; struct literals must set them).
- **Ingestion.** `Engine::ingest_with_audit_context(&TransportMessage, …)`,
  `AccountDeviceSession::ingest_delivery(&TransportDelivery)` and marmot-account
  `ingest_delivery*` borrow their input. The `CgkaEngine::ingest` trait method
  is unchanged.
- **Signature verification.** Group peeling no longer verifies kind-445 Schnorr
  signatures; the adapter's ingest boundary does. Hosts that build
  `TransportMessage`s from `NostrTransportEvent` DTOs themselves must call
  `to_verified_nostr_event` first. Welcomes are still verified by the NIP-59
  unwrap.
- **Transport adapter.** `NostrRelayClient` loses `reissue_subscription` and
  `subscription_eose_received`; `unsubscribe_account` takes `replacements`;
  `RelayReissue`, `EoseReissueSummary`, `NotificationLagMark` and
  `SubscriptionReissue` are removed; `reconcile_subscription` takes an absolute
  deadline; `NostrSubscription::GroupBatch`, `NostrAcquisitionScope::GroupsWindow`
  and `NostrAcquisitionEnd::InvalidMessage` are new. The relay plane now lives
  in the `transport-nostr` crate; `marmot-app` re-exports the same names.
- **Relay notifications.** `NostrTransportAdapter::observe_relay_event` takes
  `(id: &[u8], endpoint: &TransportEndpoint, subscription_id: Option<&str>,
  created_at: u64)` instead of a `NostrRelayEvent`. Pass an authenticated event
  id, and pass each relay's copies in order with that relay's EOSE: the adapter
  counts stored events before EOSE to detect a replay the relay clamped. Report
  a stored event that could not be converted to a `NostrTransportEvent` with
  `observe_unconvertible_relay_event(endpoint, subscription_id, created_at)`
  instead of dropping it, because it still used a slot of the relay's page.
- **Storage.** App and transport methods moved from `SqliteAccountStorage` to
  `SqliteAppStorage`, reached through `storage.app_storage()`.
  `record_reconciliation_items` replaces `record_transport_reconciliation_item`;
  `AttachmentPartial` and `AvatarAssetRead` changed shape;
  `SqlCipherKey::raw([u8; 32])` is new and `SqlCipherKey::new` rejects raw-key
  syntax. `StorageProvider` and `MessageStorage` gain three methods with
  default bodies.
- **New crates** (unpublished): `transport-nostr`, `nostr-directory`,
  `media-store`, and the internal `marmot-uniffi-macros`.
- **Tracing targets.** `storage-sqlite` targets are module paths, for example
  `storage_sqlite::base::connection` and
  `storage_sqlite::app::attachment_acquisition::file_import`. Directory events
  use `nostr_directory::{search,sync,cache}`, and the app's directory-side
  events `marmot_app::{directory_resources,user_blocks,profile_publication}`
  and `marmot_app`. Update log filters that matched the old names.

## WN Agent and integrations

- **Edits.** Agent control adds `edit_message`
  `{account_id_hex, group_id_hex, target_message_id_hex, text}`, answered with
  `final_sent` naming the edit event. Only an available chat message the agent's
  account sent can be edited; anything else is refused with `invalid_edit_target`
  (not retryable) and nothing is published. The protocol id stays
  `marmot.agent-control.v2`; Rust `AgentControlRequest` matches must handle the
  new variant. OpenClaw adds `message(action: "edit")`; the Hermes control
  client adds `edit_message`, but Hermes agents cannot edit yet.
- **Upgrade together.** A 0.14.0 plugin calling `edit_message` against a 0.13.0
  `wn-agent` sees the socket close without an error
  ([#2242](https://github.com/marmot-protocol/mdk/issues/2242)).
- **OpenClaw** deletes and edits act only in the conversation the host
  authorized, and refuse a message the agent sent to another conversation.
- **Hermes** accepts `final_sent` for `delete_message`; 0.13.0 reported every
  own-message delete as failed. `disconnect()` no longer hangs on Python 3.11.
- **Group changes.** The new group-change refusals and incomplete lookups reach
  agents as a generic `app_error`, with no acknowledge request.
- **QUIC previews.** `wn-agent` has no certificate-pin option. A broker that
  only the OS trust store accepted now fails verification, so live previews
  stop; durable final messages still send.
- **Installers.** Install only from the immutable `wn-agent-v0.14.0` release
  with sibling `.sha256` verification. Installers run from a checkout on a
  `-dev` version default to the newest published release notes.
- Dated `wn-agent-v0.14.0-nightly.*` pre-releases exist for testing. They carry
  no installers and are never marked Latest.

## Changes requiring no new calls

- **Catch-up and delivery.** Each group's full offline replay range is staged
  before MLS processing, so catch-up is ordered and complete; a cold start
  without a durable cursor requests retained history. Live group subscriptions
  are batched up to 50 routes per REQ, about 21 REQs per relay at 1,000 groups.
  Leaked REQs are closed, and replays a relay clamps at 500 events are paged
  backwards. An epoch gap falls back to each relay's newest 256 events (up to
  4 MiB) and pages back from there. Terminal `OK false` rejections (`blocked:`,
  `invalid:`, `pow:`, `restricted:`) are not retried. Stalled recovery routes no
  longer use up every pass, and reconciliation waits are bounded. Self-update
  commits retry every missed relay.
- **Correctness.** The retention sweep no longer deletes an expired message the
  unread count still shows. A quarantined group no longer stalls every
  conversation's receives. Notification-extension wakes arm epoch-stall
  detection. A Welcome built from a just-replaced KeyPackage can be joined:
  consumed KeyPackage keys are kept 24 hours. A generated identity's setup no
  longer advertises the app's relays before the user's chosen lists.
- **Lifecycle.** `shutdownAndClose` closes every engine connection before
  releasing the root lease, fixing iOS `0xdead10cc` terminations and the
  notification extension taking the lease mid-write; `storageIsClosed()` is now
  accurate. Reopening a database keeps the live connection's POSIX locks.
- **Performance.** Raw-key database opens; convergence passes skip inert
  delivered messages (2,578 ms → 8.9 ms at 50,000 messages); failed applies roll
  back through a savepoint; reorgs rewind onto their anchor without rewriting
  history; bounded Welcome scans; less redundant inbound work. Receiving an
  attachment no longer holds several copies of it in native memory.
- **Security updates.** `quinn-proto` (RUSTSEC-2026-0338 to -0342), `rustls`
  (RUSTSEC-2026-0346 to -0349), `negentropy` (RUSTSEC-2026-0365),
  `rustls-webpki` and `webpki-roots` (RUSTSEC-2026-0381, -0382).

The retired-relay denylist is unchanged (`relay.nostr.band`).

## Acceptance and remaining work

Before shipping an app on 0.14.0:

- Compile against the matched artifacts and confirm every constructor in every
  process passes the intended deployment. On a non-White-Noise host, upgrade an
  install that used the 0.13.0 keychain and confirm existing accounts unlock.
- Upgrade a real, large account in place: time the first open (rekey plus
  migrations), watch free disk during it, then reopen and confirm the second
  open is fast and migrates nothing. Repeat with the app killed mid-upgrade.
- Make the notification extension the first process to open an upgraded
  account, and confirm it stays within its budget or defers to the app.
- Confirm the account directory is excluded from iCloud and Android backups.
- Watch the background body move and compaction finish on an account with
  0.13.0 attachments: `attachmentStorageUsage` should move from `Running` to
  `Complete`, and a tight disk should report `Paused` without deleting anything.
- Exercise each group-change gate's prompt and retry, full-disk sends and
  downloads (`StorageFull`, `StorageBlocked`), invitation outcomes, and
  `FollowListTooLarge`.
- If you adopt them, exercise Manage storage, Keep media, handoff leases with
  the OS share sheet, account attachment history paging and public event
  previews offline and online.
- Report evidence by stage: source, host smoke, packaged artifact, consuming
  app, real device.

What was validated for this release: the workspace's required CI and merge-queue
matrix, upgrade fixtures from 0.10.4 (schema 89) through 116 that reopen without
rewriting, per-migration upgrade tests, crash-window tests for the raw-key
rekey, the media store, the legacy body move, avatar publication and
compaction, and the formal convergence model. Not yet validated: Android and
iOS app-level open timings for the rekey, iOS device validation of the rekey,
large-database rekey cost, a 0.13.0 (schema 107) fixture, and a pinned 0.13.0
binary against a rekeyed database.

Known limitations:

- [#2237](https://github.com/marmot-protocol/mdk/issues/2237): a message that
  arrives more than five epochs too late stays undecryptable without a notice.
- Group-change gates: undecryptable traffic can hold a group's changes
  ([#2277](https://github.com/marmot-protocol/mdk/issues/2277)), no bounded
  catch-up runs before refusing
  ([#2283](https://github.com/marmot-protocol/mdk/issues/2283)), and an
  acknowledgement cannot be withdrawn
  ([#2389](https://github.com/marmot-protocol/mdk/issues/2389)).
- [#2253](https://github.com/marmot-protocol/mdk/issues/2253): group data
  updates reorder the app-data extension, which order-preserving
  implementations reject.
- [#2158](https://github.com/marmot-protocol/mdk/issues/2158): an upload in
  flight when the group epoch advances is lost.
- Accounts with more than 64 MiB of live data are not compacted automatically.
- WN Agent's control socket grants its whole API to any authenticated client
  ([#1445](https://github.com/marmot-protocol/mdk/issues/1445)).
