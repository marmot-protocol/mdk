# Upgrading MDK 0.10.4 → 0.11.0

## Scope and provenance

This guide compares `v0.10.4` / `marmotkit-v0.10.4` / `marmotc-v0.10.4` /
`wn-agent-v0.10.4`, which all peel to
`fcc85edd8dbd07c8293c899ee52230f72c54c897`, with the source to be shipped as
`v0.11.0`. All four 0.11.0 cohort tags must peel to the release PR's merged
commit, and packaged manifests must record that exact SHA. The behavior comparison
was prepared against `origin/master` at
`3d0110ff9f25b1b3c3e3496b1513ace936cd1f9d`; use the full release SHA from the
tags for artifact verification. This guide ships in the release commit, not a
later supplement. See the [release notes](../release/0.11.0.md),
[previous upgrade guide](0.10.4.md), and
[current binding reference](../../crates/marmot-uniffi/README.md).

Readers: native app hosts (Swift/Kotlin through MarmotKit), C hosts, Rust hosts
that embed `marmot-app`, and WN Agent operators.

## Upgrade decisions

| Category | Required action or effect |
| --- | --- |
| Required | Replace generated Swift/Kotlin, native libraries and C headers together. Rebuild consumers and update exhaustive handling of `MarmotEventFfi`, `HostPerformanceOperationFfi` and `HistoryNoticeCauseFfi`, and C record layouts. |
| Required storage | Back up, then allow migrations 90–98 to complete on first open. Downgrade across them is unsupported. |
| Required host UI | Surface "history may be incomplete" notices and let the user dismiss them. The transport cursor stays fenced while any loss obligation or spill hand-off is pending. Qualified recovery releases it without a dismissal; for parked loss, dismissing releases it only when no loss recovery remains pending. |
| Required for Rust hosts | Remove `dev_epoch_backfill_eose_wait_ms` / `dev_epoch_backfill_execution_quantum_ms`. Set `recovery_operated_relays` in full `MarmotAppConfig` literals and `replaced_at` in `AppPriorNostrRoute` literals. Align on the pinned `nostr` / `nostr-sdk` fork revision. |
| Required for OpenClaw | Configure `channels.marmot.senderPolicy`, or `MARMOT_ALLOWED_USERS` / `MARMOT_ALLOW_ALL_USERS`. Without one, the channel denies every inbound sender. |
| Required for WN Agent installs | Install from the versioned `wn-agent-v0.11.0` release. The mutable `wn-agent-latest` alias is retired. |
| New defaults | Recovery certifies routes on the operated relays `wss://relay.eu.whitenoise.chat` and `wss://relay.us.whitenoise.chat`. A full delivery queue spills to disk. The cursor advances on live ingest. Relay lists and profiles are copied to public indexers. Explicit catch-up no longer re-subscribes an active session. |
| Optional adoption | Pending-send edits, NIP-88 polls, stateless event verification, new host performance stages, v5 audit OTLP destination, Hermes presence reactions. |
| Automatic fixes | Notification lag keeps the route open, lost EOSE is repaired, history REQs are floored, worker restarts and reconnects recover, and chat-list/conversation-window commands survive background refreshes. |
| Packaging | Android 64-bit JNI libraries use 16 KB ELF alignment. Apple archives carry no LLVM bitcode. MarmotKit release builds use thin LTO and one codegen unit. |

## Required upgrade steps

1. Pin all MDK, MarmotKit, Marmot C and WN Agent inputs to 0.11.0. Verify the
   source SHA in each manifest and every sibling checksum. Do not combine new
   generated records or headers with 0.10.4 native libraries.
2. Rebuild Swift/Kotlin clients after updating exhaustive handling:
   - `MarmotEventFfi` gains `HistoryNoticesChanged { accountIdHex, accountLabel }`.
   - `GroupRecoveryStatusFfi` gains `historyMayBeIncomplete` and
     `historyNoticeIds`. Both have binding defaults for host-constructed records.
   - `TimelineMessageRecordFfi` gains the optional `poll` projection.
   - `HostPerformanceOperationFfi` gains 28 shared and nine Linux-specific stages.
   - New types: `HistoryNoticeFfi`, `HistoryNoticeCauseFfi`, `PollTypeFfi`,
     `PollProjectionFfi`, `PollOptionResultFfi`, `AuditOtlpConfigV5Ffi`,
     `AuditLogTrackerUpdateResultV5Ffi` and `AuditOtlpTrackerResultV5Ffi`.

   No existing exported method changed its signature (compared against the
   `v0.10.4` [method reference](https://github.com/marmot-protocol/mdk/blob/v0.10.4/crates/marmot-uniffi/API-REFERENCE.md)).
3. Recompile C consumers. `MarmotGroupRecoveryStatus` appends
   `history_may_be_incomplete` and the `history_notice_ids` array, which its existing
   deep-free releases. `MarmotTimelineMessageRecord` gains a nullable poll field.
   `MarmotEvent` appends the `MARMOT_EVENT_HISTORY_NOTICES_CHANGED` tag and body.
   Existing tag and `MarmotStatus` values are unchanged. Use only the header shipped
   with the exact library.
4. Preserve the Swift wrapper's `PrivacyInfo.xcprivacy` resource and dependency in
   every app and extension. Update the binary ZIP, shared Swift file and privacy
   resource together. Android still requires `MarmotAndroid.initialize(context)`
   before creating `Marmot`, and all JNI ABIs must come from one cohort.
5. Back up each account database before first open. See
   [Storage upgrade](#storage-upgrade) below and the
   [storage-format contract](../marmot-architecture/storage-format-v2.md). Do not
   remove migration rows to roll back. Restore a pre-upgrade backup/export or
   re-upgrade.
6. Add the history-notice UI described below.
7. Rust hosts: see [Rust host changes](#rust-host-changes).

## Storage upgrade

The first open of each account database runs migrations 90 through 98 in one
forward pass:

| Migration | Effect |
| --- | --- |
| 90 | Indexes existing NIP-88 poll responses as message-modifier edges. |
| 91 | Records the account's local identity. |
| 92 | Adds the durable recovery ledger. It converts 0.10.4 overflow markers and epoch-backfill intents into recovery obligations and drops the old tables. |
| 93–95 | Recovery route snapshots, qualified stall observations and comparison state. |
| 96 | Durable overflow spill for the account delivery queue. |
| 97 | A lower time bound for each loss generation. Rows written before it have no known bound. |
| 98 | History-notice fields: parking time, dismissed scopes and a retired count. |

The migrations add tables and columns, and none rewrites message history. A
v0.10.4 binary refuses the upgraded database with `UnsupportedSchemaVersion` before
it reads account tables.

The committed regression test `upgrade_v0_10_4_tests.rs` opens a database that the
v0.10.4 runtime wrote (`crates/storage-sqlite/fixtures/account-v0.10.4.sql`). It
checks that migrations 90–98 apply in order, that the schema matches a fresh
database, and that 15 tables and the cursor are preserved row for row. It also
checks that recovery and notice state start empty, that the retained route is
stamped exactly once, and that the v0.10.4 migration set refuses the result. A
separate synthetic v0.10.4 → master upgrade run, not committed as a test, confirmed
the behaviors below.

What users and hosts can observe after upgrading:

- **Migrations 90–98 run on first open.** Nothing that v0.10.4 held in its
  ordinary tables becomes recovery debt or a notice.
- **An overflow marker becomes a notice.** A 0.10.4 overflow marker records only
  a count of lost deliveries, with no time bound. Migration 92 turns it into a
  delivery-loss obligation that no comparison can certify, because its goal has no
  lower bound. Shortly after upgrade, once the required relays have answered three
  comparisons in a row without progress, it parks. It then appears as a
  `DeliveryLoss` "history may be incomplete" notice. The loss stays pending, and
  the transport cursor stays fenced, until the user dismisses it; the fence then
  releases only if no other loss recovery remains pending. This is expected for
  those accounts; it is not a new loss.
- **A stuck group keeps its warning.** The `automatic_recovery_failed` warning is
  a durable row that migration 92 leaves unchanged, so a failure 0.10.4 recorded
  survives the upgrade. It clears only after authenticated recovery: the group is
  joined again (`GroupJoined`), a peer message arrives at the current epoch, or the
  user confirms a rejoin. It also clears if the group becomes terminal. The one-hour
  epoch-stall re-arm interval only paces when a wedged group may arm another
  epoch-recovery attempt under the new comparison job; it does not clear the
  warning.
- **Retained routes are stamped once.** Each retained prior route has no recorded
  switch time after upgrade. The first account load stamps it with the load time
  and never restamps it. Because the retained-route floor sits 15 minutes below
  that anchor, the route's first activation after upgrade re-fetches up to 15
  minutes of its history, once. Later loads do not repeat this.

## History may be incomplete notices

Automatic recovery now stops retrying an obligation after a fixed budget of
attempts that recover and certify nothing. It parks, and each parked occurrence
is a notice to show as "history may be incomplete". Recovery no longer retries
forever in the background or reports success it cannot prove.

- `historyNotices(accountRef)` returns `HistoryNoticeFfi` records, oldest first.
  Each has an opaque `noticeId`, a `HistoryNoticeCauseFfi` for the host's wording
  (`DeliveryLoss`, `NotificationLoss`, `EpochGap`, `IncrementalHistory`,
  `ExplicitRepair`, `KnownEvent` or `MaintenanceBoundary`), an optional
  `groupIdHex` and an optional `parkedAtMs`. `groupIdHex` is set for a
  group-scoped occurrence (an epoch gap) and absent for an account-wide one. The
  list comes from local durable state and makes no network calls.
- `groupRecoveryStatus` sets `historyMayBeIncomplete` and lists the group's own
  `historyNoticeIds`. Show a banner in that conversation. Show account-wide
  notices on an account-level surface.
- `MarmotEventFfi.HistoryNoticesChanged` fires when a notice appears, disappears
  (because new evidence re-armed recovery or the user dismissed it) or is
  replaced. Re-read the list. A group whose own notices changed also receives
  `GroupStateUpdated`.
- `dismissHistoryNotice(accountRef, noticeId)` records the user's decision
  durably, as its own outcome and never as recovered history. It runs on the
  account worker, in order with other mutations, with no network I/O. It returns
  `false` for a stale id; in that case re-read the list and show the current
  notices. A malformed id is `InvalidHex`. When no loss recovery remains pending,
  dismissing a delivery- or notification-loss notice releases the transport-cursor
  fence.

Do not dismiss on the user's behalf. Do not persist `noticeId` as a group or
account identity, because it changes whenever recovery re-arms. A dismissed
occurrence does not come back, but new evidence can raise a new notice: new loss,
a higher missing epoch, a later startup's incremental comparison or a new explicit
repair. Notices carry no relay, message or key identities; keep them out of
analytics. Localize the wording in the host.

Illustrative host flow (generated naming can vary by language toolchain):

```swift
func refreshNotices() async throws {
    let notices = try await marmot.historyNotices(accountRef: account)
    showHistoryBanner(notices)            // account-level and per-group surfaces
}
// On MarmotEventFfi.historyNoticesChanged(accountIdHex:accountLabel:)
try await refreshNotices()
// When the user taps "Dismiss":
let dismissed = try await marmot.dismissHistoryNotice(accountRef: account, noticeId: id)
if !dismissed {
    try await refreshNotices()            // stale id: show the current list
}
```

```kotlin
suspend fun refreshNotices() = showHistoryBanner(marmot.historyNotices(account))
// On MarmotEventFfi.HistoryNoticesChanged:
refreshNotices()
// When the user taps "Dismiss":
if (!marmot.dismissHistoryNotice(account, id)) refreshNotices()
```

In C, `marmot_history_notices(client, account_ref, &list)` returns an owned
`MarmotHistoryNoticeList`. Free the root with `marmot_history_notice_list_free`
only; `group_id_hex` is NULL for an account-wide occurrence, and `parked_at_ms` is
meaningful only when `has_parked_at_ms` is set.
`marmot_dismiss_history_notice(client, account_ref, notice_id, &out)` writes
`false` for a stale id. Both calls block on the account worker; keep them off the
UI thread. The CLI reports the same state in
`wn groups recovery-status --json` as `history_may_be_incomplete` and
`history_notice_ids`. See
[History may be incomplete notices](../../crates/marmot-uniffi/README.md#history-may-be-incomplete-notices).

## Account recovery v2 defaults

These behaviors change without new calls. Hosts need to know them to explain
network use and status.

- **Completion requires comparison certificates.** Delivery and notification loss,
  incremental history, explicit repair and epoch gaps complete on comparison
  certificates. A scope certifies only when every required relay finishes an
  untruncated NIP-77 comparison over a window that covers the scope's whole goal,
  and every difference has been admitted. A relay whose compared set fills the
  request limit counts as truncated. A goal with no known lower bound never
  certifies. Cold-start and incremental history compare the retained 30-day
  inventory window. Three causes have other production endings:
  - An epoch-gap obligation is also deleted, with no certificate, once the
    group's local epoch moves past the stalled epoch. A later stall arms a new
    gap at its own epoch.
  - A post-join maintenance boundary completes when its own REQ, installed by the
    comparison job, reaches end of stored events. Comparison certificates do not
    settle it.
  - Known-event demand completes once that exact event is retained. It currently
    has no production producer (see the known limitations below).
- **Operated relays.** A route certifies on its operated relays only. By default
  these are `wss://relay.eu.whitenoise.chat` and `wss://relay.us.whitenoise.chat`.
  A route that lists neither still certifies on all of the relays recovery can dial.
  Other relays are still compared and their events admitted, but their failures do
  not withhold completion. Rust hosts can change the set with
  `MarmotAppConfig::recovery_operated_relays`; changing it rebuilds pending
  recovery scopes. The bindings and CLI do not expose this setting.
- **Parking.** An obligation parks once every route it still cannot certify has
  been compared three times in a row for its goal, with its required relays
  answering, and nothing was admitted or certified. A comparison whose required
  relay failed or timed out does not count toward that, and neither does a route
  that no comparison backend could compare: it is recorded as unserved and spends
  none of the parking budget.
- **One execution path.** Comparison runs off the account worker. The worker then
  admits what the comparison fetched, a few events per turn, between commands and
  live input. Recovery reuses the live subscriptions instead of re-subscribing, so
  it no longer replays history the account already holds. Explicit catch-up (and,
  for Rust hosts, `sync()` and a directly owned client's `next_event()`) drains the
  live queue and then runs one comparison job in place. It no longer re-activates
  transport once the session is active; a route change still refreshes it.
- **Durable spill.** A full account delivery queue spills deliveries into the
  account database instead of dropping them, up to 8,192 rows or 16 MiB per account.
  A delivery still becomes queue loss when the router hand-off (4,096 deliveries or
  4 MiB) or the spill limits are exceeded, when its spill write keeps failing, when
  its row cannot be decoded, or when it is still unadmitted after 8 retries.
  `RelayPlaneHealth` reports `account_delivery_spilled` and
  `account_delivery_spill_already_seen`.
- **Live cursor promotion.** A live delivery promotes the persisted transport
  cursor once every account subscription has replayed its stored history and no
  loss is pending. A restart therefore no longer re-downloads what arrived live
  since the last drain.
- **History floors.** The post-join maintenance REQ starts 15 minutes before the
  creation of the Welcome that installed the group copy, not full history. A
  retained route's REQ starts 15 minutes before the moment the device saw that route
  replaced, and no later than the account cursor. A group hidden when its route was
  replaced keeps a full backfill until it is restored.
- **Notification lag.** A lag in the relay notification consumer no longer closes
  the account route or sends the worker into reconnect. The lag is recorded
  durably as bounded loss and recovered by comparison. An end-of-stored-events
  (EOSE) notification lost in a lag is repaired after the receiver has gone 30
  seconds without another lag. It is recorded from the SDK when the relay's EOSE
  already arrived. Otherwise the REQ is re-issued unchanged under its own id.

## Rust host changes

- `MarmotAppConfig` removes `dev_epoch_backfill_eose_wait_ms` and
  `dev_epoch_backfill_execution_quantum_ms` with their `with_*` builders. Neither
  had an effect under the comparison job. It adds `recovery_operated_relays` with
  `with_recovery_operated_relays`. Full struct literals must set it or use
  `Default`.
- `AppPriorNostrRoute` gains `replaced_at` (serde-defaulted), and struct literals
  must set it.
- `GroupRecoveryStatus` gains `history_may_be_incomplete` and
  `history_notice_ids`, and `MarmotAppEvent` gains `HistoryNoticesChanged`. Both
  fields are serde-defaulted. `MarmotAppRuntime::history_notices` and
  `dismiss_history_notice` mirror the binding methods.
- `repair_full_history` compares every route over the retained-inventory window in
  one pass inside a 60-second budget. It never reports complete, because full
  history has no lower bound. When every route's window certified, it returns
  `FullHistoryRepairIncompleteReason::BelowRetentionWindow`
  (`full_history_below_retention_window`) and closes its request without leaving
  debt or a notice. Otherwise it returns `CoverageUnproven`, `Cancelled` or
  `Deadline`. `FullHistoryRepairIncompleteReason` is new since 0.10.4; exhaustive
  matches must handle every variant.
- `HostPerformanceOperation` and `RuntimePerformanceOperation` gain the new host
  stages.
- `nostr` and `nostr-sdk` now come from the pinned fork
  `github.com/erskingardner/rust-nostr` at
  `a9c7a6423d104c603de6ea8244265ea17f0f9d89`, where 0.10.4 used crates.io 0.44.
  Rust hosts that share these types with MDK must resolve the same revision.
  `NostrRelayClient` gains `reissue_subscription` and
  `subscription_eose_received`, both unsupported by default.
- `storage-sqlite` adds `stamp_unrecorded_prior_route_switches`,
  `checkpoint_recovery_comparison`, the parked-obligation and spill APIs, and
  `StoredNostrRoute::replaced_at`. See the crate changelog.

## Optional adoption

### Edits of a pending local send

`editLocalMessageWithClientToken(accountRef, groupIdHex, originalClientToken,
content, editClientToken)` durably queues a revision of a token-aware text or
reply whose original has not settled yet. Give each submitted revision its own
edit token. The call returns local acceptance, not delivery. Follow the edit token
with `localSendStatus`. The edit publishes only after the original is engine-owned,
and it becomes `Rejected` if the original was rejected. Rapid revisions receive
strictly increasing edit times. An edit that would move more than 30 seconds ahead
of the clock fails with `InvalidAppMessagePayload` (`pending edit rate limit: retry
shortly`); keep the text and retry later with a new token. In C, use
`marmot_edit_local_message_with_client_token` with the existing local-send status
and free functions. See
[pending edits](../../crates/marmot-uniffi/LOCAL-SENDS.md#edits-of-a-pending-local-send-0110).

### Encrypted NIP-88 polls

`createPoll(accountRef, groupIdHex, question, options, pollType, endsAt)` takes 2–10
options and an optional deadline at most 30 days out.
`castPollVote(accountRef, groupIdHex, pollEventId, optionIds)` sends a complete
replacement selection. Timeline rows expose `poll` with counts, participants, the
local selection and whether the poll is open. Use option ids from the projection,
not labels. Polls are neither anonymous nor election-grade. C uses
`marmot_create_poll` and `marmot_cast_poll_vote`. See
[Polls](../../crates/marmot-uniffi/POLLS.md).

### Other additions

- `verifyPublicNostrEventJson(eventJson)` / `marmot_verify_public_nostr_event_json`
  checks a canonical Nostr event id and signature with no client state.
- `record_host_performance` accepts 28 shared host stages and nine Linux-specific
  stages. Read them through `runtime_operations`; the snapshot layout is unchanged.
- `setAuditOtlpConfigV5` installs or removes an in-memory v5 OTLP audit
  destination: a stable destination identity, an HTTPS `/v1/logs` endpoint and a
  bearer token. The token is never returned or persisted.
  `postAuditLogTrackerUpdateV5` runs an immediate tracker pass and reports v4 and v5
  outcomes separately. With audit recording enabled, the runtime writes native v5
  JSONL to its own file next to the unchanged v4 file. A host configured only for
  the v4 whole-file route keeps v5 evidence locally, because that endpoint rejects
  it. C uses `marmot_set_audit_otlp_config_v5` and
  `marmot_post_audit_log_tracker_update_v5`.
- With v5 audit recording and a v5 destination, account recovery writes six
  v5-only event kinds: `recovery_need_changed`, `recovery_attempt_started`,
  `recovery_attempt_finished`, `recovery_obligation_reassessed`,
  `transport_cursor_advanced` and `subscription_eose_repaired`. They record need
  and notice changes, each recovery attempt and its outcome, the owner's verdict on
  each obligation, cursor moves and lost-EOSE repair passes. Rows carry enums,
  aggregate counts and hashed obligation and endpoint references only; no relay URL,
  account, group or message id. A v4 recorder drops these kinds, so v4 files stay
  valid against the frozen v4 schema. Hosts that already enable v5 audit need a
  receiver that accepts these kinds; no new host call is required. See
  [account recovery owner rows](../marmot-architecture/audit-logging.md#account-recovery-owner-rows-v5-only).


## WN Agent and integrations

- **OpenClaw sender policy (required).** OpenClaw Marmot enforces an
  account-global inbound sender ACL before queueing, onboarding or agent-turn
  admission. Configure `channels.marmot.senderPolicy` (`allowedUsers`, or
  `allowAll: true`) or the Hermes-compatible `MARMOT_ALLOWED_USERS` /
  `MARMOT_ALLOW_ALL_USERS` environment fallback. `dm.allowFrom` still governs
  welcomer and invite admission only. A missing or invalid policy fails closed and
  the channel is not reported healthy. Reinstalling preserves an existing
  `senderPolicy`, and the installer does not copy `--allow-welcomer` into it. See the
  [OpenClaw guide](../../integrations/openclaw/marmot/README.md).
- **Hermes presence reactions (optional).** Set
  `platforms.marmot.extra.presence_reactions: true` to show accepted, thinking, tool
  and outcome reactions. They are off by default and require sender authorization.
- **Codex attachments.** Codex turns accept validated text, source, PDF, audio and
  archive attachments as staged files. Images still use native `--image`.
  Attachment downloads may run up to 16 minutes, while other control requests keep
  the short timeout.
- **Installers.** Install only from the immutable `wn-agent-v0.11.0` release with
  sibling `.sha256` verification. The `wn-agent-latest` alias is no longer created
  or advertised. See the [integrations quickstart](../../integrations/README.md).
- The agent control protocol is unchanged from 0.10.4.

## Changes requiring no new calls

- Generated identities and later relay-list or profile edits copy signed kind
  10002, 10050 and 0 records to the built-in public directory indexers after the
  account relays acknowledge them. Indexer latency does not delay readiness or edit
  returns. Development accounts on loopback relays skip these writes.
- Choosing recommended relays during onboarding appends missing defaults to an
  imported identity's relay list instead of replacing it. A mixed-health existing
  declaration passes onboarding when its safe routes answer.
- Group relay lists that contain onion, unsafe or malformed endpoints no longer
  fail account activation; those endpoints are skipped.
- Group publishes release MLS confirmation and Welcomes once the relay quorum
  acknowledges them, instead of waiting for every relay. Unfinished targets retry.
- Relay notification lag no longer strands the account worker in reconnect
  backoff with `transport_closed`. A worker reopen retires the prior SDK context,
  and a failed account worker no longer tears down a ready sibling. Failed workers
  retry with backoff from 1 to 60 seconds.
- KeyPackage publication and rotation reuse the live activation instead of
  resubscribing to full history.
- Chat-list and conversation-window commands quoting a sequence replaced only by a
  background content change now apply to the current window. The command no longer
  livelocks on `StaleWindow`. An older visible-anchor quote naming a row that a
  background replacement dropped still reports a stale window.
- Account setup and onboarding reads no longer fail with a JSON parse error while
  a setup file is being replaced.
- Profile `about` text keeps normalized line breaks.
- Account-scoped relay publishes are counted in the device-wide publish counters,
  with cancellations reported separately.
- Group roster reads no longer persist a removal classification. Engine fixes cover
  commit epoch storage, deferred-peel retry budgets, removed-copy maintenance and
  backlog replay cost.

## Acceptance and remaining work

Compile matched artifacts, then exercise these consuming-app checks:

- Upgrade and reopen databases from 0.10.4, including an account with a 0.10.4
  overflow marker, a group reported as `automatic_recovery_failed`, and a group with
  a retained prior route. Verify that the notice appears and can be dismissed, and
  that the group warning stays until authenticated peer recovery or a rejoin, not
  merely until time passes. Verify that the prior binary refuses
  the upgraded database before reading application tables.
- History notices: account-level and per-group presentation, the
  `HistoryNoticesChanged` refresh, dismissal, a stale-id `false`, re-arming by new
  evidence, and cold start with an existing notice.
- Large-backlog catch-up and restart: no reconnect loop on notification lag,
  restart after live receipt without a full re-download, and a spill under load.
- Pending-send edits across restart, original rejection and the rate-limit path;
  poll creation, votes, deadlines and reclassification.
- OpenClaw with a missing, invalid, allow-list and allow-all sender policy;
  Hermes presence reactions on and off; Codex non-image attachments and slow
  downloads.
- Android 16 KB page-size validation in the consuming app bundle; Apple
  privacy-resource delivery; C deep-free paths for the changed records.

Source tests, generated binding checks and packaged artifact validation are
separate from consuming-app archives, real-device measurements, live connector
deployment and store acceptance. This guide claims none of those later stages.

Known limitations:

- [#2086](https://github.com/marmot-protocol/mdk/issues/2086): during a large
  catch-up, a member can advance its MLS epoch more than five epochs
  (`max_past_epochs`) past application messages it has not downloaded yet. Those
  messages then cannot be decrypted. They stay deferred, count as admitted, and
  raise no history notice. The failure is intermittent and was already present
  before recovery v2.
- `HistoryNoticeCauseFfi::KnownEvent` currently has no production producer
  ([#2082](https://github.com/marmot-protocol/mdk/issues/2082)). Handle it anyway.
- `FullHistoryRepairIncompleteReason::NoRelayEose` and `EoseTimeout` are no longer
  produced and are planned for removal in a later breaking release
  ([#2083](https://github.com/marmot-protocol/mdk/issues/2083)).
- Cleanup follow-ups with no client impact:
  [#2084](https://github.com/marmot-protocol/mdk/issues/2084) (an unread stored
  comparison-plan field) and
  [#2085](https://github.com/marmot-protocol/mdk/issues/2085) (tightening the
  upgrade fixture test).
- Apple required-reason and SDK-signing work remains tracked in
  [#1874](https://github.com/marmot-protocol/mdk/issues/1874).
