# Upgrading MDK 0.15.0 → 0.16.0

## Scope and provenance

This guide compares `v0.15.0` / `marmotkit-v0.15.0` / `marmotc-v0.15.0` /
`wn-agent-v0.15.0`, which all peel to
`827687ba7fdbb05ec1b8f17667ad919fedde7266`, with the source to be shipped as
`v0.16.0`. All four 0.16.0 cohort tags must peel to the release PR's merged
commit, and packaged manifests must record that exact SHA. The comparison was
prepared against `origin/master` at `4a05edb354b8184e3b6a2d0f78e313c926a77298`
(72 commits after `v0.15.0`); the release commit is this documentation update's
merge on top of it. Use the full release SHA from the tags for artifact
verification. This guide ships in the release commit, not a later supplement.
See the [release notes](../release/0.16.0.md), [previous upgrade guide](0.15.0.md),
and [current binding reference](../../crates/marmot-uniffi/README.md).

Readers: native app hosts (Swift/Kotlin through MarmotKit), C hosts, Rust hosts
that embed `marmot-app` or lower crates, and WN Agent operators.

This is a smaller release than 0.15.0. It adds one `MarmotKitError` case
(`Nip46`), no `MarmotEventFfi` case and no C status, and it does not migrate
account databases. The wire format and conformance vectors are unchanged apart
from their version stamp. What changes on the wire is where events go: MDK now
withholds an event from a relay known to refuse it for size.

OpenMLS moves from the `erskingardner/openmls` fork to upstream `main`, which
carries the security fixes released in OpenMLS 0.9.1 and 0.9.2 (see
[Changes requiring no new calls](#changes-requiring-no-new-calls)). Stored
groups load unchanged, signed leaves are identical, and members on 0.15.0 and
0.16.0 interoperate.

## Required upgrade steps

1. Pin all MDK, MarmotKit, Marmot C and WN Agent inputs to 0.16.0. Verify the
   source SHA in each manifest and every sibling checksum. Do not combine new
   generated records or headers with 0.15.0 native libraries. See the
   [distribution guide](../../crates/marmot-uniffi/DISTRIBUTION.md).
2. Handle the new quarantine reason. `AppGroupHydrationQuarantineReasonFfi`
   gains `REWIND_RESTORE_FAILED` (Swift `.rewindRestoreFailed`; C
   `MARMOT_APP_GROUP_HYDRATION_QUARANTINE_REASON_REWIND_RESTORE_FAILED`). It
   arrives through `quarantinedGroups` and the
   `GroupEventKindFfi.groupHydrationQuarantined(reason:)` event. A read of past
   group state rewound the group onto a retained anchor and could not restore
   it. Do not offer Retry or Rejoin for it: `retryHydrateQuarantinedGroup`
   returns `false`, `groupRecoveryStatus` lists no `rejoinInvitations` for the
   group, and `confirmGroupRejoin` fails as `MarmotKitError.UnknownGroup`. The
   next account open tries to restore the live state and replays the retained
   input only if that succeeds; if it fails, the group is quarantined again for
   the same reason. Tell the user to reopen the account or restart the app, and
   keep treating the group as quarantined until the quarantined-groups read no
   longer lists it. A group with two
   interrupted rewinds, which used to report `GROUP_RECORD_LOAD_FAILED`, now
   reports this reason.
3. Update `QueuedIntentRefused` handling.
   `GroupEventKindFfi.queuedIntentRefused(intentIdHex:intentKind:reason:artifact:sizeClass:)`
   adds `artifact: OversizedArtifactFfi?` and `sizeClass: EventSizeClassFfi?`.
   Both are set only when `reason` is `event_too_large`; `.commit` means the
   change itself is too large for every group relay, `.welcome` that every
   inbox relay of the invitee refuses its Welcome. Positional Swift `case`
   patterns, Kotlin constructors and Kotlin destructuring declarations add the
   two fields. C: `MarmotGroupEventKind_QueuedIntentRefused_Body` appends
   `char *artifact` (NULL for other reasons; freed with the event),
   `bool has_size_class` and `enum MarmotEventSizeClass size_class`.
4. Expect `EventTooLarge` in more places. When every relay refuses the event
   for size, by its own answer or over its known limit:

   | Call | 0.15.0 | 0.16.0 |
   | --- | --- | --- |
   | `rotateKeyPackage`, `republishKeyPackage`, account setup's KeyPackage publish | `Runtime` / `MARMOT_STATUS_RUNTIME` | `EventTooLarge { artifact: .other }` / `MARMOT_STATUS_EVENT_TOO_LARGE` |
   | `blockUser`, `unblockUser` | `BlockListUnavailable` / `MARMOT_STATUS_BLOCK_LIST_UNAVAILABLE` | `EventTooLarge { artifact: .other }` / `MARMOT_STATUS_EVENT_TOO_LARGE` |
   | `syncStickerPacks` | `StickerNetwork` / `MARMOT_STATUS_STICKER_NETWORK` | `EventTooLarge { artifact: .other }` / `MARMOT_STATUS_EVENT_TOO_LARGE` |
   | profile, follow-list and relay-list publishes over a known limit | sent, then refused by the relay | `EventTooLarge { artifact: .other }` / `MARMOT_STATUS_EVENT_TOO_LARGE`, sent nowhere |
   | group create or invite whose Welcome fits none of an invitee's inbox relays | create succeeded with the Welcome owed | `EventTooLarge { artifact: .welcome }`, nothing created or sent |

   A block edit retried after an uncertain attempt still fails as
   `BlockPublicationUncertain`, and a sticker install or uninstall still
   succeeds with its list owed to the next sync. `MarmotKitError` already had
   `EventTooLarge` in 0.15.0; only where it is raised changes.
5. Handle `MarmotKitError.Nip46(reason:)` (Kotlin `MarmotKitException.Nip46`)
   in exhaustive error switches. It carries a NIP-46 session failure's typed
   `Nip46ErrorFfi` reason.
6. Swift: if your app defines its own `nextCancellable()` extensions on
   `PresentedChatListSubscription`, `ChatListWindowSubscription`,
   `AccountAttentionSubscription`, `ConversationWindowSubscription` or
   `BlockListSubscription` (White Noise iOS's `CancellablePresentedChatList.swift`),
   delete them. The 0.16.0 Swift asset defines the same methods, and Swift
   rejects the duplicates. See
   [Swift subscription cancellation](#swift-subscription-cancellation-optional).
7. C hosts with NIP-46 accounts: apply [NIP-46 for C hosts](#nip-46-for-c-hosts).
8. Let storage upgrade. See [Storage upgrade](#storage-upgrade).
9. Rust hosts: apply [Rust host changes](#rust-host-changes).
10. WN Agent: upgrade `wn-agent` and its plugins or harnesses together.

## Storage upgrade

Account databases are not migrated; their schema is the same as 0.15.0.

The shared database (`shared.sqlite3`) runs migration 0004
(`0004_audit_log_retention`) on first open, adding the
`audit_log_retention_settings` table and moving it from schema 3 to 4. It is a
single small table creation. A 0.15.0 binary then refuses the shared database
with `StorageError::UnsupportedSchemaVersion { found: 4, latest_supported: 3 }`.

The local v5 audit delivery cursor (`local-delivery.json`) moves from version
1 to version 2 on load, storing idle sealed segments as compact rows; a 0.15.0
binary refuses a version-2 cursor as incompatible. A new
`audit-otlp-delivery-v5/delivery-status.json` file records each attempt's
outcome.

Downgrade to 0.15.0 is unsupported. If you may need to roll back, keep a
device-local copy of the MDK data directory taken before upgrading while the
app and every extension (such as a notification extension) are stopped, so no
database or its WAL file is open while it is copied. Never remove migration
rows by hand. See the
[storage-format contract](../marmot-architecture/storage-format-v2.md).

## Changed defaults

### Relay event size limits

MDK now refuses to send an event to a relay that is known to refuse it for
size. A relay's limit is known when:

- the deployment lists it (`MarmotDeploymentFfi.relayEventLimits`, C
  `marmot_deployment_set_relay_event_limits`, Rust
  `MarmotDeployment::relay_event_limits`);
- the preset sets it: `marmot_deployment_white_noise()` sets 2 MiB on
  `wss://relay.eu.whitenoise.chat` and `wss://relay.us.whitenoise.chat`;
  `marmot_deployment_neutral()` sets none; or
- for events over 64 KiB, the relay's NIP-11 document advertises
  `limitation.max_message_length`. MDK subtracts the `["EVENT",…]` framing and
  applies it under every deployment, taking the smaller of this and any listed
  limit.

A relay with no known limit is sent to as before. The effects:

- A commit that fits none of its group relays fails as `EventTooLarge` and is
  rolled back with nothing sent. A Welcome-carrying invite staged at once
  whose Welcome fits none of the invitee's inbox relays is rolled back the same
  way.
- A group create whose founding Welcome fits none of an invitee's inbox relays
  fails as `EventTooLarge { artifact: .welcome }` before anything is created.
  For scale, a founding Welcome gift wrap fits under 64 KiB with up to 40
  members (about 55 KB); with 41 it is about 66 KB.
- A send queued behind an unsettled group whose commit every group relay
  refuses for size, or whose Welcome fits none of the invitee's inbox relays,
  is retired when the group settles and announced as `QueuedIntentRefused`
  with reason `event_too_large`. It is not retried.
- Every other account-signed event (profile, follow and relay lists,
  KeyPackages, block list, stickers, backup pointer) goes only to the relays it
  fits, and nowhere when it fits none.

Every event the account publishes through its relay plane, including sibling
Welcomes and Welcome-carrying recovery and own-device commits, is withheld from
a relay over its known limit. Two gaps remain in this release:

- Push-trigger gift wraps go out through an anonymous publisher that does not
  consult known limits.
- Sibling Welcomes, chosen-id device-group creates and recovery or own-device
  commits skip the up-front check that refuses a create or invite before
  anything is written. Such a change can be committed locally and its Welcome
  then withheld from every relay over its limit, rather than refused with
  `EventTooLarge`.

### Audit log retention and delivery

- Local audit files now have a per-account size budget, 256 MiB by default.
  Above it, retention deletes the oldest sealed segments that v5 delivery
  accepted or will never send (no v5 cursor, v4 or another identity's files,
  or lost to cursor overflow). Undelivered data is deleted only by age or an
  explicit clear. The age limit stays 30 days, now settable from 1 to 30.
  Deleting undelivered data by age records an `ExpiredUndelivered` gap.
- v5 delivery now retries `409`. A `400`, `413` or `422` halves the batch and
  retries the halves; a record is skipped, with a `ReceiverRejected` gap, only
  if the receiver still rejects it alone. A `401`, `403`, `404`, another unexpected status or an
  invalid success response pauses automatic delivery for that account; the
  pause survives restarts with the same configuration. Changing the
  destination, endpoint or token, or calling `postAuditLogTrackerUpdateV5()`,
  lifts it. A host that fixes its receiver without changing the token must
  make that call.
- A relay replay that ingest ignores as a duplicate or own echo now writes only
  its `ingest_outcome` audit row (previously about 6 KB per message).
- Audit v5 records a relay's size refusal as `relay_rejected_invalid` again
  (0.15.0 wrote `unclassified`), and a relay MDK did not send to because of a
  known limit as `publish_attempt_failed_before_exposure`, as it does for a
  relay the host-safety rule refuses. A group with a failed rewind restore
  reports the failure category `rewind_restore_failed`.

### Other defaults

- `start_direct_conversation` makes both accounts founding admins of a new
  direct chat. `create_group` keeps creator-only admins, and existing groups
  keep their roles.
- `sign_out`, `sign_out_and_wipe` and `remove_account` first stop any
  generated-setup attempt in flight for that account, and `sign_in_account`
  resumes a generated setup that its sign-out stopped.
- The recovery runner's per-account breaker rises from 720 to 7,200 quanta an
  hour; the 256 MiB/hour event-byte cap is unchanged. The engine's
  deferred-peel caps rise from 2,048 rows and 16 MiB to 8,192 rows and 64 MiB
  per group, and from 64 MiB to 256 MiB per account.
- Directory fetches run up to four independent queries at a time; each still
  waits up to its usual per-relay timeout.
- `uploadMediaWithClientToken` and `uploadMediaFilesWithClientToken` with
  `send = true` keep the reply target named by the request's `e` or `q`
  `messageTags` through upload and durable admission; before, the sent message
  lost its reply tags. Reply references with a missing, malformed or
  conflicting target now fail before any upload. Calls with `send = false` are
  unchanged.

## Feature adoption

Examples are illustrative; check them against the generated sources of the
artifacts you ship.

### Deployment relay limits (optional)

List limits for relays you operate that do not advertise one:

```swift
var deployment = marmotDeploymentWhiteNoise()
deployment.relayEventLimits.append(
    RelayEventLimitFfi(relay: "wss://relay.example.com", maxEventBytes: 1_048_576))
```

```kotlin
val base = marmotDeploymentWhiteNoise()
val deployment = base.copy(
    relayEventLimits = base.relayEventLimits +
        RelayEventLimitFfi(relay = "wss://relay.example.com", maxEventBytes = 1_048_576uL))
```

C: `marmot_deployment_set_relay_event_limits(deployment, relays,
max_event_bytes, len)` replaces the list, with `relays[i]` taking
`max_event_bytes[i]`. Blank relays and zero limits are ignored; a relay listed
twice keeps the smaller limit.

### Direct chats (optional)

`startDirectConversation(accountRef:peerAccountId:)` takes a hex or npub peer
and returns the MLS group id as hex. It reuses this account's direct chat with
that peer, or creates an unnamed group with both accounts as founding admins.
Lookup and creation run together on the account worker, so retrying with the
same arguments after a cancellation, a lost response or an error reuses the
canonical group; it also restores a missing chat-list row for that peer and
announces it. Cancelling the Swift/Kotlin call detaches the wait but does not
cancel creation. Success means local state is canonical, not that the Welcome
was delivered; check `pendingWelcomeDeliveries` for that. Starting a chat with
yourself fails as `MarmotKitError.Runtime`.

```swift
let groupIdHex = try await kit.startDirectConversation(
    accountRef: account, peerAccountId: npub)
```

```kotlin
val groupIdHex = marmot.startDirectConversation(account, npub)
```

C: `marmot_start_direct_chat(client, account_ref, peer_account_id, &out)`;
free `*out` with `marmot_string_free`. A self-peer returns
`MARMOT_STATUS_RUNTIME`.

### Relay liveness (optional)

For a relay settings screen. Each row is a relay configured for the account
(default, bootstrap, NIP-65 and inbox relays, canonicalized) with `url`,
`status` (`RelayStatusFfi`: `.unknown`, `.connecting`, `.connected`,
`.offline`), `lastAttemptUnix: UInt64?` and `lastError: String?` (the SDK's
connection-error category). Reads never dial; a relay not yet observed is
`.unknown`. Aggregate `relayHealth` is unchanged.

```swift
// When the screen appears:
let sub = try await kit.subscribeRelayLiveness(accountRef: account)
self.rows = sub.snapshot()                  // first list, returned once
self.watch = Task {
    while let rows = try await sub.next() { // later complete lists; may skip some
        self.rows = rows
    }                                       // nil after cancel() or shutdown
}

// "Reconnect" button for a row:
let updated = try await kit.reconnectRelay(accountRef: account, url: row.url)

// When the screen closes:
sub.cancel()                                // wakes next() with nil; does not disconnect relays
```

Kotlin, with the subscription's handle released by the generated `close()`:

```kotlin
// When the screen appears (in a lifecycle-bound scope):
val sub = marmot.subscribeRelayLiveness(account)
rows = sub.snapshot()
watch = scope.launch {
    while (true) {
        rows = sub.next() ?: break          // null after cancel() or shutdown
    }
}

// "Reconnect" button for a row:
val updated = marmot.reconnectRelay(account, row.url)

// When the screen closes:
sub.cancel()                                // does not disconnect relays
watch.join()
sub.close()                                 // release the native handle
```

`accountRelayLiveness(accountRef:)` returns one list without subscribing.
`reconnectRelay` dials only a relay the account has configured, through the
account pool's dial checks, and keeps that relay's roles; any other URL fails
as `MarmotKitError.Runtime`.

C: `marmot_account_relay_liveness` returns a `MarmotRelayLivenessList` (free
with `marmot_relay_liveness_list_free`); `marmot_reconnect_relay` returns a
`MarmotRelayLiveness` (free with `marmot_relay_liveness_free`).
`marmot_subscribe_relay_liveness` returns a `MarmotRelayLivenessSubscription`:
call `marmot_relay_liveness_subscription_snapshot` once, then either
`marmot_relay_liveness_subscription_next` (`timeout_ms` 0 waits forever) or
`marmot_relay_liveness_subscription_set_callback` (the list is borrowed for the
callback; a NULL list with `MARMOT_STATUS_CLOSED` or an error status ends it),
not both. Finish with `marmot_relay_liveness_subscription_cancel` and
`marmot_relay_liveness_subscription_free`, before freeing the client.
`marmot_relay_liveness_subscription_clear_callback` and `_free` request callback
cancellation without waiting for a callback that is already running, and no
terminal callback is guaranteed after a clear. A callback can still start
after either call returns, so keep `user_data` alive until no callback is
running or can still start; if you cannot establish that, keep it for the
process lifetime.

### Audit delivery status (optional)

`auditDeliveryStatusV5()` returns one `AuditDeliveryStatusV5Ffi` per account so
a host can show "audit delivery stalled since X" and offer a fix. It reads
local files only and never dials. Fields: `accountRef`,
`destinationConfigured`, `lastSuccessAtMs: UInt64?`,
`lastFailure: AuditDeliveryFailureV5Ffi?` (`kind`, `httpStatus: UInt16?`,
`atMs`), `consecutiveFailures`, `rejectedBatches` (records skipped after a
rejection), `paused`, and `backlog: AuditDeliveryBacklogV5Ffi?`
(`undeliveredBytes`, `undeliveredSegments`, `gaps`, `oldestUndeliveredAtMs`,
`observedAtMs`). `AuditDeliveryFailureKindV5Ffi` separates local failures
(`.stateOverLimit`, `.tooManyOpenFiles`, `.localIo`, `.localBlocked`) from
receiver verdicts (`.receiverBlocked`, `.receiverRejected`,
`.receiverRetryable`) and `.noResponse` / `.internal`.

When `paused` is true, fix the configuration and call
`setAuditOtlpConfigV5` with the corrected destination, endpoint or token, or
call `postAuditLogTrackerUpdateV5()`.

C: `marmot_audit_delivery_status_v5(client, &list)`; free the list with
`marmot_audit_delivery_status_v5_list_free`. Enum values are
`MARMOT_AUDIT_DELIVERY_FAILURE_KIND_V5_*`; `has_http_status` guards
`http_status`.

### Audit retention (optional)

`auditLogRetention()` and `setAuditLogRetention(retention:)` are synchronous
and take or return `AuditLogRetentionFfi { maxAgeDays: UInt32,
maxBytesPerAccount: UInt64 }`. The setter persists the policy, clamps
`maxAgeDays` to 1–30 and `maxBytesPerAccount` to at least 16 MiB, returns the
stored value, and asks the running app to sweep shortly after.

```swift
let stored = try kit.setAuditLogRetention(
    retention: AuditLogRetentionFfi(maxAgeDays: 14, maxBytesPerAccount: 64 << 20))
```

```kotlin
val stored = marmot.setAuditLogRetention(
    AuditLogRetentionFfi(maxAgeDays = 14u, maxBytesPerAccount = 64uL shl 20))
```

C: `marmot_audit_log_retention(client, &out)` and
`marmot_set_audit_log_retention(client, &retention, &out)`; free `out` with
`marmot_audit_log_retention_free`.

### Read-queue latency (optional)

`appPerformanceSnapshot().runtimeOperations` gains 17 rows that time a host
read's wait on its account worker: `read_queue_r1` … `read_queue_r9` by read
class, and `read_queue_behind_*` by the long unit it waited behind (startup
sync, catch-up, convergence, Welcome fan-out, repair, send, invite or create,
maintenance). Hosts that render rows generically need no change.

### NIP-46 remote signers (optional)

Swift and Kotlin hosts can now run NIP-46 (`bunker://` and client-initiated
`nostrconnect://`) accounts through MDK, sharing one session implementation
with C. MDK owns each account's signer transport and communication key and
keeps no host signer callback; host NIP-55 callbacks and local-key accounts
keep their existing APIs.

1. `Marmot.nip46New(configJson:)` returns an offline `Nip46SessionFfi`.
2. Call `reviewPermissions()`, show its version and grants, and pass that exact
   snapshot to `approvePermissions(version:grants:)` only after the user
   consents. `uri` and `connect` refuse an unapproved session, and so does an
   imported export, including an old unversioned descriptor.
3. For client-initiated pairing, await `pairingOffer()` before showing its URI;
   the `uri` accessor alone does not install the relay listener. Never log
   either URI.
4. Await `connect()`, then `nip46Login(...)`. Login accepts only an already
   verified `Ready` session; it rejects any other state without connecting or
   creating an account.
5. On restart, the ordinary runtime `start` restores sessions before their
   account workers. Use `nip46Resume(accountRef:)` for the restored handle.

Cancelling `connect` or `ping` cancels that request. Once `nip46Login` or
`nip46Register` is admitted, cancelling the call only stops the wait; use the
session's `cancel`, `disconnect` or `logout` to interrupt adoption, and mind
what each leaves behind. `disconnect` keeps the same session, which can
reconnect. `cancel` is terminal for that session and its handles but keeps the
stored credentials: `nip46Resume`, or the next `start`, builds a new session
from them at once, while the old handle stays `Cancelled`. `logout` sends a bounded remote logout and erases the local
communication key, so the user must pair again. `nip46Remove`, sign-out and
wipe also erase it. `status()` returns
`Nip46StatusFfi` (state, optional `Nip46ErrorFfi`, auth URL, request id,
generation) and is a local read. Runtime calls fail as
`MarmotKitError.Nip46(reason:)`; session calls throw `Nip46ErrorFfi`. See the
[binding guide](../../crates/marmot-uniffi/README.md#nip-46-accounts) and
[external signer accounts](../external-signer-accounts.md#nip-46-sessions).

### Swift subscription cancellation (optional)

UniFFI's generated `next()` keeps waiting on the native receive after its Swift
task is cancelled. The 0.16.0 Swift asset (`MarmotKit.swift`) adds
`nextCancellable()` to `PresentedChatListSubscription`,
`ChatListWindowSubscription`, `AccountAttentionSubscription`,
`ConversationWindowSubscription` and `BlockListSubscription`. Cancelling the
task cancels the pending native receive and throws `CancellationError`; the
subscription stays open for later receives. Cancellation wins over a typed
error that completes at the same moment, and a receive that completes as the
task is cancelled can be dropped. Apps such as White Noise iOS that carry
handwritten adapters delete them (required step 6) and get MDK's tested
version. No download is added; the existing Swift asset checksum covers it.
See the [distribution guide](../../crates/marmot-uniffi/DISTRIBUTION.md) and
[API reference](../../crates/marmot-uniffi/API-REFERENCE.md#swift-cancellation-adapters).

## C host changes

- Recompile against the 0.16.0 header and library. The only change to an
  existing struct is the `QueuedIntentRefused` event body (three appended
  fields), which grows the `MarmotGroupEventKind` union.
- Appended enum values: `MARMOT_APP_GROUP_HYDRATION_QUARANTINE_REASON_REWIND_RESTORE_FAILED`.
  New enums: `MarmotRelayStatus`, `MarmotAuditDeliveryFailureKindV5`.
- New functions: `marmot_start_direct_chat`, `marmot_account_relay_liveness`,

### NIP-46 for C hosts

`marmot_nip46_*` handles now wrap the session MDK shares with Swift and Kotlin.
Existing signatures and status numbers are unchanged, but the call sequence
changes:

- Review before pairing. Call `marmot_nip46_review_grants` (JSON `version` and
  `grants`) and, after user consent, `marmot_nip46_approve_grants` with that
  exact version and grant array. `marmot_nip46_uri` and `marmot_nip46_connect`
  refuse an unapproved session. Imports, including old unversioned
  descriptors, need the same review.
- For client-initiated pairing, await `marmot_nip46_pairing_offer` on a
  background worker before showing the URI; `marmot_nip46_uri` alone does not
  install the relay listener.
- `marmot_nip46_login` requires a session `marmot_nip46_connect` already
  verified (`Ready`); otherwise it fails without connecting or creating an
  account.
- Restart. 0.15.0 hosts kept `marmot_nip46_export` in their vault and
  re-registered each export after `marmot_client_start`. MDK now persists
  verified credentials through the configured secret store and restores them
  during `marmot_client_start`; obtain the handle with `marmot_nip46_resume`.
  Import each 0.15.0 vault export once (new, review and approve, connect,
  `marmot_nip46_register`). `marmot_nip46_remove` removes the stored session
  and credentials before you attach a different one.
- `marmot_nip46_free` now releases only its C handle; an attached session
  keeps signing for its account. `marmot_nip46_cancel` permanently stops the
  shared session and every handle on it but keeps the stored credentials:
  `marmot_nip46_resume`, or the next `marmot_client_start`, builds a new
  session from them, and signing resumes. To revoke a session, use
  `marmot_nip46_logout` (bounded remote logout, then local key erasure),
  `marmot_nip46_remove`, or account sign-out or wipe. Join every borrower
  before freeing a handle.
- `marmot_nip46_state` JSON keeps its fields and adds `permission_approval`,
  `listening`, `disconnected` and `reconnecting` states plus `last_error`,
  `request_id` and `generation`. New `marmot_nip46_status` returns a typed
  `MarmotNip46Status`: `state`, `last_error` (read it only when
  `has_last_error` is true), nullable `auth_url` and `request_id`, and
  `generation`. Free the whole record with `marmot_nip46_status_free`, never
  its strings separately.
- New calls: `marmot_nip46_ping`, `marmot_nip46_disconnect` (reconnectable),
  `marmot_nip46_cancel_request`, `marmot_nip46_complete_auth`,
  `marmot_nip46_resume` and `marmot_nip46_remove`.

See the [C NIP-46 guide](../../crates/marmot-c/README.md#nip-46-accounts).

## WN Agent and integrations

- New control request `group_admin` with `account_id_hex`, `group_id_hex`,
  `member_id_hex` and optional `promote`, `add` and `remove`. With no flag it
  reads the member's status; `promote` makes a current member an admin; `add`
  invites a missing member (as an initial admin together with `promote`);
  `remove` takes precedence and removes the member in one commit. The reply
  `group_admin_status` carries a fresh `is_member`/`is_admin` readback,
  `message_ids_hex` and, when a change was sent, `accept_disposition`
  (`published`, `accepted_pending` or `completion_unknown`). Do not resend an
  `accepted_pending` or `completion_unknown` change; after an error, read the
  status before retrying. The protocol name stays `marmot.agent-control.v2`; a
  0.15.0 connector closes the socket on this request. Hermes, OpenClaw and the
  terminal harnesses do not expose it as a tool yet.
- `wn`, `wnd` and `wn-agent` use the White Noise preset, so they withhold events
  over 2 MiB from its relays. `group create`, `groups create`, `group invite`,
  `groups add-members`, `keys publish`, `keys rotate`, `create-identity`,
  `login` and the profile, follow and relay-list commands can report JSON
  `event_too_large` with `artifact` and `size_class`.
- `wn groups quarantined` can report `RewindRestoreFailed`, and
  `wn groups retry-hydrate` reports `recovered=false` for it.
- `send_media` accepts an optional `reply_to_message_id_hex` (64 hex
  characters): the caption and every ordered attachment go out as one reply
  message. A malformed target fails as `invalid_hex` before upload. Reusing a
  retained `idempotency_key` with different inputs, including a different
  reply target, fails with the new non-retryable `media_idempotency_conflict`;
  a matching retry returns the original message ids. Hermes image, document,
  video and voice sends accept `reply_to`, and multi-image sends accept
  `reply_to_message_id_hex` in their metadata; 0.15.0 refused reply-targeted
  media. The Python control client's `send_media` takes the same keyword.
  Older connectors ignore the field and send ordinary media, so upgrade the
  connector with the plugin.
- Hermes now creates inbound attachment staging private (`0700` directory,
  `0600` files) and tightens an existing staging directory before copying, and
  writes `config.yaml`, its backup and temporary files `0600` regardless of
  umask. No action is needed.
- Install pins move to `wn-agent-v0.16.0`.

## Changes requiring no new calls

- OpenMLS now carries the fixes from OpenMLS 0.9.1 and 0.9.2. A Welcome,
  GroupInfo, Proposal or Commit with deeply nested extensions could abort the
  process (GHSA-gc79-23g3-8g52); anyone can gift-wrap a Welcome to a user. A
  rejected private message could advance its sender's ratchet and block that
  sender's later messages (GHSA-p276-g3f3-wwgh). Stored groups load unchanged
  and members on 0.15.0 and 0.16.0 interoperate.
- A chat keeps receiving new messages after its account's live subscriptions
  are rebuilt. A relay's end-of-stored-events reply that arrived late held the
  group's live messages until the recovery runner answered, and nothing woke
  the runner, so the chat stayed silent until unrelated activity.
- Joining several groups in quick succession, while earlier history was still
  replaying, no longer records account-wide history loss and a re-sync.
  History the new subscription asks for again is owed to it and charged as
  lost only if it does not arrive.
- A leave that a rival branch blocked is re-driven at once: the step-down is
  staged again or the leave is reported blocked, so sign-out no longer waits
  out its 30 s leave deadline.
- A chat the account was removed from no longer wakes the account worker every
  10 ms for the life of the process.
- A delayed generated-setup handoff at startup or in the foreground no longer
  creates a replacement account after the original is wiped or removed.
- `reconnectRelay` right after a disconnect dials at once instead of waiting
  out the 5 s retry interval and failing its 5 s bound.
- A group whose deferred-peel backlog filled no longer holds its live messages
  and the account's sync cursor behind a history event the engine could neither
  open nor store; the event is let go of and the rest of the group admitted.
- Opening an account restores every group's interrupted rewind before ingest
  or a Welcome join reads the group.
- A relay the host-safety rule refuses (private or loopback address, plaintext
  `ws://`, unparseable URL) counts as never contacted: a commit every other
  relay refused rolls back instead of retrying forever, and a Welcome goes to
  the inbox list's other relays.
- A relay spelled with an upper-case host or explicit default port now
  confirms or rolls back commits; such a group used to freeze on its next
  commit.
- After a crash during a commit's send, a relay's refusal of the retry keeps
  the commit pending (possibly exposed) instead of rolling it back.
- An account event over a relay's advertised message limit
  (`limitation.max_message_length`) is no longer sent to that relay, so it is
  not exposed there and not resent. Before, the relay closed the socket, the
  event read as possibly exposed, and it was resent three times.
- Wiping or removing a generated identity whose setup was still publishing no
  longer creates a new, unrequested account.
- A `declineGroupInvite` that timed out with `AccountWorkerResponseTimedOut`, or
  was cancelled, while still queued no longer leaves the group later. A decline
  the worker had already started still completes, so after a timeout read the
  group's state before offering Accept.
- An offline account no longer repeats its full replay synchronization on every
  15 s maintenance tick.
- v5 audit delivery no longer stalls once about 3,250 segments are retained.
- An audit file a receiver's `409` blocked for good under 0.15.0 resumes
  delivery after the upgrade: loading the cursor clears that block and resends
  the file's pending range.
- Live notifications reuse settings, mutes, group records and users across
  events; mute expiry and setting changes still apply at once.

## Acceptance and remaining work

Before shipping an app on 0.16.0:

- Compile against the matched artifacts with every exhaustive `switch`/`when`
  updated; for C, rebuild every consumer.
- Upgrade a 0.15.0 install in place and confirm the shared database and audit
  cursor upgrade once and the second open changes nothing. Confirm 0.15.0
  refuses to reopen it, and that restoring the pre-upgrade copy works.
- Exercise `EventTooLarge` paths: a create and an invite against an invitee
  whose inbox relays all have a small listed limit (nothing is created or
  sent), and KeyPackage rotation, block and sticker sync against relays with
  a small limit. Confirm your UI's copy for each.
- Show a `QueuedIntentRefused` with `artifact` and `sizeClass`.
- If adopted: relay liveness across offline, reconnect, background and
  screen dismissal (`cancel`); direct-chat start with retries after
  cancellation and with an offline peer; audit status with a receiver
  returning `401` (paused, then lifted by a configuration change), `409` and
  `413`; retention changes and their clamping.
- Sign out or wipe a freshly generated identity while its setup is still
  publishing, and confirm no new account appears.
- Swift: build with the 0.16.0 asset after deleting any host-owned
  `nextCancellable()` adapters, and cancel a task waiting on each adopted
  subscription.
- NIP-46 (C, or Swift/Kotlin if adopted): approve permissions, pair, log in,
  restart and resume without a host callback; import one 0.15.0 vault export;
  sign out and confirm the communication key is erased.
- If you send media with `uploadMediaWithClientToken` or the agent-control
  `send_media`, send a reply-targeted batch and confirm receivers show it as a
  reply.
- Report evidence by stage: source, host smoke, packaged artifact, consuming
  app, real device.

What was validated: every change in this comparison landed through the merge
queue's CI matrix, and the binding-docs gate passes for the MarmotKit method and
C symbol inventories at this source. Not validated here: upgrade of a real
0.15.0 installation, relay limits against production relays, and app-level
adoption on iOS or Android.
