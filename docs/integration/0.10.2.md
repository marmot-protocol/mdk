# Integrating MDK 0.10.2

This guide covers **0.10.1 → 0.10.2** for Swift/iOS, Swift/macOS, Kotlin/Android,
C/raw FFI and Rust runtime hosts. It was added after the 0.10.2 source tag as a
documentation supplement; it is not itself present in that tagged source archive.

Source comparison: `v0.10.1` (`fcc6f67609113f9bb1547b7de0ba22c65437ccd3`) →
`v0.10.2` (`7dba6fc83eb054c6d703da182300a8e0f140eefc`). See the
[complete source comparison](https://github.com/marmot-protocol/mdk/compare/v0.10.1...v0.10.2). The short
[release notes](../release/0.10.2.md) describe the release as a whole. The
[binding README](../../crates/marmot-uniffi/README.md) and
[complete method reference](../../crates/marmot-uniffi/API-REFERENCE.md) explain the
current API; the contracts below apply specifically to 0.10.2. Names in prose are
generated Swift/Kotlin names; Rust uses snake_case and C uses its published header.

## Upgrade decisions at a glance

| Area | What changes | What the client needs to do |
| --- | --- | --- |
| Artifact compatibility | New methods, enums and record fields | Update generated sources/native binaries together; rebuild. C must pair the exact header/library. |
| Database | Account migrations 81–86 | Allow MDK to upgrade. Preserve a pre-upgrade backup/export; do not downgrade only the library. |
| Attachment acquisition | Automatic downloads now default **on**, including eligible retained history | Choose whether to keep that policy; apply host network policy before starting account work. Budget for storage/network activity even before building new UI. |
| Attachment display | Local verified byte access and progress/control APIs | Recommended adoption: render from MDK's retained bytes and expose progress/retry/remove controls. Existing `downloadMedia` remains usable. |
| Media library | Local bounded history with revision/cursor rules | Optional screen migration; use it instead of `listMedia` for new galleries. |
| Deletions/custom events | New provenance field; custom-event tags preserved | Update exhaustive switches/fixtures. Adopt localized deletion wording and custom rendering where used. |
| KeyPackages | Local inventory, explicit refresh and optional client label | Set the White Noise label at every runtime entry point; migrate settings if desired. Selection improvements themselves are automatic. |
| Diagnostics | New host milestones/outcomes and runtime operation snapshots | Update DTO/switch handling; instrument the two UI milestones to measure actual readiness. |
| Other runtime fixes | Less repeated timeline work; recovery, account initialization and diagnostics fixes | Usually no new call required; run the regression checks below. |

Upgrading does not require adopting every new screen immediately. It **does** change
default acquisition behavior. A binding build passing in MDK is not evidence that an
app integrated its controls, privacy resources, lifecycle or media cache correctly.

## 1. Install one coherent artifact cohort

Use the exact `marmotkit-v0.10.2` release for Swift/Kotlin or `marmotc-v0.10.2` for C
when its verified artifacts are available. A source tag alone is not an artifact.
Do not substitute mutable latest assets or independently generated code from master.
Verify manifest source/version metadata, sibling SHA-256 files and Apple SwiftPM
checksums. See [distribution](../../crates/marmot-uniffi/DISTRIBUTION.md) for exact
asset URLs, packaging and platform deployment requirements.

- **Apple:** update the XCFramework, shared generated Swift, and the matching platform
  privacy asset. Stage the latter as `PrivacyInfo.xcprivacy` in the Swift wrapper,
  declare `resources: [.copy("PrivacyInfo.xcprivacy")]`, and make each consuming
  app/extension depend on that wrapper. Keep required-reason/SDK-signing assessment
  separate from successful resource packaging. These are existing requirements to
  preserve, not all new APIs in this release.
- **Android:** update generated Kotlin, support sources and all shipped JNI ABIs as
  one cohort. Preserve `MarmotAndroid.initialize(context)` before first construction
  and the generated file's runtime dependencies.
- **C:** recompile against the matched header and library; new output fields change
  concrete record layouts. Use matching deep-free functions, not host allocation frees.
- **Rust:** pin the intended source/cohort and handle added public enum variants and
  record fields. No crates.io publication is implied by these source releases.

Account migrations 81–86 add attachment indexing, deletion provenance, acquisition,
worker demand, protected partials and durable controls. MDK owns migrations; clients
must not create a parallel index or edit the migration ledger. Old binaries reject
newer schemas: recovery means re-upgrade or restore a pre-upgrade database/export.
The large free-space requirement for migration 47 applies to upgrades crossing that
older boundary, **not an additional 0.10.1 → 0.10.2 table rebuild requirement**.
See [storage compatibility](../marmot-architecture/storage-format-v2.md).

### C compatibility and retry guidance corrections

Two older descriptions could mislead C integrators and are corrected by this documentation
supplement. They are corrections to guidance, not new runtime behavior:

- **Retry safety:** an invalid required output pointer is rejected before the operation
  runs. That guarantee does not cover every non-OK return. Other errors or timeouts may
  occur after a mutation records durable intent or reaches an external service. If your
  client implemented blanket retry-on-error from the old README wording, audit that logic:
  inspect authoritative operation/projection state and follow that method's retry contract
  before resending, rather than duplicating a send or other mutation.
- **ABI compatibility:** “versioned C ABI” replaces the overbroad “stable C ABI” label in
  agent instructions. The [0.10.2 C README](https://github.com/marmot-protocol/mdk/blob/v0.10.2/crates/marmot-c/README.md#binary-compatibility)
  already requires the exact matching header/library and disclaims cross-release record-layout
  compatibility. This supplement does not change that contract or any C declaration.
  Recompile clients for 0.10.2's new output fields; do not assume a shared major/minor version
  makes an older header safe with a newer binary.

## 2. Adopt retained attachment acquisition deliberately

### New default behavior

An active, non-frozen account runtime discovers and acquires eligible accepted-chat
attachments in the background, including retained history; the user need not first
open each chat. Acquisition retains the required media secrets, retries suitable
failures, and checkpoints partial ciphertext for compatible HTTP-range resume.
Only fully authenticated/decrypted/verified media is published as readable local bytes.
OS suspension still stops opportunities to work: the host must follow its platform's
background execution rules and terminally close the runtime when required.

| Default policy | Value |
| --- | --- |
| Automatic acquisition | Enabled |
| Retained attachment quota | 2 GiB per account |
| Minimum free-disk reserve | 256 MiB, plus SQLite/WAL headroom |
| Automatic ciphertext limit | 64 MiB per transfer |
| Concurrent acquisition | One across the runtime's accounts |
| Automatic transfer deadline | Two minutes |
| Explicit queued download hard limit/deadline | 512 MiB / 15 minutes |

The 64 MiB ceiling concerns ciphertext; it is not a decoder memory bound. Explicit
requests still obey disk/quota/source eligibility. There is no automatic eviction of
retained attachments to make room. Capacity pressure produces scheduled retry state;
UI should not report it as successful acquisition. The quota must be at least the
automatic transfer cap. Settings expose bytes; localize units in the host.

Pending invitations do **not** automatically or explicitly download message attachments
before acceptance. This differs from avatars, which may be acquired before acceptance.
Leaving a group preserves eligible retained history access; unavailable/deleted/expired
sources cannot be made readable by presenting an old reference.

### Policy integration

Read `attachmentDownloadPolicy(accountRef)` and modify that complete record with
`setAttachmentDownloadPolicy`. Preserve fields the settings screen does not own.
The policy is durable and account-scoped. Do not reset a user's choice to defaults
on every launch. If the host requires Wi-Fi-only or other network-specific behavior,
it owns detection and must apply `automatic=false` before starting runtime work on
a disallowed network. These APIs do not implement an OS network-class selector.

Disabling automatic acquisition cancels active automatic leases and pauses automatic
queues; it preserves partials, explicit work and retained files. Re-enabling does not
undo individual cancellations/removals. These examples show the async call shapes;
`account` must already refer to an existing account. They are not full UI controllers.

```swift
var policy = try await marmot.attachmentDownloadPolicy(accountRef: account)
policy.automatic = false
try await marmot.setAttachmentDownloadPolicy(accountRef: account, policy: policy)
```

```kotlin
val policy = marmot.attachmentDownloadPolicy(account)
marmot.setAttachmentDownloadPolicy(account, policy.copy(automatic = false))
```

### Read local media for visible rows

1. Use each original media slot's `messageIdHex`, `sourceMessageIdHex` and original
   `attachmentIndex`. Rejected slots still occupy positions in an album. A reply's
   own identity is not the identity of its quoted attachment. If the original source
   identity is unavailable, use attachment-history discovery.
2. Batch up to 64 targets **within one group** into `attachmentLocalAssets`. This is
   metadata lookup: it neither downloads nor registers demand, and returns in target
   order including duplicates. A missing reference means unavailable now, not a failed
   network request. Available empty files have a reference and zero byte count.
3. Read the returned opaque reference with `readAttachmentAsset(accountRef, reference,
   offset, limit)`. Each call returns at most 1 MiB; limits must be 1 through 1,048,576.
   Advance by actual returned bytes. `available=true` and empty bytes means EOF.
4. If any chunk returns `available=false`, discard the partial assembly and refresh
   metadata. Never concatenate chunks from different references. Local removal, source
   replacement, expiry or deletion can invalidate availability between reads.
5. Decode/play on the host with bounded buffers or an appropriate temporary file.
   MDK does not return a permanent filesystem path. Do not accumulate an unbounded
   video in memory merely because the API supports repeated reads.

```swift
let targets = [AttachmentLocalTargetFfi(
    messageIdHex: messageId, sourceMessageIdHex: sourceId, attachmentIndex: index)]
let assets = try await marmot.attachmentLocalAssets(
    accountRef: account, groupIdHex: group, targets: targets)
if let ref = assets.first?.reference {
    let chunk = try await marmot.readAttachmentAsset(
        accountRef: account, reference: ref, offset: 0, limit: 65_536)
    // Consume only if chunk.available; continue with bounded reads when needed.
}
```

References are account/store/source bound and runtime scoped; do not persist or inspect
them. Reacquire after reconstruction. Host buffers, decoded images, exports and copied
files remain host-owned plaintext: clearing MDK bytes does not erase those copies.
Keep existing persistent host caches until migration and device validation prove the
replacement path; then retire redundant acquisition deliberately to avoid duplicate
network work. `downloadMedia` still performs a one-shot fetch returning complete transient
bytes; it is neither redirected through this cache nor removed by this release.

### Observe progress and expose controls

`attachmentTransferSnapshot` gives a one-shot view; `subscribeAttachmentTransfers`
returns an initial snapshot through `next()`, then complete replacements in target order,
coalesced to at most four per second. Recreate the subscription when visible targets
change. Its `cancel()` stops observation, **not the transfer**. Cancel, then release
its handle when the view leaves. C callers use blocking `next` with a timeout off the UI thread.

Render all states: `Unavailable`, `NotRequested`, `Queued`, `Paused`, `Downloading`,
`VerifyingCiphertext`, `Decrypting`, `VerifyingPlaintext`, `Ready`, `RetryScheduled`,
`Failed`, `PolicyBlocked`, `Cancelled`, `Removed`. These are structured state, not
localized text. `received`/optional `total` measure ciphertext transfer. `attempt`
changes when counters can reset; do not carry a percentage across attempts, locator
fallback or a restarted body. Only `Ready` indicates verified local publication;
recheck local byte availability before consuming it. Unknown total means indeterminate
progress. `retryAt` can inform a retry indicator; it is not a guaranteed completion time.

| User action | Method and result |
| --- | --- |
| Cancel download | `controlAttachment(..., Cancel)` durably cancels; already-ready bytes remain. Valid partial ciphertext retains its existing 24-hour expiry. |
| Retry | `controlAttachment(..., Retry)` requests explicit work even with automatic acquisition off. |
| Remove local media | `controlAttachment(..., Remove)` removes bytes and suppresses automatic reacquisition; it does not delete the message. |
| Download again | `downloadAttachmentAgain(accountRef, groupIdHex, target)` clears cancellation/suppression for an exact current slot and queues explicit work atomically. |

Controls use the transfer entry's reference, available before content is ready.
A stale/ineligible control returns false; an unavailable/obsolete download-again target
returns no reference. Refresh UI rather than pretending success. Persisted requests need
an active, non-frozen runtime to acquire. Closing a screen must not cancel a durable
request unless the user chose that action.

Idle observation uses a 30-second fallback shortened for known expiry; active entries
use a one-second fallback. Local control/presentation notifications wake promptly.
Cross-writer idle changes may take up to 30 seconds to display, but each byte read
revalidates visibility/expiry immediately. See the [full attachment contract](../../crates/marmot-uniffi/ATTACHMENT-ACCESS.md).

### C attachment entry points

These operations mirror the same semantics; do not infer ownership or function names
from a Swift/Kotlin wrapper. All calls below belong off the UI thread.

| Operation | C API |
| --- | --- |
| Local metadata / bounded read | `marmot_attachment_local_assets` / `marmot_read_attachment_asset` |
| Policy read/write | `marmot_attachment_download_policy` / `marmot_set_attachment_download_policy` |
| Progress snapshot / stream | `marmot_attachment_transfer_snapshot` / `marmot_subscribe_attachment_transfers` |
| Stream lifecycle | `marmot_attachment_transfer_subscription_next`, `marmot_attachment_transfer_subscription_cancel`, `marmot_attachment_transfer_subscription_free` |
| Durable user action | `marmot_control_attachment` / `marmot_download_attachment_again` |
| History page/version | `marmot_attachment_history_page` / `marmot_attachment_history_version` |

Use each result's matching deep-free from the [C symbol reference](../../crates/marmot-c/API-REFERENCE.md).
Copy a returned asset reference before freeing the owning result if it will be used later.
`next` timeout does not consume an update. Cancel wakes observation; do not free while a
concurrent call still uses the handle. Plaintext returned through C remains host-owned
content until the matching free; the free does not promise to wipe host copies or buffers.

## 3. Move media libraries to bounded local history

`attachmentHistoryPage(accountRef, groupIdHex, limit, cursor)` reads the canonical
local attachment index without an engine/network dependency. Limits are 1–100 original
slots, including rejected attachments. Render MDK categories and typed parse outcomes;
do not renumber slots, sort by display timestamp, or assume audio means voice-note intent.
URL-only links are outside this API.

The first page returns a version baseline and optional next cursor. Keep that baseline
until replacing the loaded collection. Use `attachmentHistoryVersion` on resume and
relevant projection wakeups, including after an empty or exhausted list. Compare the
current version against the baseline with `changeSince`:

- `Unchanged`: keep the loaded collection.
- `Additions`: cursors remain usable, but new items above a passed boundary need a
  refresh; later paging alone does not guarantee those additions appear.
- `RestartRequired`: discard stale rows/cursors and reload from the head. A page call
  may also require restart. Do not append a fresh first page to the old collection.

Filter categories within each returned page. Zero matches while `hasMore` is true
means a partially loaded filtered view, not an empty library. Page in bounded,
cancellable work. `InvalidLimit` and `CursorMismatch` require correcting the request.
Discard responses from obsolete account/group/view attempts.

History discovery does not prove local-byte availability or permission to fetch. Keep
cursor/version handles process-local. Kotlin explicitly closes consumed handles;
Swift drops references at the corresponding boundaries. C must clone a page's version
before freeing the page if retaining it as the collection baseline. See
[history ownership and examples](../../crates/marmot-uniffi/ATTACHMENT-HISTORY.md).

## 4. Render deletion provenance and custom events

`deletionSource` is added to timeline messages, reply previews and chat-list message
previews, including their prepared-window representations. Consult it only if `deleted`:

| Value | Client presentation |
| --- | --- |
| `Author` | Existing localized author-deletion wording. |
| `Admin` | Localized admin-deletion wording, including an admin deleting their own message. |
| `Unknown` | Neutral deleted-message fallback without an invented actor. |

MDK derives this from accepted authenticated deletion evidence, not current roster/admin
status or reports. Legacy tombstones can stay `Unknown` indefinitely; migration does
not backfill history. `deletedByMessageIdHex` identifies the selected deletion, while
`kind` remains the original message kind. `invalidationStatus` is a separate convergence
condition, not proof of an author/admin deletion. Live provenance can change if evidence
is invalidated; handle a metadata-only update without changing message identity.

Prepared conversation windows now retain ordered custom-event `tags`, together with
numeric `kind` and original `plaintext`, so app-defined renderers need no raw-event
lookup. Deleted rows expose no raw tags. MDK-owned kinds continue to use structured
prepared fields/references. Do not replace all typed rendering with raw tag parsing.
This does not change notification/chat-list activity policy for custom events.

## 5. Configure and display KeyPackages

### Label every runtime construction

Use `Marmot.newWithConfiguration` with `MarmotOptions` to combine optional `relayPolicy`,
`cursorPersistence`, `clientName` and `secretStore`. Preserve the host's existing
policies/store. The old constructors still work; adding the label must not reset a
notification extension's frozen cursor or silently replace custom key storage.

```swift
let options = MarmotOptions(clientName: "whitenoise")
let marmot = try Marmot.newWithConfiguration(
    rootPath: rootPath, relayUrls: relayUrls, options: options)
```

```kotlin
val options = MarmotOptions(clientName = "whitenoise")
val marmot = Marmot.newWithConfiguration(rootPath, relayUrls, options)
```

These examples use default public-only endpoints, advancing cursor and platform keychain.
Set other fields explicitly where those defaults do not match the entry point. C uses
`MarmotClientOptions` / `marmot_client_new_with_configuration`; zero initialization means
defaults. A narrower `newWithClientName` convenience is also available.

The label is public metadata, not an authenticated application identity. Use it only for
the application actually publishing. It applies to new initial publications and normal
rotations, not previously signed events or queued publication retries. Existing constructors
remain untagged; no special republish is required simply to upgrade.

MDK automatically prefers valid compatible `whitenoise` packages, then untagged/other
clients, then `amethyst`. Names are trimmed and compared exactly, case-insensitively.
Recency still orders each tier; current publication slots supersede older packages before
ranking. This temporary selection heuristic is not synchronized multi-device support or
proof that a recipient is online. No host ranking implementation is needed.

### Local-first settings

Render `localAccountKeyPackages(accountRef)` first, off the UI thread: it is a synchronous
SQLCipher read. Then call asynchronous `refreshAccountKeyPackages(accountRef, bootstrapRelays)`
and replace the snapshot. An empty relay argument still allows network access. Keep the
local result on refresh failure/cancellation; discard obsolete refresh responses after
account changes or mutations and re-read authoritative local state.

Each `AccountKeyPackageInventoryEntryFfi` contains the existing `record` and typed
`localState`: `NotLocal`, `Current`, `PendingReplacement`, `RetainedPrivateMaterial`,
`OtherOwned`. Local ownership and `record.relay` are independent: retained private
material can still have a relay observation. Empty event IDs or publication timestamps
are not proof of publication. `accountKeyPackageRelayEvents` remains the observed-history
API; the new inventory does not replace it.

Missing private KeyPackage material for an invitation now has explicit MDK diagnostic
classification (`missing_welcome_key_package`) and recovery guidance: publish a fresh
KeyPackage and ask for a new invitation. This is not an invitation auto-repair or a new
native method. Do not endlessly retry the same undecryptable invitation or interpret it
as generic malformed content. The existing native error path carries its detail; this
release does not introduce a dedicated new UniFFI exception variant for that engine error.

## 6. Measure local visibility separately from composer readiness

The host performance enum adds `ConversationLocalVisible` and `ConversationComposerReady`;
outcomes add `Cancelled`, `Timeout`, `Unavailable`. Use `recordHostPerformance` to record
elapsed milliseconds from a consistent host-defined open/navigation start to actual first
visible content and to actionable composer readiness. Treat these as two milestones,
not a single API-response duration. Closing the view before completion should not be
reported as success. Do not inject account/group/message identifiers into metric labels.

`appPerformanceSnapshot().runtimeOperations` adds bounded operation names, started/completed
counts, successes/failures/cancellations/timeouts/not-ready counts, in-flight gauges and
duration histograms. These are cumulative process diagnostics, not per-chat histories.
An empty conversation, cancelled navigation and a timeout are distinct outcomes. Update
exhaustive switches and fixture constructors for the new enum/record surface.

`recordHostTiming` remains the separate consent-gated product-event path; it is not the
same as recording these fixed runtime performance milestones. Preserve existing consent,
export configuration and privacy rules. See [telemetry](../marmot-architecture/telemetry.md).

## 7. Improvements requiring no new client calls

With matching bindings, the existing APIs gain reduced repeated timeline projection
work, batched display-name reads, group reads that avoid full-account loading, and ready
account/worker reuse. Identity creation handles concurrent database initialization.
Retained/deferred replay and losing-branch parking fixes improve recovery. Size-rotated
audit segments retain source metadata; QUIC subscriber writes are bounded.

The macOS C bundle/smoke build disables debug stripping to avoid malformed Mach-O linkage
with Xcode 27; this does not add an API or require a client-side linker workaround.
Keep deployment-target validation separate from successful local host linking.

Prepared conversation windows, initial unread/latest navigation, durable avatar APIs,
chat-list windows, account attention, reaction viewer state and edit/moderation APIs
already existed in 0.10.1. Do not schedule them as newly added 0.10.2 methods merely
because the current README describes them. They may still need adoption in a particular
client. The new draft-aware chat-list preview and row-action work audited in #1918 is
future work, not a feature delivered by this release.

## Client acceptance checklist

Run with the actual released artifacts and representative retained history; document
platform/build/source provenance and which checks were performed.

- [ ] C callers have audited blanket retry-on-error logic against authoritative mutation state and per-method retry contracts.
- [ ] All consuming targets compile with one coherent cohort; switches/fixtures accept new fields/variants.
- [ ] Apple app/extension archives include the matching privacy resource; Android loads each shipped ABI and initializes key storage.
- [ ] A 0.10.1 account upgrades, reopens and retains history/settings. A backup/export remains usable for recovery; no unsupported library-only downgrade is attempted.
- [ ] Cold conversation opening renders local history before network catch-up where available; unread/latest anchor and composer readiness remain correct. Record first-visible/composer-ready timings separately.
- [ ] Automatic policy is intentional for each account and host network condition; pending invites acquire no message attachments before acceptance.
- [ ] Image, audio, video, empty, rejected, multi-slot and larger attachments have correct progress/local rendering without unbounded buffer assembly.
- [ ] Offline reopen reads ready media locally; interrupted work resumes or safely restarts. Cancel/retry/remove/download-again persist through reconstruction.
- [ ] Deletion/expiry/replacement between chunk reads discards partial results; host exports/caches follow the host's removal policy.
- [ ] Quota/disk pressure and files above the automatic ceiling display appropriate non-ready state without retry storms or false success.
- [ ] Media-history paging/filters handle additions, destructive changes, empty pages, stale responses and cursor/version disposal.
- [ ] Author/admin/unknown deletion wording is localized in messages, replies and previews; custom-event tags render only where appropriate.
- [ ] Foreground/background/extension constructions preserve cursor/store policies and intended client label; local KeyPackage settings survive refresh failure.
- [ ] Screens release subscriptions/handles, terminal suspension awaits `shutdownAndClose`, and foreground reconstructs without stale references or root-lock conflicts.

Host smoke/compilation tests do not replace real-device scrolling, media decoding,
background/foreground, memory and storage measurements. Keep incomplete consumer work
visible in client tracking issues rather than claiming MDK release publication completes it.
