# Upgrading MDK 0.12.0 → 0.13.0

## Scope and provenance

This guide compares `v0.12.0` / `marmotkit-v0.12.0` / `marmotc-v0.12.0` /
`wn-agent-v0.12.0`, which all peel to
`122bd90ffac60bb6311346e228d0f609a18521ee`, with the source to be shipped as
`v0.13.0`. All four 0.13.0 cohort tags must peel to the release PR's merged
commit, and packaged manifests must record that exact SHA. The behavior comparison
was prepared against `origin/master` at
`897022e1e901223191de990c70963ee304a93985`; use the full release SHA from the
tags for artifact verification. This guide ships in the release commit, not a
later supplement. See the [release notes](../release/0.13.0.md),
[previous upgrade guide](0.12.0.md), and
[current binding reference](../../crates/marmot-uniffi/README.md).

Readers: native app hosts (Swift/Kotlin through MarmotKit), C hosts, Rust hosts
that embed `marmot-app`, and WN Agent operators.

## Upgrade decisions

| Category | Required action or effect |
| --- | --- |
| Required | Replace generated Swift/Kotlin, native libraries and C headers together. Update exhaustive handling of `MarmotKitError` (five moderation-report variants), `GroupEventKindFfi` (three device-local membership events) and `MarkdownInlineFfi` (`Timestamp`). Set the new defaultless record fields when constructing `AttachmentEntryFfi`, `PresentedChatRowFfi` or `OnboardingRepairProposalFfi` by hand. |
| Required for C hosts | Recompile. `MarmotAttachmentEntry`, `MarmotPresentedChatRow` and `MarmotOnboardingRepairProposal` change layout; event and Markdown inline tags are appended; statuses 96–100 are new; relay-repair preview strings are JSON string literals. |
| Required storage | Back up, then allow migrations 102–107 to complete on first open. Downgrade across them is unsupported. |
| Required for Rust hosts | Handle new `AppError` and `GroupEvent` variants and set the new fields listed in [Rust host changes](#rust-host-changes). |
| Strongly recommended | Render `Timestamp` Markdown nodes; peers on 0.13.0 can send them. Use `createIdentityWithInitialProfile` when onboarding collects a name. Use `uploadMediaFiles` for large attachments. |
| New defaults | External-signer account database keys move into the host `SecretStore` (downgrade unsupported). Polls can be created in direct conversations. `relay.damus.io` is no longer retired. Sync drains stop waiting for relays that refused a history REQ. Profile, follow and relay-list saves finish delivering in the background to relays the quorum cut off. |
| Optional adoption | Private moderation reports, message reaction details, attachment-role gallery filtering, draft-version handoff, lossless relay-repair previews, SOCKS5 routing, native startup diagnostics, C NIP-46 sessions (beta). |
| Automatic fixes | Batched, oldest-first catch-up; relay `CLOSED` handling; KeyPackage recovery from discovery relays; queued and relay-accepted sends no longer stay failed; durable sends progress through recovery; faster media upgrades on open; `libcrux-kem` 0.0.10 security fix. |

## Required upgrade steps

1. Pin all MDK, MarmotKit, Marmot C and WN Agent inputs to 0.13.0. Verify the
   source SHA in each manifest and every sibling checksum. Do not combine new
   generated records or headers with 0.12.0 native libraries.
2. Rebuild Swift/Kotlin clients after updating exhaustive handling:
   - `MarmotKitError` gains `ModerationReportingNotConfigured`,
     `InvalidModerationReportConfig { details }`, `InvalidReportedPublicKey`,
     `CannotReportSelf` and `ModerationReportRateLimited`. Only the
     moderation-report methods return them.
   - `GroupEventKindFfi` gains `LocalGroupCopyTerminated { voluntary }`,
     `LocalGroupCopyRestored` and `GroupMemberLeavesRemoved { epoch }`. See
     [Device-local membership events](#device-local-membership-events).
   - `MarkdownInlineFfi` gains `Timestamp { unixSeconds, style }` with the nine
     `MarkdownTimestampStyleFfi` variants.
   - `AttachmentEntryFfi.role: AttachmentRoleFfi` (`Shared` / `InlineEmoji`),
     `PresentedChatRowFfi.draftVersion: ChatListDraftVersionFfi?` and
     `OnboardingRepairProposalFfi.relayRepair` are new fields with no binding
     default. Host-constructed records (previews, fixtures) must pass them;
     `nil` / `null` is correct for the two optional ones.
   - `MarmotOptions.moderationReportConfig` is new and defaults to unset.

   No existing exported method changed its signature (compared against the
   `v0.12.0`
   [method reference](https://github.com/marmot-protocol/mdk/blob/v0.12.0/crates/marmot-uniffi/API-REFERENCE.md)).
   The new methods are listed under [Feature adoption](#feature-adoption).
3. Recompile C consumers against the regenerated `marmot.h`:
   - `MarmotAttachmentEntry` adds `role: MarmotAttachmentRole`.
   - `MarmotPresentedChatRow` adds the nullable row-owned
     `MarmotChatListDraftVersion *draft_version`; the parent deep-free releases it.
   - `MarmotOnboardingRepairProposal` adds an optional `relay_repair` pointer.
   - Relay-repair preview content, tag fields and optional endpoints are JSON
     string literals, so embedded NULs and all UTF-8 bytes survive. Decode them
     once with a length-aware parser before showing them for consent or editing.
   - The event surface appends the three device-local membership events, and
     `MarmotMarkdownInline` appends `Timestamp` (signed `int64_t` seconds plus
     `MarmotMarkdownTimestampStyle`). Existing discriminants are unchanged.
   - `MARMOT_STATUS_MODERATION_REPORTING_NOT_CONFIGURED` (96),
     `_INVALID_MODERATION_REPORT_CONFIG` (97), `_INVALID_REPORTED_PUBLIC_KEY`
     (98), `_CANNOT_REPORT_SELF` (99) and `_MODERATION_REPORT_RATE_LIMITED` (100)
     are new. Existing status values are unchanged.

   Use only the header shipped with the exact library.
4. Keep the Swift wrapper's `PrivacyInfo.xcprivacy` resource and dependency in
   every app and extension, and update the binary ZIP, shared Swift file and
   privacy resource together. Android still requires
   `MarmotAndroid.initialize(context)` before creating `Marmot`, and all JNI ABIs
   must come from one cohort.
5. Back up each account database before first open. See
   [Storage upgrade](#storage-upgrade).
6. If your app uses external-signer accounts, confirm the configured
   `SecretStore` is durable before upgrading. See
   [External-signer database keys](#external-signer-database-keys).
7. Rust hosts: see [Rust host changes](#rust-host-changes).

## Storage upgrade

Account databases advance from schema 101 to 107 on first open:

- 0102 records the source `emoji` tags behind each attachment-history entry and
  invalidates cached history versions when they change, so entries can carry
  `AttachmentRole`.
- 0103 adds bounded file-backed bodies for optional outgoing upload staging.
- 0104 adds retained-body metadata without rewriting existing encrypted payloads.
- 0105 preserves bounded ciphertext checkpoints for resumable downloads while
  widening file-transfer bounds.
- 0106 adds chunk tables so large file imports stay unreadable until verified and
  an outgoing file can share immutable chunks with its retained source.
- 0107 adds the account-private `moderation_report_outbox`. Rows never hold the
  reported key or explanation in the clear, and a published row drops its wrap.

Migrations 0104 and 0105 keep retained bodies and checkpoint chunks in place
instead of copying them during account open. On a synthetic encrypted 512 MiB
host fixture, 0104 dropped from about 16 s to 2 ms and 0105 from about 12.7 s to
13 ms. These are host measurements, not device acceptance. None of these
migrations rebuild message history.

Downgrade across them is unsupported: the 0.12.0 binary refuses the upgraded
database before reading application tables. Re-upgrade or restore a pre-upgrade
backup/export instead of removing migration rows. See the
[storage-format contract](../marmot-architecture/storage-format-v2.md).

## Feature adoption

### File-backed media upload (strongly recommended for large files)

`uploadMediaFiles(accountRef, groupIdHex, request, control)` and
`uploadMediaFilesWithClientToken(…, clientToken)` take a
`MediaFileUploadRequestFfi` whose attachments name a `sourcePath` (a regular
file, not a symlink) with an optional `expectedSize`, instead of a byte array.

- MDK snapshots and encrypts each source into owner-only temporary files under
  the account directory before the first PUT, then deletes them on completion or
  failure. Keep the source valid until the call returns.
- Create one `MediaFileTransferControlFfi` per operation. `processedBytes()` is
  a monotonic byte count, not a percentage. Call `cancel()` explicitly; dropping
  your wait is not cancellation. After an error, `isCancelled()` tells a
  requested cancellation (`InvalidMediaReference`, detail
  `media transfer cancelled`) apart from a failure.
- Cancellation observed before message admission starts publishes nothing.
  Admission itself is not interruptible.
- `maxFileMediaCiphertextBytes()` is the batch bound, including a 16-byte AEAD
  tag per attachment. Retained file bodies are bounded at 900 MiB; the existing
  byte-array `uploadMedia` APIs keep their smaller limits and are unchanged.
- File uploads have no fixed worker-response timeout; per-endpoint network
  deadlines still apply. They require the server descriptor's `sha256` and
  `size`, and fall over to the next server when either is missing or wrong.
- With a client token, probe `localSendStatus` after an unknown outcome before
  uploading again. See [local sends](../../crates/marmot-uniffi/LOCAL-SENDS.md).

Receivers need no new call: large explicit acquisitions stream into private files,
resume from protected ciphertext checkpoints, and authenticate before publishing a
readable local asset. A file-backed download API is not exposed yet.

C uses `marmot_upload_media_files`, `marmot_upload_media_files_with_client_token`,
`marmot_media_file_transfer_control_{new,cancel,is_cancelled,processed_bytes,free}`
and `marmot_max_file_media_ciphertext_bytes`. See the
[C file-backed upload section](../../crates/marmot-c/README.md#file-backed-media-upload).

### First profile at account creation (strongly recommended)

`createIdentityWithInitialProfile(profile, defaultRelays, bootstrapRelays, inboxRelays)`
creates a generated identity whose first public kind-0 is the onboarding-selected
profile. It returns at durable local readiness, like `createIdentityWithProfile`.
Creating with the generated default and then calling `publishUserProfile` exposes
the default name to relays first, and contacts can keep showing it. A setup
resumed past its first local step ignores `profile` and returns what its bootstrap
publishes; change it later with `publishUserProfile`. C uses
`marmot_create_identity_with_initial_profile`.

### Local-time Markdown timestamps (strongly recommended)

`<t:UNIX_SECONDS>` and `<t:UNIX_SECONDS:STYLE>` parse into
`MarkdownInlineFfi.Timestamp`; an omitted style is `ShortDateTime`, and invalid
syntax stays literal text. Format with native formatters using the device locale,
time zone and 12/24-hour preference at render time. Refresh on locale, time zone
or clock changes and on resume, and keep visible `Relative` nodes ticking. See
[Markdown rendering](../../crates/marmot-uniffi/README.md#markdown-rendering).

### Private moderation reports (optional)

`submitModerationReport(accountRef, reportedPubkey, reason, explanation, origin)`
privately reports an account to the deployment's moderation team. It is additive:
`reportMessage`, `contentReports` and `dismissReports` (in-group moderation) are
unchanged.

- Configure the destination per build flavor with
  `MarmotOptions.moderationReportConfig` (`recipientPubkey` as hex or `npub`, plus
  `relays`), or at runtime with `configureModerationReporting`. An invalid config
  is rejected whole and leaves reporting unconfigured. Gate the UI on
  `moderationReportingAvailable()`.
- The report is a NIP-56 kind-1984 rumor, sealed by the account key and
  gift-wrapped (NIP-59) to the reports key. It carries only the reported key, the
  reason and an explanation of at most 1,000 characters: no message, group or
  relay identifiers. It publishes only to the configured relays, without account
  AUTH.
- `origin` is `Report` or `BlockAndReport`. Blocking stays a separate
  `blockUser` call.
- The outcome's `acceptDisposition` is `Published`, `AcceptedPending` or
  `CompletionUnknown`. The last two are queued and retried after
  `catchUpAccounts`; do not resubmit them. A repeat within 10 minutes returns the
  same `reportId`, and each account can send 20 reports per hour
  (`ModerationReportRateLimited`). Pending reports are purged on sign-out and wipe.

C uses `marmot_submit_moderation_report`,
`marmot_moderation_reporting_available`, `marmot_configure_moderation_reporting`
and `marmot_moderation_report_outcome_free`; `MarmotClientOptions` is unchanged.
The wire contract for the operator's reader is in
[moderation reports](../marmot-architecture/moderation-reports.md).

### Message reaction details (optional)

`messageReactions(accountRef, groupIdHex, messageIdHex)` returns every effective
reaction on one exact message, one entry per sender and emoji, without the
conversation-preview cap. It is a local read with no network work: run it off the
UI thread. Missing, hidden, deleted, invalidated and retention-pruned targets
return an empty list, and blocked reactors are excluded. C uses
`marmot_message_reactions` and frees with
`marmot_timeline_user_reaction_list_free`.

### Attachment-history roles (optional)

`AttachmentEntryFfi.role` is `InlineEmoji` for custom-emoji artwork and `Shared`
otherwise. Shared-media galleries can skip `InlineEmoji` entries; keep paging after
a filtered page and keep the original slots and acquisition references. See
[attachment history](../../crates/marmot-uniffi/ATTACHMENT-HISTORY.md).

### Pending-send draft handoff (optional)

`PresentedChatRowFfi.draftVersion` is an opaque, device-local version of the
row's draft. Capture the composer's `MessageDraftRevisionFfi` before accepting a
send, then `revision.includesChatListVersion(row.draftVersion)` tells whether the
row still shows that draft or a newer edit (even with identical text). A true
result does not authorize deletion: after durable acceptance, clean up with
`clearMessageDraftIfRevision`. A save with identical text now advances the draft
revision, so the presented-list subscription emits a replacement snapshot for it.
See [pending-send draft presentation](../../crates/marmot-uniffi/CHAT-LIST-ROWS.md#pending-send-draft-presentation-0130).
C uses `marmot_message_draft_revision_includes_chat_list_version`.

### Lossless onboarding relay repair (optional)

`proposeOnboardingRelayRepair(accountRef, step)` previews the smallest change to
a general or inbox relay list without signing or publishing.
`OnboardingRepairProposalFfi.relayRepair` carries the ordered before/after tags,
the exact diff, the restored capabilities and the repair mode. Show the diff for
consent; `ManualReview` cannot be approved, so prefill a manual editor or offer a
separately labeled reset. NIP-65 read/write markers match case-insensitively and
keep their original spelling. Explicit relay edits keep untouched tags, duplicate
entries, extensions and content as they were, and a no-op selection cannot
publish. Manual-edit checkpoints are now version 7, which 0.12.0 readers reject.
C uses `marmot_propose_onboarding_relay_repair`.

### SOCKS5 routing (optional)

Set `WN_SOCKS5_PROXY` (a numeric `ip:port`) and, optionally, both
`WN_SOCKS5_USERNAME` and `WN_SOCKS5_PASSWORD` in the process environment before
the runtime (or a C NIP-46 session) is first constructed. Relay publishing,
receive and history pools, directory reads, media, Open Ranking, collectors,
audit uploads, moderation reports and C NIP-46 sessions then connect through the
proxy, and never fall back to direct connections.

- The policy is read once per process. `ALL_PROXY` and `NO_PROXY` are ignored.
  Restart the process to change it.
- Invalid settings (partial credentials, a hostname, a zero port) make
  `Marmot.new` / `newWithOptions` and `marmot_client_new` fail, and
  `marmot_nip46_new` return `MARMOT_STATUS_INVALID_ARGUMENT`.
- Agent preview publishing and watching (QUIC) are unavailable while SOCKS5 is on.
- With all three variables unset, routing is unchanged.

See [SOCKS5 routing](../../crates/marmot-app/README.md#socks5-routing).

### Native startup diagnostics (optional)

For slow-open investigations, call `setStartupDiagnosticsEnabled(true)` before the
first account query, then read `startupDiagnosticsSnapshot()`, even while a call
is still running. Snapshots report fixed phases (key lookup, database-open waits,
SQLCipher phases, migration numbers, result delivery) with bounded history and
drop counters. They contain no paths, account identifiers or error text, never
query storage or the keystore, and change no upload consent or database state.
Keep normal builds disabled and revoke with `false`. C uses
`marmot_set_startup_diagnostics_enabled`, `marmot_startup_diagnostics_snapshot`
and `marmot_native_startup_snapshot_free`.

### C NIP-46 sessions (beta)

C hosts can log in and restore accounts through a NIP-46 remote signer with one
`MarmotNip46Session` per account (`marmot_nip46_{new,uri,connect,login,register,state,export,cancel,logout,free}`),
alongside local-key accounts. Store `marmot_nip46_export` only in an encrypted
vault. This surface is beta; MarmotKit does not expose it. See
[NIP-46 accounts](../../crates/marmot-c/README.md#nip-46-accounts).

## Changed defaults

### External-signer database keys

The SQLCipher key for an external-signer account database now goes through the
configured `SecretStore` under the reserved `.external-sqlcipher/<account label>`
credential. On first open, an existing `.external-sqlcipher-secret` file migrates
only after a verified secret-store write, and is then scrubbed and removed. If a
database has neither credential, opening fails instead of generating a new key.
Make sure the host secret store is available and durable at first open after
upgrading. A 0.12.0 binary cannot open a migrated external-signer account,
so downgrade is unsupported for these accounts as well. See
[external-signer accounts](../external-signer-accounts.md).

### Other defaults

- **Polls in direct conversations.** `createPoll` now works in direct
  conversations as well as groups, under the same admission, validation and
  retention rules. Hosts that hid poll creation in DMs can offer it.
- **`relay.damus.io`** is no longer on the retired-relay denylist;
  `retiredRelayHosts()` returns only `relay.nostr.band`, and members whose inbox
  list names only `relay.damus.io` can be invited again.
- **Relay refusals.** A relay that answers a live subscription with `CLOSED` no
  longer stays counted as live. A sync drain stops waiting once every relay has
  answered, counting a permanent refusal as answered; a refusal is not served
  history, so live cursor promotion still needs end-of-stored-events from every
  relay. Refusals are audited (`subscription_refused`) and counted in relay stats.
- **Profile, follow and relay-list saves** still return on the first relay
  acknowledgement, but relays the quorum cancelled now receive the identical
  signed record in a bounded background send.
- **Missing inbox relays.** When a member lookup does not complete and the known
  inbox list has no usable relays, an invite fails with a retryable "known member
  inbox relay list has no usable relays and its refresh did not complete" error.

### Device-local membership events

The group-event firehose now separates account-level timeline activity from
device-local copy changes: `LocalGroupCopyTerminated { voluntary }`,
`LocalGroupCopyRestored` and `GroupMemberLeavesRemoved { epoch }`. MDK applies
their membership, pending-send and notification effects before delivering them,
and they create no system row. Use them to refresh presentation. Restoration
describes retained-history repair, not automatic scheduler restoration of a
removed copy. See
[device-local membership events](../../crates/marmot-uniffi/README.md#device-local-membership-events).

## Rust host changes

- `AppError` gains `ModerationReportingNotConfigured`,
  `InvalidModerationReportConfig`, `InvalidReportedPublicKey`, `CannotReportSelf`
  and `ModerationReportRateLimited`; update exhaustive matches.
- `MarmotAppConfig::moderation_report_config` is new; full struct literals must
  set it.
- `GroupEvent` gains `LocalGroupCopyTerminated`, `LocalGroupCopyRestored` and
  `GroupMemberLeavesRemoved`.
- `AttachmentEntry::role` (`AttachmentRole`) and storage's
  `AttachmentHistoryEntry::emoji_tags` are new required fields.
- `RelaySyncSnapshot::refusals` (`Vec<RelayRefusalStats>`) is new; use
  `Vec::new()` for the old meaning. Serialized snapshots omit it when empty and
  older ones still deserialize.
- `NostrAdapterMetrics::reconciliation_order_unproven_passes` and
  `NostrReconciliationSummary::order_unproven` are new; use
  `..Default::default()` in struct literals.
- `MarmotApp::try_with_relays_and_account_home_and_config` fails with an
  `InvalidInput` I/O error on invalid `WN_SOCKS5_*` settings; the infallible dev
  constructors open, but every connection is refused.
- New runtime methods include `submit_moderation_report`,
  `moderation_reporting_available`, `retry_pending_moderation_reports`,
  `MarmotApp::set_moderation_report_config`, `message_reactions`,
  `upload_media_files`, `upload_media_files_with_client_token`,
  `create_identity_local_ready_with_initial_profile` and
  `AccountManager::propose_onboarding_relay_repair`.
- `storage-sqlite`'s `PresentedChatRow::draft_version` is a new field, and its
  new `chat_list_selection_snapshot` / `_count` / `_page` and
  `revalidate_chat_list_selection` capture every eligible chat id for a fixed
  chat-list view, for batch actions beyond the loaded window.
- `marmot-markdown`'s `Inline::Timestamp`, `cgka-traits`' `GroupEvent` variants and
  `agent-control`'s relay-list request/response variants are additions to
  exhaustive enums; these crates have no changelog of their own.
- Opt-in relay telemetry exports `relay_reconciliation_attempts` and
  `relay_reconciliation_order_unproven_passes`.

## WN Agent and integrations

- **Goose.** WN Agent releases include the `wn-goose` terminal-harness connector
  and `install-goose-marmot.sh` for Goose 1.53.0 or newer. It supports the
  `inherit` and `unrestricted` execution profiles and refuses `autonomous`.
- **Group profile.** `wn-agent group-profile` reads `{name?, description?}` JSON
  on stdin and updates the current group through `group_profile_update`
  (`MARMOT_GROUP_PROFILE_TIMEOUT_SECS`, default 30). Claude Code, Codex, OpenCode
  and Pi turns get it automatically, and OpenClaw adds a `marmot_group_profile`
  tool. Unconfirmed outcomes are reported as unknown and never retried.
- **Relay lists.** The control protocol adds `account_relay_lists`,
  `account_relay_list_add` and `account_relay_list_remove` (optional
  `direction`), answered with `relay_lists`. Edits read, merge and republish
  kinds 10002/10050, and refuse an unconfirmed read with
  `relay_list_inconclusive`, so a generated agent account can adopt its own
  relays.
- **SOCKS5.** `wn` and `wn-agent` follow the same `WN_SOCKS5_*` settings; live
  QUIC previews are unavailable while SOCKS5 is on.
- **Setup.** Terminal-harness installers show the full agent npub to compare and
  end with a phone round-trip check. `wn-agent` reports `socket_path_too_long`
  before binding an oversized control socket path.
- **Relay stats.** `wn relay-stats` reports live-subscription refusals under
  `sync.refusals` by opaque relay index, route kind, reason category and
  disposition, without relay URLs or reason text.
- **Installers.** Install only from the immutable `wn-agent-v0.13.0` release with
  sibling `.sha256` verification. See the
  [integrations quickstart](../../integrations/README.md).
- The control socket still grants its whole API to an authenticated client;
  capability-scoped grants remain tracked in
  [#1445](https://github.com/marmot-protocol/mdk/issues/1445).

## Changes requiring no new calls

- **Catch-up.** Each comparison pass fetches up to 256 events (1 MiB) across all
  relays in batched requests instead of 16 one-at-a-time requests, and narrows to
  the oldest part of a backlog larger than one pass. Commits no longer routinely
  move a member more than five epochs past messages it has not downloaded
  ([#2086](https://github.com/marmot-protocol/mdk/issues/2086)).
- **Sends.** A message the engine queued while the group was converging is no
  longer marked failed when an unrelated publish in the same batch fails, and a
  row already marked failed revives once a relay accepts its fanout. Durably
  accepted sends no longer wait behind startup recovery, push gossip or older
  publications' retries.
- **Invitations** search up to eight discovery relays for a member's KeyPackage
  when their advertised outboxes have none, and check signed deletions before
  using a recovered package.
- **Attachments.** File acquisition enforces the disk reserve, saves interrupted
  ciphertext tails, and restarts a rejected resumed representation from zero.
- **Group activity** keeps per-commit reaction targets for authors and peers,
  including commits before a disband, and projection, push-token and
  maintenance retries keep committed work across partial failures.
- **Security.** `libcrux-kem` 0.0.10 fixes malformed hybrid-key and short-seed
  panics (RUSTSEC-2026-0330, RUSTSEC-2026-0331).

## Acceptance and remaining work

Compile matched artifacts, then exercise these consuming-app checks:

- Upgrade and reopen databases from 0.12.0, including one with large retained
  attachments and an unfinished download. Measure first-open time on a
  representative device and verify the 0.12.0 binary refuses the upgraded
  database.
- External-signer accounts: open an account created by 0.12.0 and confirm the key
  moved into the secret store and the account reopens after restart.
- Large files: `uploadMediaFiles` with progress, cancellation before admission,
  and a recipient download interrupted and resumed.
- Onboarding: `createIdentityWithInitialProfile` publishes the chosen name as the
  first kind-0; a relay-repair preview shows the diff and a `ManualReview` repair
  cannot be approved.
- Markdown timestamps render in the device locale and `Relative` nodes refresh.
- Moderation reports: unconfigured builds hide the UI; a report while offline
  returns `AcceptedPending` and publishes after catch-up; a repeat returns the same
  id.
- Device-local membership events refresh presentation after a removal and a
  restoration.
- SOCKS5 (if used): every connection goes through the proxy, invalid settings fail
  construction, and nothing falls back to direct.
- Android 16 KB page-size validation in the consuming app bundle; Apple
  privacy-resource delivery; C deep-free paths for the changed records.

Source tests, generated binding checks and packaged artifact validation are
separate from consuming-app archives, real-device measurements, live connector
deployment and store acceptance. This guide claims none of those later stages.
The migration timings above come from host fixtures, not devices.

Known limitations:

- [#2237](https://github.com/marmot-protocol/mdk/issues/2237): a message that
  arrives more than five epochs too late stays undecryptable without a "history
  may be incomplete" notice. Batched, oldest-first catch-up makes this much rarer.
- `HistoryNoticeCauseFfi::KnownEvent` still has no production producer
  ([#2082](https://github.com/marmot-protocol/mdk/issues/2082)), and the drain-era
  `FullHistoryRepairIncompleteReason` variants remain
  ([#2083](https://github.com/marmot-protocol/mdk/issues/2083)).
- File-backed download is not exposed through the bindings yet.
