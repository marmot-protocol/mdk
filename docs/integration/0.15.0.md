# Upgrading MDK 0.14.0 → 0.15.0

## Scope and provenance

This guide compares `v0.14.0` / `marmotkit-v0.14.0` / `marmotc-v0.14.0` /
`wn-agent-v0.14.0`, which all peel to
`3fb4b4759ac676b0c21c4c3527074866c9fa4c89`, with the source to be shipped as
`v0.15.0`. All four 0.15.0 cohort tags must peel to the release PR's merged
commit, and packaged manifests must record that exact SHA. The comparison was
prepared against `origin/master` at `1a5d7d419341f7b205362c25b6166ed2252c7be7`;
use the full release SHA from the tags for artifact verification. This guide
ships in the release commit, not a later supplement. See the
[release notes](../release/0.15.0.md), [previous upgrade guide](0.14.0.md), and
[current binding reference](../../crates/marmot-uniffi/README.md).

Readers: native app hosts (Swift/Kotlin through MarmotKit), C hosts, Rust hosts
that embed `marmot-app` or lower crates, and WN Agent operators.

Unlike 0.14.0, this release changes what devices put on the wire: KeyPackages and
leaves advertise the account-devices component, new groups can require it,
KeyPackages are refreshed weekly, push-token records are exchanged more often, and
automatic rejoin adds an account-inbox handshake. The conformance vectors add the
`account-devices-*` scenarios and a large-Welcome NIP-44 fixture. The new formal
models cover experimental device pairing and linking only.

## Upgrade decisions

| Category | Required action or effect |
| --- | --- |
| Required | Replace generated Swift/Kotlin, native libraries and C headers together. Update `TimelineMessageQueryFfi` construction (four new fields with no default) and remove `MarmotDeploymentFfi.keyPackagePreferredClients` / `keyPackageLastClients`. Handle 22 new `MarmotKitError` cases, 8 new `MarmotEventFfi` cases, `WelcomeDeliveryPending.sizeClass` and new enum cases. Re-upload media references saved by 0.14.0. |
| Required for C hosts | Recompile. Several structs gain fields mid-struct (`MarmotMediaAttachmentReference`, message/timeline/preview/notification records, `MarmotTimelineMessageRecord`). Statuses 108–129 and enum values are appended; none is renumbered. `marmot_deployment_set_key_package_client_preference` is removed. |
| Required storage | Keep a device-local copy, then allow account migrations 0117–0153, 0160–0180, 0200 and 0201 (schema 116 → 201) on first open. Downgrade is unsupported. |
| Required for Rust hosts | `cgka-session` is now `marmot-session`; handle the API changes in [Rust host changes](#rust-host-changes). Building from source needs Odin. |
| New defaults | Account-devices component on new groups (0.14 clients cannot be invited into them later), every device of an account invited, members listed per account, 30-day KeyPackages refreshed weekly, sign-out deletes only this device's slot, `signOutAndWipe` steps an admin down and leaves, recovery runner owns history, automatic rejoin, more push-token gossip, admin invitees step down before declining, `MultiDeviceUnsupported` no longer produced, ordinary constructors refuse device-group accounts, wider preview lookup, identity-proof reuse. |

## Required upgrade steps

1. Pin all MDK, MarmotKit, Marmot C and WN Agent inputs to 0.15.0. Verify the
   source SHA in each manifest and every sibling checksum. Do not combine new
   generated records or headers with 0.14.0 native libraries. See the
   [distribution guide](../../crates/marmot-uniffi/DISTRIBUTION.md).
2. Update host-built records:
   - `TimelineMessageQueryFfi` gains `sender`, `since`, `until` and
     `cursorGroupId` with no binding defaults, plus `attachmentType` (default 0)
     and `searchWallClock` (default `false`). They are declared before `before`,
     so positional Kotlin calls shift. See
     [Timeline search filters](#timeline-search-filters-optional).
   - `MarmotDeploymentFfi` drops `keyPackagePreferredClients` and
     `keyPackageLastClients`; delete those assignments. Invite candidates are no
     longer ranked by KeyPackage client.
   - `MarmotOptions` gains `devicePlatform` (default `nil`) between `clientName`
     and `secretStore`. It only labels this device for experimental device
     groups.
   - Output records gain fields without defaults, breaking host-built mocks and
     previews: `AccountSummaryFfi.unlinked`; `leaveBlocked` and `canCancelLeave`
     on group, chat-row, management and capability records; `sticker:
     StickerRefFfi?` on message, received, notification, chat-preview, timeline
     and reply-preview records; `recipientConfirmed`, `importedFrom` and
     `historyImportProvenance` on `TimelineMessageRecordFfi`; two new
     `WipeOutcomeFfi` fields. `deviceCount`, `convergenceParked` and
     `MediaAttachmentReferenceFfi.sourceEpochIdentity` have defaults.
3. Update exhaustive handling:
   - `MarmotKitError` gains `MediaReferenceStaleEpoch`,
     `MediaReferenceEpochUnsettled`, `EventTooLarge { artifact, sizeClass }`,
     `LeaveNotBlocked`, `AccountDevicesActivationRefused`,
     `InvalidChatListQuery { reason }`, `AccountUnlinked`,
     `GroupRecoveryUnsettled`, `GroupRecoverySourceMismatch`, five `Sticker*`
     errors and eight `EmojiSet*`/`EmojiImage*` errors.
   - Remapped failures: busy, closed or full storage and a rejected
     external-signer prompt that reached the host as `Runtime` now arrive as
     `StorageBusy`, `StorageClosed`, `StorageFull` and `ExternalSignerRejected`.
     Wipe-outcome `reason` strings follow the underlying error, whichever layer
     wrapped it: `local storage error`, `unknown local group`,
     `account is the chat's last admin` (`AdminDepletion`), `account is an admin
     of the chat` (`AdminCannotSelfRemove`), `session error` for any other engine
     failure, or `account error`;
     an event every relay refused for size (`Publish` or `Runtime`) is
     `EventTooLarge`; a media send at the wrong epoch (`InvalidMediaReference`)
     is `MediaReferenceStaleEpoch` or `MediaReferenceEpochUnsettled`.
   - `MarmotEventFfi` gains `RecoveryStatusChanged`, `DeviceUnlinked`,
     `LinkedDevicesChanged`, `KeyPackageRefreshOverdueChanged`,
     `UnrecognizedSignInsChanged`, `CompromiseWarningChanged`,
     `DeviceLinkChanged` and `ChatHistoryImportsChanged`. Every case except
     `RecoveryStatusChanged` belongs to experimental device groups: MDK sends
     them only when device groups are on, so ordinary hosts never see them, but
     exhaustive switches still need the arms.
   - `WelcomeDeliveryPending` gains `sizeClass: EventSizeClassFfi?`.
     `HistoryNoticeCauseFfi` gains `UnprovenHistory` and `BeforeRejoin`;
     `SelfMembershipFfi` and `ConversationParticipationFfi` gain `DeviceRemoved`;
     `GroupEventKindFfi` gains `QueuedIntentRefused`.

   No existing exported method was removed, renamed or changed between sync and
   async, and callbacks are unchanged. Compare with the `v0.14.0`
   [method reference](https://github.com/marmot-protocol/mdk/blob/v0.14.0/crates/marmot-uniffi/API-REFERENCE.md).
4. Media references saved by 0.14.0 have no `sourceEpochIdentity`. Sending one
   fails with `MediaReferenceStaleEpoch` and publishes nothing; upload the
   retained bytes again. Saved and received references stay downloadable.
   Preserve `sourceEpochIdentity` unchanged wherever you store an upload result.
5. Recompile C consumers against the regenerated `marmot.h`. See
   [C host changes](#c-host-changes).
6. Keep a device-local copy of each account directory before first open. See
   [Storage upgrade](#storage-upgrade).
7. Update localized copy for the onboarding `SingleDevice` notice and new
   prompts (blocked leave, admin invitee decline, catching up). See
   [Changed defaults](#changed-defaults).
8. Rust hosts: see [Rust host changes](#rust-host-changes). WN Agent operators:
   see [WN Agent and integrations](#wn-agent-and-integrations).

Illustrative Swift for the new event field and errors:

```swift
switch event {
case let .welcomeDeliveryPending(accountIdHex, _, groupIdHex, _, recipientHex, sizeClass):
    showWelcomePending(accountIdHex, groupIdHex, recipientHex, tooLarge: sizeClass != nil)
case .recoveryStatusChanged(let accountIdHex, _):
    refreshRecoveryStatus(accountIdHex)
case .linkedDevicesChanged, .keyPackageRefreshOverdueChanged, .unrecognizedSignInsChanged,
     .compromiseWarningChanged, .deviceLinkChanged, .chatHistoryImportsChanged:
    break // experimental device groups only
default:
    handleExisting(event)
}

do {
    try await marmot.sendMediaAttachments(accountRef: account, groupIdHex: group,
                                          attachments: refs, caption: nil)
} catch MarmotKitError.MediaReferenceStaleEpoch {
    promptReupload() // nothing was published
} catch MarmotKitError.MediaReferenceEpochUnsettled {
    retryLater()
}
```

Kotlin equivalents are `is MarmotEventFfi.WelcomeDeliveryPending -> event.sizeClass`
and `catch (e: MarmotKitException.MediaReferenceStaleEpoch)`.

## Storage upgrade

### Schema migrations

Account databases (`session.sqlite`) advance from schema 116 to 201 on first
open through migrations 0117–0153, 0160–0180, 0200 and 0201 (the gaps are
unused numbers). Each migration runs in its own transaction, so an interrupted
upgrade resumes where it stopped. Tables for experimental device groups are
created but stay empty in ordinary builds.

No migration copies or rebuilds `app_events` or `message_timeline`. A few scan
history-sized tables once, so a large account's first open takes longer and
needs temporary disk for the WAL and new indexes:

- 0167 backfills attachment sources from stored custom-emoji reactions.
- 0141 adds `last_message_tags_json` to chat-list rows, so the first open after
  upgrade rebuilds the chat-list projection of almost every account.
- 0169 adds columns and builds eight indexes on the processed transport-id table,
  which has one row per processed event; 0174 drops those indexes again in the
  same upgrade and leaves the unused columns in place.
- 0173 rebuilds the chat-preview index over `message_timeline` and marks failed
  own sends a peer has reacted to as delivered (`recipientConfirmed`).
- 0175 decodes every saved outbound fanout and group evolution to seed a
  pending-reference watermark. An undecodable row aborts the migration, and the
  account does not open, rather than risking a reused reference.
- 0180 reads stored moderation-removal events once, records the validation
  state and hold targets of each, and blanks the bodies of pruned removals
  whose original decision could not be proved. Nothing keeps a copy of a
  blanked body, including a valid decision that could no longer be proved.
- With native push on, 0117 queues a push-registration share for every joined
  group, so the first open after upgrade republishes once per group.
- 0120, 0153, 0179 and 0200 work per group or per chat: member counts become
  account counts, each group records its current copy for recovery, chat rows
  gain their kind, and the presentation dependency table is rebuilt.

0200 invalidates every stored chat presentation once. Rows keep rendering their
last value while the account's presentation worker rewrites them, but until it
finishes a query with a `Text` node fails with `ChatPresentationNotReady`. 0136
adds the one-time conversion of the old recovery rows; the account worker runs it
after open, not inside the migration.

This guide has no measurement of the 116 → 201 upgrade on a large account. Account
startup now gives up only after 45 seconds without progress rather than 45
seconds in total, so a slow first open that is still migrating no longer fails
startup. If a notification extension can be the first process to open an account
after upgrade, it runs these migrations inside its own time and memory budget;
test that path and prefer letting the main app open first.

The per-account directory cache (`app-cache.sqlite3`) stays at schema 2, and the
shared `shared.sqlite3` schema is unchanged.

### Downgrade and backups

Downgrade is unsupported. A 0.14.0 binary refuses a migrated database with
`UnsupportedSchemaVersion` before reading application tables, and older readers
cannot decode the new stored-message variants. The remedies are to re-upgrade or
to restore a device-local copy of the account directory taken before upgrading:
the databases with their WAL, the `.salt` sidecars, `media/`, and the secret-store
credentials. Restoring an older copy also rewinds MLS state, so prefer
re-upgrading. Keep excluding the account directory from cloud and device backups.

See the [storage-format contract](../marmot-architecture/storage-format-v2.md#versioning-model)
and [local artifact safety](../marmot-architecture/overview/local-artifact-safety.md).

## Changed defaults

### Accounts with several devices

- Every 0.15 build advertises `marmot.group.account-devices.v1` (0x800d) in its
  KeyPackages and leaves. A new group requires it when the creating device and
  every device added at creation advertise it, and that requirement is
  permanent: a client that does not advertise it, including 0.14.0 and older,
  cannot be invited into the group later, and no account may hold more than 20
  devices in it. A group created with a 0.14.0 founder is created as before.
  Existing groups are unchanged until an admin calls `enableAccountDevices`
  (see [Account-devices activation](#account-devices-activation-optional)).
- Creating a group or inviting adds every device of each recipient account: up
  to 20 valid KeyPackages published in the last 30 days, or the single best
  valid one when none is that recent. Lookup is best effort; see
  [known limitations](#acceptance-and-remaining-work). Inviting the inviter's own
  account is refused before anything is sent (`Runtime`), as creating a group
  already was.
- A device joins only through the Welcome that names its own KeyPackage.
- Member rows, rosters, conversation snapshots, `memberCount`, admin counts and
  direct-chat detection count accounts, not leaves. A member row's `deviceCount`
  says how many of that account's devices are in the group. A group-system row
  marks only an account's first device joining or its last device leaving. See
  [Members are accounts](../../crates/marmot-uniffi/README.md#members-are-accounts).

### KeyPackages and sign-out

- New KeyPackages are valid for 30 days (0.14.0: 84), and each device replaces
  its own every 6 to 7 days while it runs and after a Welcome uses it. Expect
  more KeyPackage publishing.
- `signOutAndWipe` and sign-out delete only this device's KeyPackage slot with
  one kind-5 deletion, instead of every KeyPackage the account published.
  `keyPackagesDeleted` on `SignOutOutcomeFfi` and `WipeOutcomeFfi` is now 1 when
  a relay accepted that deletion, otherwise 0.
- `signOutAndWipe` now also leaves chats the account administers. In a chat
  where another account is an active admin and no other device of this account
  remains, it steps the account down and leaves, waiting up to about 30 seconds
  for a commit that removes this device. A last admin, or an admin whose other
  device stays in the chat, keeps its leaf and is reported in
  `groupLeaveFailures`. Their `reason` strings are new: `account is the chat's
  last admin`, `account is an admin of the chat`, `account is an admin and
  another of its devices stays in the chat`, `account's step-down as admin was
  not accepted in time` and `account is not an admin and its removal was not
  seen in time`. The call keeps running when the caller cancels; show
  progress rather than assuming an instant return. Plain `signOut` is
  unchanged: it keeps chat membership and admin rights.
- A `clientName` over 64 bytes is left off the KeyPackage.
- Reopening an account reuses its stored, validated identity proof, so a
  NIP-46/Amber signer is no longer asked to sign again on every reopen.

### Recovery and automatic rejoin

- The recovery runner owns account history. Catch-up after time offline is
  bounded and paced, history arrives in order, and a group's newer live messages
  wait until its fetched backlog is admitted, so they can appear slightly later
  after a reconnect. Notification wakes fetch only the history their messages
  wait on. `RecoveryStatusChanged` and `UnprovenHistory` notices are now
  produced; see [Account recovery status](#account-recovery-status-optional).
- Account workers rejoin a group copy that became `Unrecoverable` through an
  authenticated handshake with an admin device over the account inbox, with
  bounded retries. The existing Repair action rearms a parked attempt;
  restarting does not reset its budget. Usable forks still need the user's
  consent. A rejoined group raises one `BeforeRejoin` notice: messages from
  before the rejoin that the device had not received are unavailable. See the
  [automatic rejoin contract](../marmot-architecture/invitation-recovery.md#automatic-rejoin-of-an-unrecoverable-copy).

### Leaving and invitations as an admin

`requiresSelfDemoteBeforeLeave` is now also `true` for an admin invitee with a
pending invitation: `declineGroupInvite` returns `AdminCannotSelfRemove` until
`selfDemoteAdmin` succeeds. Admin Leave is still refused until self-demotion, as
in 0.14.0. A leave that later becomes blocked is now shown; see
[Blocked leaves](#blocked-leaves-optional).

### Other defaults

- Push notifications reach every device of a member, members added later learn
  existing tokens, and devices repair missed tokens inside each group. This adds
  push-token traffic (kinds 447–449) after Adds and on repair; no API change.
- Onboarding no longer produces `OnboardingIssueFfi.MultiDeviceUnsupported`
  (the case remains), and the `SingleDevice` step explains what signing in alone
  restores. Update the copy as the README's
  [Single-device notice](../../crates/marmot-uniffi/README.md#single-device-notice)
  shows.
- `resolvePublicEventPreview` asks the deployment's discovery indexers and up to
  four cached author write relays (eight relays at most) once more when relay
  hints and directory relays miss, so pasted `note1`, hex and author-only
  `nevent` references resolve. Neutral deployments dial no indexer.
- `sendCustomEvent` refuses device-group kinds 457–461, 473, 475 and 476.
- Timeline search lowercases non-ASCII text, so `école` finds `ÉCOLE`.
- Ordinary constructors refuse an account that holds or is joining a device
  group: its session fails with `Runtime` `experimental_device_groups_required`.
  Only roots previously opened by an experimental build are affected; see
  [Experimental device groups](#experimental-device-groups).

## Feature adoption

These are local unless stated; call them off the UI thread. MarmotKit's
[threading model](../../crates/marmot-uniffi/README.md#threading-model) is unchanged.

### Chat-list queries and select all (optional)

Filter the chat list and select every chat a filter matches, for folders and bulk
actions. See [Chat-list select all and filtered queries](../../crates/marmot-uniffi/README.md#chat-list-select-all-and-filtered-queries).

- `openChatListQueryWindow(accountRef, query, initialRows)` is
  `openChatListWindow` narrowed by `ChatListViewQueryFfi { view, filter }`.
  `filter` is a flat `ChatListFilterNodeFfi` list: node 0 is the root and every
  other node is the child of exactly one earlier node. `All`, `Any` and `Not`
  combine `Condition` (`ChatListConditionFfi`: `Unread`, `Pinned`, `Archived`,
  `Direct`, `Group`, `Muted`, `HasDraft`, `PendingSend` and more), `GroupIds`,
  `Text` and `MessageText`. The existing `openChatListWindow` is unchanged and
  equals an unfiltered query.
- `chatListQueryIds(accountRef, query)` and `chatListIds(accountRef, view)` return
  every matching chat ID in display order, beyond any window; use the length as
  the count. Call `revalidateChatListQueryIds` (or `revalidateChatListIds`)
  right before a bulk action: it returns the subset still matching, in your
  order, and never adds chats. Then run the existing per-chat commands.
- Limits: 64 nodes, 8 levels, 500 group IDs and 1024 bytes of text, refused with
  `InvalidChatListQuery { reason: ChatListQueryErrorFfi }` before any read. A
  window refuses `MessageText` (`MessageTextInWindow`) because it scans history.
- While rows or presentation are still being prepared (after migration 0200,
  for example), the ID queries and any query with a `Text` node fail with
  `ChatPresentationNotReady` rather than return a partial list; retry.

Illustrative Kotlin (unread groups, excluding some):

```kotlin
val query = ChatListViewQueryFfi(
    view = ChatListViewFfi.CHATS,
    filter = listOf(
        ChatListFilterNodeFfi.All(children = listOf(1u, 2u, 3u)),
        ChatListFilterNodeFfi.Condition(ChatListConditionFfi.UNREAD),
        ChatListFilterNodeFfi.Condition(ChatListConditionFfi.GROUP),
        ChatListFilterNodeFfi.Not(child = 4u),
        ChatListFilterNodeFfi.GroupIds(groupIds = excludedIds),
    ),
)
val window = marmot.openChatListQueryWindow(account, query, null)
val selected = marmot.chatListQueryIds(account, query)
// later, before archiving:
val stillMatching = marmot.revalidateChatListQueryIds(account, query, selected)
```

### Timeline search filters (optional)

`timelineMessages(accountRef, query)` can filter by `sender` (any form
`normalizeMemberRef` accepts), inclusive `since` and exclusive `until` (Unix
seconds) and `attachmentType` (0 Any, 1 Image, 2 Video, 3 Audio, 4 File, 5 any
attachment; other values return `Runtime`). Filters combine with `AND` before the
page limit; the existing 200-row page cap applies. `searchWallClock = true`
orders by `(timelineAt, messageIdHex, groupIdHex)`; to continue an account-wide
wall-clock search, pass the last row's group as `cursorGroupId` with
`before`/`beforeMessageId`. Keep filters unchanged between pages.
`subscribeTimelineMessages` is unchanged. The call is synchronous and local, so
run it off the UI thread. See
[Advanced timeline search](../../crates/marmot-uniffi/README.md#advanced-timeline-search).

Illustrative Swift (every caller must now pass the four new optional fields):

```swift
let query = TimelineMessageQueryFfi(
    groupIdHex: group, search: "invoice", sender: nil,
    since: startOfMonth, until: nil, attachmentType: 4,
    cursorGroupId: nil, before: nil, beforeMessageId: nil,
    after: nil, afterMessageId: nil, limit: 50)
let page = try marmot.timelineMessages(accountRef: account, query: query)
```

### Stickers (optional)

Sonar-compatible packs: `syncStickerPacks` and `fetchStickerPack` use the
network; `stickerPacks` and `stickerPack` are synchronous local reads;
`installStickerPack` / `uninstallStickerPack` edit the published installed list.
Render a message's `sticker: StickerRefFfi?` with `fetchStickerAsset`, never by
fetching a URL yourself, and send with `sendSticker(accountRef, groupIdHex,
stickerRef)`. `importSignalStickerPack` validates a Signal link and then refuses
with `StickerImport`. See [Stickers](../../crates/marmot-uniffi/README.md#stickers).

### Emoji sets (optional)

NIP-51 kind-30030 sets. `syncEmojiSets`, `fetchEmojiSet`, `emojiSets`,
`emojiSet` and `userEmojiList` never download images. Image downloads reveal the
user's IP address to hosts the set's author chose, so call `fetchEmojiSetAsset`,
`fetchEmojiSetCover` and `installEmojiSet` only after the user acts.
`installEmojiSet(accountRef, coordinate, expectedEventIdHex, control)` stores the
version the user was shown (another fails with `EmojiSetChanged` before any
download). Create an `EmojiSetInstallControlFfi()` per install, read
`progress()`, and `cancel()` from any thread; a cancelled install fails with
`EmojiSetInstallCancelled` and stores nothing. Caps: 50 sets, 500 emoji and
32 MiB per set, 128 MiB in all (`EmojiSetLimit`). Send an installed emoji by
uploading `readInstalledCustomEmoji` bytes as an attachment. See
[Emoji sets](../../crates/marmot-uniffi/README.md#emoji-sets).

### Custom reaction artwork (optional)

`reactionAttachment(accountRef, groupIdHex, reactionMessageIdHex)` resolves an
active custom-emoji reaction's encrypted artwork to an `AttachmentEntryFfi`, or
`nil`. It is a bounded local read and starts no download; acquire the returned
source slot with the existing attachment calls. Custom-emoji reaction sends are
bound to their upload branch like media sends.

### Blocked leaves (optional)

If the selected branch makes the account the group's last active admin after a
leave was accepted (two admins left at once, say), the leave cannot finish. The
chat keeps reading as leaving, and `leaveBlocked` is set on the group record, the
chat-list row and management state. While `canCancelLeave` holds, offer Cancel:
`cancelLeave(accountRef, groupIdHex)` clears the leave on this device only and the
chat reads as joined again. In any other state it fails with `LeaveNotBlocked`.
MDK never retries or reverses the leave by itself. See the README's leave contract
under [Linked devices](../../crates/marmot-uniffi/README.md#linked-devices).

Illustrative Swift:

```swift
let state = try await marmot.groupManagementState(accountRef: account, groupIdHex: group)
if state.leaveBlocked && state.canCancelLeave, await userChoosesCancel() {
    try await marmot.cancelLeave(accountRef: account, groupIdHex: group)
}
```

### Undelivered Welcomes (optional)

`pendingWelcomeDeliveries(accountRef)` lists Welcomes still owed after a
confirmed create or Add, oldest first (`groupIdHex`, `messageIdHex`,
`recipientHex`, `recordedAt`, `sizeClass`). The event still fires once per
process and Welcome; re-read the query for later causes. `sizeClass` diagnoses
an observed all-relay size refusal; `nil` proves neither delivery nor
non-delivery. MDK keeps retrying. See
[Undelivered Welcomes](../../crates/marmot-uniffi/README.md#undelivered-welcomes).

### Account recovery status (optional)

`accountRecoveryStatus(accountRef)` returns the groups still catching up
(`catchingUpGroupIdsHex`), whether the inbox is (`inboxCatchingUp`), and every
notice (`notices`). Show the first two as "catching up" and re-read on
`RecoveryStatusChanged`. See
[History may be incomplete notices](../../crates/marmot-uniffi/README.md#history-may-be-incomplete-notices).

### Account-devices activation (optional)

An existing group gets the account-devices component only when an admin asks.
Call `accountDevicesActivation(accountRef, groupIdHex)` and offer the action only
on `Eligible`; otherwise explain `NotAdmin`, `AlreadyEnabled`, `LegacyGroup`,
`MembersNeedUpdate`, `DevicesNeedReplacement` or `DeviceLimitExceeded`. The answer
never names members. `enableAccountDevices(accountRef, groupIdHex)` sends one
admin Commit that can never be undone, checks again, and fails with
`AccountDevicesActivationRefused` and the same reason. Once enabled, clients
older than 0.15 can no longer be invited into that group. See
[Turning on account devices](../../crates/marmot-uniffi/README.md#turning-on-account-devices).

### Experimental device groups

Pairing, linked devices, sign-in review, compromise warnings, history transfer and
backups are experimental: compiled only with the `dev-device-groups` build feature
and enabled only through `Marmot.newWithExperimentalDeviceGroups`,
`marmot_client_new_with_experimental_device_groups` or, in Rust,
`MarmotAppConfig::with_dev_device_groups(true)`. In ordinary builds and
constructors their reads return empty, `false` or zero, their actions are refused
(`Runtime`), and the experimental constructor returns
`experimental_device_groups_unavailable`. Do not ship them.
See [Experimental device-group test builds](../../crates/marmot-uniffi/README.md#experimental-device-group-test-builds).

## C host changes

Recompile against the `marmot.h` shipped with the exact library. Input structs
are read from host memory, so a mismatched header misreads silently; hand-written
FFI declarations (ctypes, cgo, Dart) are not compiler-checked. Initialize input
structs with `{0}`.

- **Removed:** `marmot_deployment_set_key_package_client_preference`.
- **Mid-struct insertions** (every later field moves):
  `MarmotMediaAttachmentReference` gains `char *source_epoch_identity` after
  `source_epoch` (input to every media and reaction send, `marmot_download_media`
  and `marmot_build_media_imeta_tag`; embedded in `MarmotMediaRecord` and

New functions mirror the features above (`marmot_open_chat_list_query_window`,
`marmot_chat_list_query_ids`, `marmot_revalidate_chat_list_query_ids`,
`marmot_chat_list_ids`, `marmot_revalidate_chat_list_ids`, `marmot_cancel_leave`,

`marmot_account_recovery_status`, `marmot_account_devices_activation`,

new call blocks. Differences from Swift/Kotlin:

- No structured error payloads: the chat-list query and activation refusal
  reasons, the `EVENT_TOO_LARGE` artifact and size class, and the
  `EMOJI_SET_CHANGED` current event id are only in the thread-local
  `marmot_last_error_message`; read it once, immediately.
- Chat-list queries take a borrowed `MarmotChatListViewQuery { view, filter,
  filter_len }`; enums are `uint32_t` (out of range returns
  `INVALID_CHAT_LIST_QUERY`) and optional values use `uint8_t` presence flags.
- `MarmotEmojiSetInstallControl` is host-owned: free it only after the install
  has returned and every other call on it has finished; cancel from another
  thread. See [Emoji set installs](../../crates/marmot-c/README.md#emoji-set-installs).
- `marmot_reaction_attachment` writes NULL with `MARMOT_STATUS_OK` when nothing is
  available; free a standalone result with `marmot_attachment_entry_free`, never
  an entry borrowed from a page.
- `sticker` and `history_import_provenance` are freed by their parent record.
  `marmot_sticker_ref_free`, `marmot_sticker_free`, `marmot_sticker_list_free` and
  `marmot_installed_custom_emoji_free` are exported, but calling them on an
  embedded member is a double free.
- Read `size_class` on the Welcome event and list only when `has_size_class` is
  set. `marmot_cancel_leave` allocates nothing.
- `marmot_client_new_with_experimental_device_groups` exists in every build and
  returns `MARMOT_STATUS_RUNTIME` without the feature.

`key_packages_deleted` on `MarmotWipeOutcome` and `MarmotSignOutOutcome` is now 0
or 1, and `MarmotRelayFailure.event_id_hex` is empty when the failed deletion
targeted the whole slot. See the [C README](../../crates/marmot-c/README.md)
([timeline search](../../crates/marmot-c/README.md#advanced-timeline-search),
[blocked leaves](../../crates/marmot-c/README.md#blocked-leaves)) and the
[symbol inventory](../../crates/marmot-c/API-REFERENCE.md).

## Rust host changes

- **Build.** Building `marmot-app` or anything that depends on it needs Odin
  `dev-2026-10` (revision `84bc3fc`), because `marmot-markdown` parses Markdown
  in Odin. Install it with `scripts/install-odin.sh` or set `ODIN`; otherwise
  `odin` on `PATH` is used. Published MarmotKit, C and WN Agent artifacts are
  unaffected.
- **Crates.** `cgka-session` is renamed `marmot-session`, and the runtime half of
  `marmot-account` (`AccountDeviceRuntime`, `AccountError`, `MaintenanceTiming`,
  `KeyPackagePublisher`, routing and effect types) moves there. Diagnostics
  exporters move to `marmot-observability`; old paths are re-exported except
  `product_analytics::configure_product_analytics_from_environment`, now
  `marmot_app::configure_product_analytics_from_environment`. Other new
  unpublished crates: `marmot-pairing` and `marmot-markdown-ast`.

  `SessionError::Engine(EngineError::Storage)`. A custom `KeyPackagePublisher`
  must implement `withdraw_key_package_slot` and `delete_key_package_event`,

  `ConversationParticipation`, `GroupEvent` (`QueuedIntentRefused`,

  variants or fields. These enums are exhaustive.
- **Records.** `TimelineMessageQuery` gains `sender`, `since`, `until`,
  `attachment_type` (`TimelineAttachmentType`), `search_wall_clock` and

  `device_platform` and `dev_device_groups` and loses

## WN Agent and integrations

- **Protocol.** The control protocol stays `marmot.agent-control.v2` and only gains
  requests: `group_create_capabilities` (answered with `initial_admins`) and
  `group_create_with_admins` for founding co-admins; `attachment_get`,
  `download_attachment` and `release_attachment` for historical inbound
  attachments with leased local copies (release every lease;
  `attachment_release_failed` is retryable). `AgentControlMediaRef` gains optional
  `source_epoch_identity`. Rust `AgentControlRequest`/`AgentControlResponse`
  matches must handle the new variants.
- **Upgrade together.** A 0.14.0 `wn-agent` closes the control socket without a
  reply on any request it cannot parse, including `group_create_capabilities`;
  treat that as "unsupported". Upgrade `wn-agent` and its Hermes, OpenClaw and
  terminal-harness plugins together.
- **OpenClaw.** The plugin requires OpenClaw 2026.10.10 or newer (was 2026.7.1)
  and Node 24.22.1+ (24.x) or 26.12.1+ (was 22.19). The installer checks Node
  even with `--no-configure-openclaw`, and `--yes` runs
  `openclaw plugins install --force --accept-capabilities`.
- **Connector-only install.** `scripts/install-wn-agent.sh` installs and
  supervises `wn-agent` alone for your own control-socket client (home
  `~/.marmot-agents/standalone`, service `wn-agent-standalone` /
  `org.marmot.wn-agent.standalone`), with `--bootstrap` or
  `--import-identity`. See [custom clients](../../integrations/custom-client.md).
- **Relays.** `wn-agent` started without `--relay` reads `MARMOT_RELAYS` /
  `MARMOT_RELAY` and then falls back to the White Noise relays (0.14.0 started
  with none); `--no-default-relays` restores the old behavior. Installed
  services pass `--relay` and are unaffected. Startup adopts the account's
  published relay lists and publishes its own only when a complete read proves
  none exist; an inconclusive read fails with `relay_list_inconclusive`.
  `wn-agent bootstrap --relay` accepts comma-separated URLs.
- **Diagnostics.** `wn-agent doctor` checks the home, socket, token, relays,
  accounts, daemon, protocol, KeyPackage and relay health (`--json`; nonzero exit
  on failure).
- **CLI.** `wn media send` needs the complete `media upload` JSON, including
  `source_epoch_identity`; references rebuilt from `media list` fail with
  `media_reference_stale_epoch`. Timeline search gains `--sender`, `--since`,
  `--until`, `--attachment-type` and `--cursor-group-id`. `wn daemon start` waits
  up to 60 seconds; a daemon still migrating then is stopped with
  `daemon_start_timeout`, and the next start resumes the migrations. `wnd` no
  longer grows about 3 MB per request. Admin leave is refused until
  `groups self-demote`, as in the bindings.
- **Installers.** Install only from the immutable `wn-agent-v0.15.0` release with
  sibling `.sha256` verification.

## Changes requiring no new calls

- **Sends.** Sends queued while offline publish after reconnect. A send never
  goes ahead of an intent queued earlier in the same group. A Welcome is
  published only once its Commit is, and every failed Welcome publish records a
  pending delivery. Failed convergence retries back off and park
  (`convergenceParked`; `retryGroupConvergence` resumes them). A queued intent
  the settled group refuses is retired with `QueuedIntentRefused`. Oversized
  events report `EventTooLarge`. Transfer-state changes are reported immediately.
- **Correctness.** A write error while receiving a valid message no longer loses
  it; invite recovery and late group-record failures no longer leave stale rows;
  a member who left on a losing branch reaches the selected one; concurrent
  directory updates no longer erase relay lists; an accepted `blockUser` no
  longer reports `BlockPublicationUncertain` because the database was busy.
- **Performance.** Idle maintenance ticks no longer open write transactions.
  Cached user search ranks in SQL and finds identities past the 10,000th.
  Dropping a `MarmotApp` without `shutdown()` frees its relay plane.
- **Privacy and security.** Local forensic audit files expire 30 days after
  their last write. The pinned Nostr SDK rejects tampered events even when their
  id is cached, and directory events are verified before they are forwarded or
  stored. `elliptic-curve`/HPKE (RUSTSEC-2026-0387), `openssl` and the OpenClaw
  plugin's npm dependencies are updated.

The retired-relay denylist is unchanged.

## Acceptance and remaining work

Before shipping an app on 0.15.0:

- Compile against the matched artifacts with every host-built record and
  exhaustive `switch`/`when` updated; for C, rebuild every consumer.
- Upgrade a real, large 0.14.0 account in place: time the first open, watch free
  disk and WAL size during it, then reopen and confirm the second open migrates
  nothing. Repeat with the app killed mid-upgrade, and with the notification
  extension as the first opener.
- Interoperate with a 0.14.0 peer: an existing group keeps working; a new group
  with the 0.14.0 peer among its founders does not require the component; a 0.14.0
  peer cannot be invited into a new 0.15-only group. Decide what your UI says then.
- Test offline and cold start: queue sends offline, reconnect, and confirm they
  publish in order; confirm catch-up after a long absence and that
  `accountRecoveryStatus` clears.
- Push to several devices of one account and to a newly added member.
- Sign out an admin of a shared chat (step-down wait, cancellation); confirm only
  this device's KeyPackage is deleted. Decline as an admin invitee; Cancel a
  blocked leave.
- Re-upload a media reference saved by 0.14.0, and exercise search filters
  (sender, date range, attachment type, non-ASCII text, wall-clock paging).
- If adopted: select-all with revalidation and a text filter during the 0200
  rewrite, emoji-set install cancellation, and account-devices activation.
- Report evidence by stage: source, host smoke, packaged artifact, consuming
  app, real device.

What was validated: every change in this comparison landed through the merge
queue's CI matrix, which includes the per-migration upgrade tests and the 0.10.4
account fixture upgraded through every migration with older-runner refusal; the
binding-docs gate passes for the MarmotKit method and C symbol inventories at this
source. Not validated here: upgrade
time and disk use on a large 0.14.0 account, a schema-116 fixture from a 0.14.0
binary, device-level push across multiple devices, and app-level adoption on iOS
or Android.

Known limitations:

- Adding every device of an account is best effort: a device whose KeyPackage a
  relay does not return in time is left out until the account is invited again,
  lost devices are not re-added automatically, and an account for which one
  relay returns a full page (500) of KeyPackages or of KeyPackage deletion
  requests cannot be invited.
- Right after a reconnect, a new send can still go out ahead of older unsent ones.
- Migration 0175 refuses to open an account with an undecodable saved fanout or
  group evolution rather than guess.
- A failed legacy group create in an earlier release can have left orphaned MLS
  state; 0.15 stops creating it but does not purge it.
- The automatic-rejoin handshake's inner event kind is still under discussion in
  the specification ([marmot#451](https://github.com/marmot-protocol/marmot/issues/451)).
- Still open from 0.14.0:
  [#2237](https://github.com/marmot-protocol/mdk/issues/2237) (a message more
  than five epochs late stays undecryptable without a notice);
  group-change prompts [#2277](https://github.com/marmot-protocol/mdk/issues/2277),
  [#2283](https://github.com/marmot-protocol/mdk/issues/2283),
  [#2389](https://github.com/marmot-protocol/mdk/issues/2389) and
  [#2286](https://github.com/marmot-protocol/mdk/issues/2286);
  [#2253](https://github.com/marmot-protocol/mdk/issues/2253) (group data
  extension order); [#2158](https://github.com/marmot-protocol/mdk/issues/2158)
  (an upload in flight across an epoch change is lost; its send now fails with
  the typed `MediaReferenceStaleEpoch`); and
  [#1445](https://github.com/marmot-protocol/mdk/issues/1445) (WN Agent's control
  socket grants its whole API to any authenticated client).
