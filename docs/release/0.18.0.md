# MDK 0.18.0

MDK 0.18.0 releases the Rust workspace, WN Agent, MarmotKit (iOS, macOS and
Android), and Marmot C from one source commit. See the
[0.17.0 → 0.18.0 client upgrade guide](../integration/0.18.0.md) for the
device-group default, the new errors and events, the record and layout
changes, storage and the Rust API changes.

## Highlights

- Multi-device ships. Every artifact now includes device groups, and every
  constructor opens with them on: linking a new device, the linked-device
  list, sign-in review, history transfer, backups and admin step-down on
  Leave work without a special build or constructor. There is no binding
  switch to turn them off. Ship this library in every process that opens the
  root, extensions included.
- A newly linked device gets each chat as the device that adds it holds it:
  confirmed chats arrive confirmed instead of as invitations from the account
  itself (one with an invitation generation once its shared decision
  arrives), and unanswered ones arrive pending from their real inviter. The
  device that approved the link adds the new device to its chats while it is
  active, so the other devices no longer race it and fork chats. Link status
  reports how many chats remain on each device (`chatProgress`).
- An invitation answered on one linked device shows as answered on the
  other within seconds instead of about a minute.
- Idle accounts stop waking every 15 seconds. Session maintenance, device
  pairing, device-group passes, recovery, attachments, avatars and the other
  maintenance jobs run when their data says they are due or an event wakes
  them, and an idle maintenance tick no longer writes the database.
- Group changes left pending by an unclear relay answer now resolve where
  MDK can tell what happened. MDK confirms one when its own subscription
  receives the change back or a relay returns it on a read ten minutes in,
  and gives up one that reached no relay once the device shows it is online.
  A change a relay may hold but never confirms stays pending and is never
  given up; `groupPendingCommit` shows it as `Stuck`. Changes given up after
  their call returned are recorded until acknowledged
  (`groupChangesNotDelivered`, `GroupChangeNotDelivered`). A queued message
  is no longer prepared a second time, as a new message, after a retry or a
  restart.
- Direct-follow availability: `followAvailabilityPage` reads, offline, which
  followed accounts have a current Marmot KeyPackage, and
  `refreshFollowAvailability` checks up to 100 of them with partial progress
  and cancellation.
- Composer drafts can hold large attachments as files
  (`stageMessageDraftAttachmentFile`) instead of in-memory buffers, kept
  across saves and restarts and uploaded straight from the encrypted media
  store.
- New: emoji-scoped reaction removal (`unreactFromMessageMatching`) with a
  typed `ReactionNotFound`; direct chats founded with a disappearing-message
  duration (`startDirectConversationWithOptions`); durable attachment-removal
  cursors for host caches (`attachmentRemovals`); the `invalidated` flag on
  raw message records.
- Onboarding: relay checks no longer fail healthy relays behind a wrapped
  `auth-required` or a slow answer; an inconclusive relay or inbox check can
  be fixed from the step; declared relays that cannot serve their role can be
  removed; other-installation packages name the publishing app; and a
  single-device acknowledgment survives a long pause.
- A group send with no relay MDK may send to fails as the typed
  `NoUsableRelay` instead of a generic publish error.
- The v5 audit log records every invite Welcome on the sender, Welcome sizes
  and withdrawals, and pending commits that go stuck, confirm without an `OK`
  or are given up. Hosts exporting v5 audit records should repin and deploy
  the White Noise audit receiver before shipping so it accepts the new kinds.
- Fixes: sticker packs and emoji sets are also read from the configured
  relays, so an imported account's pack browser is no longer empty; a retried
  emoji-set install no longer deletes emoji the user has; NIP-22 comments
  project their parent, media and author edits, and their media stays
  decryptable after the epoch advances; history recovery continues across
  partial epoch advances and no longer stalls a newly linked device on
  pre-join history; a linked-then-removed device no longer returns as a new
  sign-in; a fresh account no longer fails KeyPackage rotation because an early
  read created its database; runtime shutdown lets a Welcome that is still
  publishing finish for up to 2 s; and the OpenClaw plugin installs and
  updates on OpenClaw 2026.10.10 and later.

## Compatibility

Ship generated Swift/Kotlin, native libraries and C headers from this exact
cohort together, in the app and in every extension that opens the same root.

- Device groups are on in every constructor. `newWithConfiguration` now links
  devices, runs backups and steps a nonlast admin down on Leave
  (`requiresSelfDemoteBeforeLeave` is false), and
  `newWithExperimentalDeviceGroups` is the same open. Once 0.18.0 has opened
  an account, a process on an older library refuses its database
  (`UnsupportedSchemaVersion`), even for a single-device account; see the
  [upgrade guide](../integration/0.18.0.md#required-upgrade-steps).
- `MarmotKitError` gains `GroupCommitPending`, `NoUsableRelay` and
  `ReactionNotFound`; `GroupEventKindFfi` gains `GroupChangeNotDelivered`;
  `OnboardingActionFfi` gains `RemoveUnusableRelays`. Exhaustive switches must
  add them. Group changes, a member's leave and an invite decline fail with
  `GroupCommitPending` while the group's own commit is pending.
- Records gain fields: `AppMessageRecordFfi.invalidated`,
  `DeviceLinkSnapshotFfi.chatProgress`, `OnboardingDevicePackageFfi.client`,
  `OnboardingRelayTagChangeFfi.removalReason`,
  `OnboardingRepairProposalFfi.inconclusive`,
  `SelectedMessageDraftAttachmentFfi.fileBacked` and
  `AttachmentStorageUsageFfi.draftBytes`. Code that constructs them directly
  must pass the new fields.
- Usage diagnostics add the `mdk_onboarding_summary` aggregate, so the
  registry revision changes and users who opted in are asked to accept again.

C hosts must recompile. `MarmotAppMessageRecord`, `MarmotDeviceLinkSnapshot`,
`MarmotOnboardingDevicePackage`, `MarmotOnboardingRelayTagChange`,
`MarmotOnboardingRepairProposal`, `MarmotSelectedMessageDraftAttachment` and
`MarmotAttachmentStorageUsage` change layout. Statuses `131`
(`GROUP_COMMIT_PENDING`), `132` (`REACTION_NOT_FOUND`) and `133`
(`NO_USABLE_RELAY`) are appended, as are
`MARMOT_GROUP_EVENT_KIND_GROUP_CHANGE_NOT_DELIVERED` and
`MARMOT_ONBOARDING_ACTION_REMOVE_UNUSABLE_RELAYS`. The `dev-device-groups`
feature and `--dev-device-groups` build flags are gone.

Rust hosts: `MarmotAppConfig::dev_device_groups` is renamed `device_groups`
and defaults to true; the `dev-device-groups` and `unreleased-device-pairing`
features are gone; `OutboundIntentStorage` gains the not-delivered methods;
`SendIntent::AddOwnAccountDevices` and `GroupEvent::GroupJoined` gain
`forwarded`; `EngineError` gains `SiblingAddUnsettled`; and several engine and
`storage-sqlite` signatures change. See the upgrade guide.

Storage: account databases migrate from schema 207 to 216 (migrations 0208 to
0216), the shared database from 4 to 5 and each account's directory cache
from 2 to 3 on first open. Downgrade is unsupported: 0.17.0 refuses the
upgraded databases. Keep a device-local copy
of the MDK data directory before upgrading, taken while the app and every
extension are stopped.

Wire: a sibling Welcome that forwards how the adding device holds a chat is
version 3, which devices older than 0.18.0 cannot read. Link devices only
between 0.18.0 builds. Runtimes with device groups on (the default)
advertise the device-roster component.

WN Agent: the agent-control protocol is unchanged. The connector runs its
accounts with device groups on, through the runtime's new default, and has no
switch for them. `wn` and `wnd` include multi-device, on by default
(`WN_DEVICE_GROUPS=0` turns it off for both);
`wn groups` adds `pending-commit`, `changes-not-delivered` and
`acknowledge-change-not-delivered`, and JSON errors add `group_commit_pending`
and `no_usable_relay`.

## Known issues

- A linked device can show an accepted chat as an invitation until its shared
  decision arrives ([#3556](https://github.com/marmot-protocol/mdk/issues/3556)),
  and a queued sibling Add can forward invitation facts that changed while it
  waited ([#3559](https://github.com/marmot-protocol/mdk/issues/3559)).
- A message sent while a new device is joining a chat can be lost on that
  device ([#3537](https://github.com/marmot-protocol/mdk/issues/3537)); the
  approver hold's hand-off edges remain
  ([#3561](https://github.com/marmot-protocol/mdk/issues/3561)).
- Startup hydration re-drives every outstanding fanout after each batch of
  four groups, which delays live transport on accounts with many groups
  ([#3367](https://github.com/marmot-protocol/mdk/issues/3367)).
- Pending Welcomes and a few other reads still go through the account
  worker's queue ([#3273](https://github.com/marmot-protocol/mdk/issues/3273)).
- Still open from earlier releases:
  [#2237](https://github.com/marmot-protocol/mdk/issues/2237) (late messages
  more than five epochs behind),
  [#2277](https://github.com/marmot-protocol/mdk/issues/2277),
  [#2283](https://github.com/marmot-protocol/mdk/issues/2283),
  [#2389](https://github.com/marmot-protocol/mdk/issues/2389) and
  [#2286](https://github.com/marmot-protocol/mdk/issues/2286) (group-change
  prompts), [#2253](https://github.com/marmot-protocol/mdk/issues/2253) (group
  data extension order), [#2158](https://github.com/marmot-protocol/mdk/issues/2158)
  (an upload in flight across an epoch change is lost) and
  [#1445](https://github.com/marmot-protocol/mdk/issues/1445) (WN Agent's
  control socket grants its whole API to any authenticated client).

## Release artifacts

- `v0.18.0`: MDK source snapshot; workspace crates remain unpublished to crates.io.
- `wn-agent-v0.18.0`: WN Agent, terminal harness binaries, gateway plugins and
  checksum-paired installers.
- `marmotkit-v0.18.0`: iOS/macOS XCFrameworks, shared Swift source, platform
  privacy resources, Android Kotlin and all four JNI ABIs with
  `android-elf.json`, manifests and checksums.
- `marmotc-v0.18.0`: C library/header bundle and checksum.

Verify sibling SHA-256 files and source/version manifests; Apple binary ZIPs also
have SwiftPM checksums. Follow the
[distribution guide](../../crates/marmot-uniffi/DISTRIBUTION.md). Dated
`0.18.0-nightly.*` builds are for testing only; pin this release instead.
